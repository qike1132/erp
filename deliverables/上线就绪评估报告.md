## 一、结论（TL;DR）

# 🔴 不具备正式上线条件（No-Go）

**核心判断**：系统**已在实际使用**（3,722 张订单、45,241 条审计日志等真实数据），
但**当前运行形态是「开发模式 + 真实数据」**，且存在 **5 项上线阻断缺口**，
其中一项（B5）**已造成真实数据损坏**。

> **最需要立刻知道的两件事**：
> 1. **最新备份是 2026-09-10，已过期 5 天**，且定时备份服务（`erp-arq`）处于停止状态 —— **当前数据无有效备份**。
> 2. **API 文档端点对全网开放**（`/api/docs` 返回 200，`/api/openapi.json` 暴露 342 条路由 / 413 个 schema，服务绑定 `0.0.0.0`）。

**估算修复成本**：阻断项 P0 全部处理约 **1 个工作日**（不含数据修复验证与 UAT）。

## 三、上线阻断项 🔴（必须处理）

### B1 — 无有效备份，且备份链路已停摆 【最紧急】

| 事实 | 证据 |
|---|---|
| 最新备份 | `backups/server/erp_backup_20260910_175156.zip`（**2026-09-10 17:51，距今 5 天**） |
| 备份调度机制 | ARQ cron `scheduler_poller` 每 5 分钟扫描 `backup_schedule` 表入队 |
| **ARQ 服务状态** | `erp-arq` = **Stopped** → **定时备份不再运行** |
| 备份目录 | `backups/daily/` `manual/` `monthly/` `weekly/` **均为空**（0 文件） |
| 保留配置 | `BACKUP_RETENTION_DAYS=30`、`BACKUP_RETENTION_COUNT=100` |

**风险**：数据库当前无 5 天内的可恢复副本。若磁盘/库损坏，最多丢失 5 个工作日数据。

**动作**：
1. 立即执行一次全量备份并验证产物可解压；
2. 恢复 ARQ 服务（`net start erp-arq`）或改用 Windows 计划任务驱动备份；
3. 补一次**恢复演练**（最近一次演练记录停留在 `2026-08-23`）。

### B2 — API 文档对全网开放

| 事实 | 证据 |
|---|---|
| `/api/docs` | **HTTP 200**，返回完整 Swagger UI |
| `/api/openapi.json` | **HTTP 200**，暴露 **342 条路由 / 413 个 schema** |
| 监听地址 | `0.0.0.0:5002`（**全网卡**，局域网可达） |
| 根因 | `.env` **未设置 `APP_ENV`** → `config.py:46-48` 判定为非生产 → `DOCS_URL`/`OPENAPI_URL` 保持开启 |

**风险**：整个 API 结构（含全部请求/响应 schema、参数、权限码线索）对局域网内任意主机未认证可读，为攻击者提供完整攻击面地图。

**动作**（二选一，推荐同时）：
1. 设置 `APP_ENV=production`（或经 `python start.py --prod` 启动）→ 文档端点自动关闭；
2. 若确需文档，改为仅绑定 `127.0.0.1` 或加访问白名单。

### B3 — 以开发模式运行（非生产部署形态）

| 组件 | 实测命令 |
|---|---|
| 后端 | `uvicorn fastapi_app.main:app --host 0.0.0.0 --port 5002 **--reload** --reload-dir fastapi_app` |
| 前端 | `node .../vite.js --host 0.0.0.0 --port 5173 --port 3000`（**Vite 开发服务器**，非静态产物） |
| 生产服务 | `erp-prod` / `erp-arq` / `erp-redis` / `erp-redis-broker` **全部 Stopped**（StartMode=Auto，NSSM 封装） |

**风险**：
- `--reload` 是开发特性：文件变更即重启，单进程无 `--workers`，无进程守护；
- Vite 开发服务器不适用于生产（无 gzip/缓存策略、内存占用高、无产物完整性）；
- 生产服务已定义但未启用 → 说明**从未按生产方式启动过**。

**动作**：用 `erp-prod` 服务方式启动（含 `--workers`），前端改为静态产物托管（nginx 或后端静态目录）。

### B5 — 已发生真实数据损坏（孤儿订单 19 条）

| 事实 | 实测值 |
|---|---|
| **孤儿订单**（订单指向的客户已不存在） | **19 条** |
| 涉及客户 | 「名创优品海外」10 条（08-01~08-07）、「名创优品」9 条（08-01~08-09） |
| 孤儿备货 / 孤儿出货 | 0 / 0 |
| 已产生出货的孤儿订单 | 0（影响面已收窄） |

**根因**：`customer_service.delete_customer` 的「客户有关联订单则拒绝删除」守卫因
`not Order.is_deleted` 求值为 Python 布尔而使 SQL 恒假（`WHERE false`），**守卫从未生效** →
删客户时未拦截，订单被留成孤儿。**该缺陷已于本会话修复**（详见 `deliverables/SQL条件恒假缺陷报告.md`）。

**动作**：
1. 决定修复策略：恢复这 2 个客户记录（推荐，保留业务连续性）或按规则清理孤儿订单；
2. 修复后重跑孤儿检查确认归零；
3. 同类检查扩展到 `stock_in` / `stock_out` / `packaging_record` 等以客户名做字符串引用的表。

## 七、评估方法与诚实边界

**本次实测取证**（非引用历史结论）：
- 直连 PostgreSQL 实测表规模、查询延迟、迁移版本、孤儿数据
- 扫描运行中进程命令行、端口绑定、Windows 服务状态
- 实跑 `mypy` / `pytest`（1312 项）/ `vue-tsc`
- 实测 HTTP 端点（`/api/docs`、`/api/openapi.json`、`/api/health`）
- 交叉验证 3 份历史评审（09-05 / 09-11 / 09-13）并复核其遗留项的**当前**状态

**未覆盖 / 无法验证**：
- **未做业务功能逐项验收**（无 UAT 依据，本次仅做技术就绪度评估）
- 未做压力/并发测试（无压测基线；当前数据量下性能充裕，但未验证峰值并发）
- 未审计前端交互与打印/导出等业务细节的正确性
- 未验证灾备（异地备份、断电恢复）能力

> **结论适用性**：本报告基于 `D:\erp_system` 本机现状。若生产部署在其他主机，需在该环境重跑本报告的关键取证项。
