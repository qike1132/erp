## 二、两处需要单独说明的关键发现

### 2.1 A1 的"包装中间件"方案会双重包装

原方案建议"新增 `core/response.py` **包装中间件**"。实测发现该方案在本项目**不可行**：

1. 本项目 **335 处端点**已通过 `response_model=` 声明响应契约（Pydantic 强类型校验 + 序列化）；
2. 中间件运行在 FastAPI 完成 `response_model` 序列化**之后**，再包裹会产生
   `{success, data: {success, ...}}` 双重包装；
3. `response_model` 按模型白名单过滤字段，中间件新增的键（如 `request_id`）
   在声明了 `response_model` 的端点上会被**静默丢弃** —— "加了但看不到"。

**`request_id` 的正确载体是响应头**，已由 `RequestIdMiddleware` 承担，不进响应体。

→ 改为**构造 helper**（`success_response()`），只做"构造收敛"，不动响应形状。

### 2.2 实测基线推翻了性能类优化的前提

详见 **`docs/performance-baseline.md`**。核心数据：

| 指标 | 实测 |
|---|---|
| 数据库总大小 | **43.4 MB** / 68 表 |
| `shared_buffers` | **3948 MB**（全库占 1.1%） |
| 最大表 | `audit_log` 45,241 行 |
| `order` 行数 | **3,722** |
| `product` 行数 | **118** |
| `order` 最深页 | **0.719 ms** |
| `product` COUNT(*) | **0.107 ms** |
| Redis GET hit | **0.120 ms** |

**结论**：数据全在内存，查询 0.1~0.7 ms。A2/A9/A10 三项性能优化**均无收益或负收益**。

## 三、A1 实施详情（本轮唯一落地的 P1 项）

### 3.1 新增文件

**`fastapi_app/core/response.py`**（新增，已纳入 mypy 门禁）

```python
def success_response(**fields: Any) -> dict[str, Any]:
    """构造标准成功响应体 {'success': True, **fields}。"""
    return {'success': True, **fields}
```

设计约束（已写入模块 docstring）：
- 明确**不采用中间件**（理由见 §2.1）
- 明确 `request_id` 走 Header 不走 body
- 明确与内联字面量 `{'success': True, **fields}` **逐字节等价** → 前端零改动

### 3.2 迁移范围（35 处 / 2 文件）

| 文件 | 迁移数 | 说明 |
|---|---|---|
| `api/v1/endpoints/purchase_center/order_routes.py` | **21** | 全项目最密集；含 11 处 `**result` 展开、多行 dict 2 处 |
| `api/v1/endpoints/customer_sampling.py` | **14** | 含 9 处 `'message': ..., **result` 合并形态 |

全局进度：**已迁移 35 处，剩余内联 163 处**（不含测试）。后续可按同一模式分批推进。

### 3.3 ★ 测试抓到一处真实回归隐患（本轮最有价值的发现）

首次迁移 `customer_sampling.py` 时，我把
`{'success': True, 'message': '创建成功', **result}` 写成了：

```python
success_response(message='创建成功', **result)   # ❌
```

单元测试立即失败：

```
TypeError: success_response() got multiple values for keyword argument 'message'
```

**根因**：Python 在**调用点**就拒绝重复关键字，任何函数签名都拦不住。
原内联字面量 `{'success': True, 'message': '创建成功', **result}` 是**静默让 `result` 覆盖**的 ——
一旦服务层返回体含 `message` 键，新写法会抛 `TypeError`，**线上表现为 500**。

**修正**：合并语义必须在调用侧完成：

```python
success_response(**{'message': '创建成功', **result})   # ✅ 与原文等价
```

已同步修正 9 处，并把该约束写入 helper docstring + 两条**回归护栏测试**
（`test_duplicate_key_is_rejected_at_call_site` / `test_duplicate_success_key_also_rejected`），
防止后续有人"简化"回危险写法。

> **这正是"先补测试再重构"的价值**：一个纯重构差点埋下 500 的雷，
> 而 1281 项存量测试**都拦不住它**（因为没人覆盖过这个组合）。

### 3.4 顺带修复

`customer_sampling.py` 的 `import functools` 位于模块 docstring **之前**，
导致第 2-8 行的文档字符串失效（只是无用字符串表达式，不是 docstring）。
已调整顺序，模块文档恢复生效。

## 七、经验教训

1. **"20 个端点"和"13 处 N+1"这类数字，必须连同行号一起验证。**
   原方案的 A2 数字是对的（确实 20 处），但**结论是错的** —— 数字对不等于问题存在。
2. **性能结论必须以数据规模为前置条件。** 讨论"深分页优化"之前，
   先问"表里有多少行"。43 MB 的库讨论 keyset 分页，等于给自行车装涡轮。
3. **二次结论（二手分析）不可直接执行。** P1 六项中 4 项是错的，全部错在
   "看代码形状就下结论"（看到 `lazy='select'` 就说 N+1，看到没装饰器就说没缓存）。
4. **纯重构也需要测试。** 本次一个"逐字节等价"的重构差点引入 500，
   靠的是一条自己写的护栏测试拦下来的 —— 存量 1281 项测试全都没覆盖到这个组合。
