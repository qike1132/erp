# Redis 缓存命中率诊断报告（实测）

> 日期：2026-09-14
> 目标：验证「缓存命中率低」假设（选项 C）
> 结论：**假设成立，但真凶与最初推测不同。命中率低是"指标失真"，不是"缓存失效"。**

---

## 一、实测数据

对运行中的 Redis 缓存实例（127.0.0.1:6379）直接执行 `INFO stats`：

| 指标 | 数值 |
|---|---|
| `keyspace_hits` | 671 |
| `keyspace_misses` | 26,566 |
| **命中率** | **2.46%** |
| 未命中/命中比 | **39.6 : 1** |
| `total_commands_processed` | 74,764 |
| `expired_keys` | 315 |
| `evicted_keys` | 0 |
| `DBSIZE` | **15** |

**表面结论**：缓存几乎完全失效。
**实际结论**：见下。

---

## 二、关键发现一：DBSIZE 只有 15 —— 业务缓存几乎没在写

15 个 key 逐个展开：

| key | TTL | 类型 |
|---|---|---|
| `token_blacklist:*` × 9 | 59.7万秒 ≈ 6.9 天 | 登出令牌黑名单 |
| `erp:active_customer_names` | 29s | 业务（短 TTL） |
| `erp:inventory:map` | 30s | 业务（短 TTL） |
| `erp:nav_sections` | 22s | 业务（短 TTL） |
| `erp:plan_fifo:2026-09` | 1529s | 业务 |
| `login_attempt:192.168.0.149` | 22s | 限流 |
| `order_batch:whitelist` | 31s | 业务 |

**观察**：`@cache_result` 生成的业务缓存 key（形如 `erp:DESKTOP-11111:orders:list:p1:pp50:...`）**一个都不存在**。

原因不是 bug，而是 **TTL 太短**：`orders:list` 的 `ttl=60 / local_ttl=15`，30–60 秒就过期，且 `evicted_keys=0` 说明不是被驱逐，是**自然过期**（`expired_keys=315`）。在低访问频率下，key 过期后无人再访问，自然不在库里。

---

## 三、关键发现二：真正的 miss 来源是 token 黑名单校验

### 归因链（已实验证实）

`fastapi_app/core/auth/blacklist.py:102`：

```python
return bool(await redis.exists(f"token_blacklist:{jti}"))
```

该函数 `is_token_revoked()` 被 `fastapi_app/core/deps.py:215` 调用——即**每一个已认证请求**都会执行一次 Redis `EXISTS`。

- 正常情况下 token **不在**黑名单 → Redis 返回 `0` → **计入 1 次 MISS**
- 只有登出过的 token 才会返回 `1` → HIT

### 实验证实 EXISTS 计入 miss

```
EXISTS 前 keyspace_misses = 26577
执行单次 EXISTS token_blacklist:__nonexistent_test__
EXISTS 后 keyspace_misses = 26578
差值 = 1  ✅ 证实
```

### 数量对账

- miss = 26,566 ≈ **已认证请求数**（每请求 1 次 EXISTS）
- 这段时间的业务缓存 key 只有 4 个、TTL 仅 30s，**几乎不可能产生大量 hit**

**结论：2.46% 的命中率是"结构性失真"** —— 分母被海量的、注定 miss 的黑名单探测撑大了。

---

## 四、关键发现三：这个指标不可观测，且已有指标是死代码

| 指标 | 定义位置 | 是否被调用 |
|---|---|---|
| `cache_operations_total`（含 `operation` 标签） | `core/metrics.py:147` | ❌ **0 次引用（死代码）** |
| `erp_perm_cache_hits_total` | `core/metrics.py:179` | ✅ 仅用于权限缓存 |
| `erp_perm_cache_misses_total` | `core/metrics.py:184` | ✅ 仅用于权限缓存 |

**核心问题**：`@cache_result` 这个**承载全部业务缓存**的装饰器，**没有任何命中率埋点**。

这导致的直接后果：
1. 你无法回答"缓存到底有没有生效"
2. Redis 的全局命中率会**误导**判断（如本次：2.46% 看起来缓存挂了，实则业务缓存只是 TTL 短 + 黑名单探测稀释）
3. 无法做容量规划与 TTL 调优

---

## 五、次要发现：两套 Redis 访问路径，key 前缀策略不一致

| 路径 | 使用方 | key 前缀行为 |
|---|---|---|
| `utils.redis_cache.py`（wrapper） | `@cache_result` | 自动加 `erp:{HOSTNAME}:` |
| `fastapi_app/core/redis_wrapper.py`（raw） | `blacklist.py` | **不加前缀**，直连 |

证据：
- `blacklist.py:63` → `redis.set(f"token_blacklist:{jti}", "1", ex=remaining)` 用的是 raw client
- 因此 Redis 中 `token_blacklist:*` **没有** `erp:DESKTOP-11111:` 前缀
- 而 `@cache_result` 的 key 有前缀

**风险评估**：当前**不构成功能性 bug**（各写各读，自洽）。但存在隐患：
- 同一台机器部署多个实例时，`HOSTNAME` 相同则前缀相同，可能互相读到对方的缓存
- 运维时 `KEYS erp:*` 会漏掉 `token_blacklist:*`，排查困难
- 切换部署方式（如 Docker）导致 `HOSTNAME` 变化时，**旧缓存全部失联**（冷启动）

## 六、结论与建议

### 结论

| 问题 | 判定 | 证据 |
|---|---|---|
| 业务缓存"完全失效" | ❌ 不成立 | 4 个业务 key 存在，TTL 正常 |
| 业务缓存 TTL 过短，命中率天然低 | ✅ **成立** | `orders:list` ttl=60s、多个 key TTL 22–31s |
| 全局命中率 2.46% 是失真指标 | ✅ **成立** | 分母被 26,566 次黑名单 EXISTS 撑大（已实验证实） |
| 缓存**不可观测**（无命中率埋点） | ✅ **成立（最关键）** | `cache_operations_total` 是死代码 |
| 前缀策略不一致 | ⚠️ 隐患 | 两套 client，前缀行为不同 |

### 建议（按优先级）

**P0 — 给 `@cache_result` 加命中率埋点**（把 `cache_operations_total` 死代码激活）

在 `core/cache.py` 装饰器的命中/未命中分支埋点，标签区分来源：

```
cache_operations_total{operation="l1_hit"}
cache_operations_total{operation="l2_hit"}
cache_operations_total{operation="miss"}
cache_operations_total{operation="stampede_wait"}
```

这样即可**精确回答"业务缓存命中率是多少"**，与 Redis 全局指标解耦。

**P1 — 复核关键接口的 TTL 是否合理**

TTL=60s 的列表缓存，在用户浏览间隔 >60s 的场景下命中率必然低。需按接口的实际访问特征定 TTL（如字典类数据可 300s+，列表类可用「写入时主动失效」替代短 TTL）。

**P2 — 统一 Redis 访问路径与 key 前缀**

建议让 `blacklist` 也走 wrapper，或统一约定前缀规则，避免 `HOSTNAME` 变化导致缓存全失联。

**P3 — 优化黑名单校验（可选，非瓶颈）**

当前设计正确但成本偏高：每个请求 1 次 Redis 往返（约 0.1–1ms）。若将来请求量上升，可改为：
- 批量/管道校验
- 用 Bloom filter 本地缓存"最近未撤销"的 jti（有极小误判率，但可接受）

**当前不必做**——26,566 次 EXISTS 在一个自用系统里不是性能问题。

---

## 七、方法论备注

本次诊断的价值在于**推翻了两个错误推断**：

1. 初判「`redis.set(timeout=N)` 未设置 TTL」 → **错**。wrapper 内部正确调用了 `setex(full_key, timeout, serialized)`。
2. 初判「key 前缀不一致导致失效失败」 → **错**。`set` 与 `delete_pattern` 都走 `_make_key`，自洽。

**教训**：读到不熟悉的封装层时，必须先读封装实现再下结论，不能凭对底层库（redis-py 的 `timeout` vs `ex`）的印象直接判断。
