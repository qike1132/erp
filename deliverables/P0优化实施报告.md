## 三、原方案的 3 处前提纠正

### 3.1 A7「移除 PrimeVue，688KB → 0」——前提错误

**原方案依据**：`vendor-primevue` 688KB，"PrimeVue 仅被 2 个组件使用"（`UiAutocomplete.vue:42`、`UiDateRangePicker.vue:22`）。

**实测推翻**：

1. **使用面不是 2 个，是 4 个**。`UiDataTable.vue:50`（`import { DataTable, Column } from 'primevue'`）与 `UiDrawer.vue:30`（`import { Drawer } from 'primevue'`）同样依赖 PrimeVue。`UiDataTable` 是"统一 13 个视图"的核心表格组件，重写它属于 P2 级工程，不是速赢。

2. **`vendor-primevue` 根本不在首屏加载路径上**。`dist/index.html` 仅 preload 4 个 vendor chunk：

   | index.html 实际声明加载 | raw | gzip |
   |---|---|---|
   | `index-*.js`（入口） | 51,789 B | 18,738 B |
   | `vendor-vue` | 115,959 B | 45,055 B |
   | `vendor-query` | 38,581 B | 11,513 B |
   | `vendor-fontawesome` | 151,895 B | 45,489 B |
   | `vendor-axios` | 45,425 B | 17,588 B |
   | **首屏合计** | **≈403.6 KB** | **≈138.4 KB** |

   `vendor-primevue` 与 `index-8985Y_zC.js`(444K) 都是由入口**动态 import** 的。**因此原报告"首屏 JS 总量 4.1M → 3.4M，-15%~-17%"是错的**——4.1M 是 `dist` 总体积，不是首屏体积。由此推导的"首屏 LCP -20%~-35%"失去依据。

3. **barrel 导入本就被正确 tree-shake**。按 PrimeVue 官方推荐改为深导入（`primevue/datatable`、`primevue/column`、`primevue/drawer`）后重建：

   | | 字节数 |
   |---|---|
   | 改动前 `vendor-primevue-_eWMvzqY.js` | 688,563 |
   | 改动后 `vendor-primevue-SadobcXg.js` | **688,555** |

   **仅差 8 字节。** 676K 的真实构成是 `DataTable` 的内部静态依赖——`primevue/datatable/DataTable.vue:353-354` 静态 import 了 `Paginator`(214KB 源码) 与 `VirtualScroller`(226KB 源码)，后者**本项目明确不使用**（`useTableVirtualScroll.ts` 自研了虚拟滚动）却无法摘除。

**处置**：保留深导入（PrimeVue 官方推荐写法，显式声明依赖），但**已把注释修正为准确描述**，避免留下一个已被证伪的技术理由误导后人。**A7 从 P0 降级**：真正的收益需要重写 `UiDataTable`，属 P2。

### 3.2 A3「6 处手写事务全部收敛」——仅 1 处成立

逐处核实结果：

| 位置 | 判定 | 理由 |
|---|---|---|
| `customer.py:294` | ✅ **已收敛** | docstring 理由**已过时**：称"db_transaction 会把 IntegrityError 转为 HTTP 500"，但 `error_map` 现已支持 400 映射（`outsource.py:102`、`purchase_plan.py:146` 已在用） |
| `supplier.py:91,279` | ❌ 保持原样 | `_run_supplier_write` 是**一个**已收敛的 helper（4 个端点复用），带"提交前 + 提交后各失效一次缓存"的并发竞态防护；转 db_transaction 会丢失该语义 |
| `order_routes.py:136` | ❌ 保持原样 | IntegrityError 后需**回滚并回查**返回**幂等成功响应**；`error_map` 只能映射为 HTTPException，无法表达"继续做工作" |
| `backup/restore.py:177,264` | ❌ 保持原样 | 处于恢复编排的锁获取/释放（`finally: release_restore_lock()`）语义中，改造成本高、收益低 |

**处置**：只改 `customer.py`，并清理随之未使用的 `SQLAlchemyError` 导入。

```python
# 改动前：手写 try/except/commit（11 行）
try:
    await customer_service.delete_customer(db, customer_id)
    await db.commit()
except IntegrityError:
    await db.rollback()
    logger.info(...)
    raise HTTPException(status_code=400, detail='该客户已有相关单据，无法删除！建议禁用该客户。') from None
except SQLAlchemyError as e:
    await db.rollback()
    logger.exception(...)
    raise HTTPException(status_code=500, detail='数据库操作失败') from e

# 改动后：与 outsource.py / purchase_plan.py 一致的声明式写法
async with db_transaction(db, error_map={IntegrityError: _customer_in_use_error}):
    await customer_service.delete_customer(db, customer_id)
```

> 响应结构保持不变（`detail` 仍为纯字符串）。注：本项目端点层有 **133 处** `HTTPException(status_code=..., detail='字符串')`，而 `http_error()`（统一错误码）在 `api/` 下用量为 **0** —— 即原报告所称"错误响应已统一"仅对 `make_error_response` 本身成立，端点层并未采用。这属于 A1（成功响应统一）应一并处理的范畴。

## 四、A13 的真实问题：CI 一直是红的

原方案说"pytest.ini 无 fail_under；mypy 仅 21 文件；Husky 未跑 lint/type-check"。核查 `.github/workflows/ci-cd.yml` 后发现**实际状况比描述更严重**：

| CI 步骤 | 位置 | 改动前状态 |
|---|---|---|
| `python -m mypy --config-file mypy.ini` | `ci-cd.yml:146` | 🔴 **8 个错误 → 失败** |
| `npm run build`（= `vue-tsc -b && vite build`） | `ci-cd.yml:179` | 🔴 **2 个类型错误 → 失败** |
| `npm run lint` | `ci-cd.yml:176` | 已有 |
| coverage 阈值 | `ci-cd.yml:35` `COVERAGE_MIN: "40"` + `:117-119` 脚本校验 | **已存在**（原报告"无覆盖率门禁"不准确，只是门禁在 CI 而非 pytest.ini） |

**即：本次改动把 CI 的 `lint` 与 `frontend` 两个 job 从红转绿。**

### 4.1 修复的 8 个存量 mypy 错误

| 文件 | 错误数 | 根因 | 修法 |
|---|---|---|---|
| `core/purchase_cache.py` | 6 | `except (RuntimeError, *INFRA_EXCEPTIONS)` —— mypy 无法推导星号解包后的 except 元组类型 | 预展开为显式元组 `_LOCAL_INFRA_EXCEPTIONS`（语义等价） |
| `core/telemetry.py` | 1 | `trace.get_tracer_provider().add_span_processor(...)` —— 该方法属 SDK 层，API 层基类无此方法 | 保留 SDK Provider 实例引用后调用 |
| `shared/report_data_service.py` | 1 | `Order.order_stockouts` 由 `stock_out.py:38` 的 `backref` 运行时注入，mypy 不可见 | 作用域化 `# type: ignore[attr-defined]` + 说明（改 `back_populates` 会引入模型层循环导入，收益不成比例） |

同时修复 `exception_handler.py:28` 的 `INFRA_EXCEPTIONS` 类型标注（该处修复使 `except INFRA_EXCEPTIONS` 的普通形式一并转绿）。

### 4.2 mypy 覆盖扩面：21 → 100 个文件

`fastapi_app/services/` 172 个文件中，**78 个仍有类型错误（合计 416 个 error）**。因此**不能一次性扩至全 services**（会把门禁立刻打红），改为纳入其中**已零错误的 79 个文件**，并在 `mypy.ini` 写入渐进式收紧策略与复核命令，供后续逐个修复后继续纳入。

### 4.3 修复的 2 个前端类型错误 + 1 个真实功能缺陷

`src/views/pattern-room/PatternRoomView.vue`：

| 问题 | 性质 |
|---|---|
| `<CustomerGroupList>` 未传 `statusFilter`（子组件声明为必填） | 真实缺陷：子组件搜索栏的状态筛选恒为 `undefined` |
| `<ProjectDetailPanel>` 未传 `editingPartId` / `editForm`（均为必填） | **真实功能失效**：内联编辑状态由 `usePatternRoomPartActions` → `usePartInlineEdit` 提供，但视图从未解构下发，导致 `PartsVersionRowV2` 的内联编辑（`v-if="editingPartId === part.id"`）**永远不显示** |

该缺陷 `eslint` 与 `vitest` 都拦不住，只有 `vue-tsc` 能发现——**这正是保留 type-check 门禁的直接价值**。

### 4.4 接入从未被调用的 lint-staged

`package.json` 中早已配置 `lint-staged`（`eslint --fix` + `prettier --write`），但 `.husky/pre-commit` 只跑 `npm test`，**该配置从未被执行过**。现已接入，并补上 `type-check`：

```sh
npx --no-install lint-staged   # 暂存文件，约 1-2s
npm run type-check             # 约 18s
npm test                       # 约 18s
```

## 七、经验教训（供后续对标复用）

1. **"某个依赖只被 N 处使用"必须自己 grep 验证**，不能采信二手结论——本次原报告把 4 处漏成 2 处，直接导致方案方向错误。
2. **"体积大"≠"影响首屏"**。判断优化价值必须看 `index.html` 的实际 preload 列表，而不是 `dist` 总大小。
3. **改配置/门禁前先跑一次**。原报告基于"配置缺失"的推断，实测发现 CI 里门禁早已存在，而真正的问题是**门禁是红的**——一个没人发现的事实。
4. **类型检查门禁的价值需要具体案例证明**。本次它拦住了一个 eslint/vitest 都发现不了的功能失效（内联编辑不可用），这比"提升代码质量"的抽象说辞更有说服力。
