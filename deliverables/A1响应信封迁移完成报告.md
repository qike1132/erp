## 一、范围决策：为什么只做端点层，不做服务层

全项目内联 `success` 共 **159 处**（不含测试），分布：

| 层 | 处数 | 处理 |
|---|---|---|
| `api/v1/endpoints/**` | **79** | ✅ **本轮全部迁移** |
| `services/**` | 71 | ❌ **刻意不迁移** |
| `core` / `shared` / `shared_models` | 9 | ❌ 不迁移 |

**服务层不能一刀切** —— 抽样甄别发现三种语义混在一起：

| 文件 | 形态 | 语义 | 可否迁移 |
|---|---|---|---|
| `material_registration/_queries.py` | `return {'success': True, 'registrations': [...]}` | **HTTP 响应信封** | 可 |
| `case/commands.py` | `return {'success': True, 'stockin_no': ...}` | **HTTP 响应信封** | 可 |
| `backup/incremental.py` | `{'success': True, 'filename': ..., 'format': 'incremental'}` | **内部结果字典**（备份编排消费，非 HTTP） | **不可** |
| `stock_in_service.py` | 外层是信封；内层 `results[i] = {'success': False, 'error': ...}` | **单项部分结果** | **不可** |

后两者若被迁移，会把"业务结果标志"错当成"响应信封"包装，
`success_response()` 的语义是"构造 HTTP 成功响应"，用于内部结果字典是错的。

> **端点层的 79 处经逐个确认全是 HTTP 响应信封**（`backup/validation.py` 里的
> `'valid': False` 是载荷字段，不是 `success: False`）。

## 二、Codemod 方案与正确性依据

### 2.1 关键洞察：只需替换前缀

```
{'success': True, <rest>}   ≡   success_response(**{<rest>})
```

因为 `success_response(**fields)` 的实现就是 `{'success': True, **fields}`。
因此转换**完全不必解析其余键值** —— 这消除了键名转换、嵌套 dict、f-string、
跨行表达式等全部风险。

### 2.2 输出形态

| 场景 | 输出 | 例 |
|---|---|---|
| 单行 + 键均为字符串字面量 + 无 `**` | `success_response(k=v, ...)`（可读） | `success_response(products=products)` |
| 多行 或 含 `**` 展开 | `success_response(**{<rest>})`（保底，恒等价） | `success_response(**{**result})` |

### 2.3 实现要点

- 用 `ast` 精确定位目标 dict（首键为 `success`、值为 `True`）
- **去嵌套**：若一个目标 dict 的跨度包含另一个，只处理最外层
- 替换**从后往前**执行，避免偏移错乱
- 按模块序插入 import（只考虑**模块级**一手 import）

## 三、★ 过程中发现并修复的两个 codemod 缺陷

### 3.1 import 被插进函数体 → `IndentationError`

**现象**：`auth.py` 编译失败 `IndentationError: unexpected indent (line 109)`

**根因**：初版 `ensure_import` 按**文本行**扫描 `from fastapi_app.` 前缀，
把 `auth.py` 里**函数内的局部 import**（`from fastapi_app.services import user_service`）
误判为模块级，于是把 import 插进了函数体中间。

**修复**：改用 `ast.parse(src).body` 只取**模块级** import，再按模块名排序定位插入点。

> 值得记录：**只有 1 个文件触发**（19 个里唯一含函数内一手 import 的），
> 但如果没有 `py_compile` 全量校验，这个错误会以"某个接口 500"的形式在运行时才暴露。

### 3.2 外观瑕疵 `{ **result}` 多余空格

**现象**：单行展开场景产出 `success_response(**{ **result})`（语法正确但难看）

**根因**：`_strip_first_key` 只做 `rstrip()`，保留了 `, ` 之后的空格。

**修复**：单行场景改用 `strip()`；多行场景保留 `rstrip()`（避免破坏多行缩进）。
已清理已生成的 7 文件 / 16 处。

## 六、经验教训

1. **批量重构必须有"逐单元计数核对"。** codemod 跑了 79 处，但真正让我确信
   没漏没错的不是"测试通过"，而是**逐文件对比原内联数与现调用数**（0 不一致）。
2. **codemod 的两个 bug 都是"语法能过、语义悄悄错"的类型** ——
   import 插错位置靠 `py_compile` 拦下，空格瑕疵靠 diff 审查发现。
   → **codemod 必须配：全量语法检查 + diff 抽样审查 + 全量回归。**
3. **"同名写法"不等于"同一语义"。** 服务层 71 处 `'success': True` 里混着
   内部结果字典和单项部分结果，一刀切会静默破坏语义。
   → 重构的边界应由**语义**划定，而不是由**文本模式**划定。
4. **codemod 本身也值得沉淀为脚本。** 放进 `scripts/` 而非临时文件，
   后续服务层迁移可直接复用（含已修复的两个缺陷）。
