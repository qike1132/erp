customer-order 前端交互审查报告

目标页面：http://192.168.0.95:3000/customer-order　·　审查范围：加载与首屏、表单反馈、按钮响应态、错误与异常、响应式、操作路径、可访问性

审查时间2026-09-18 14:56–15:40（GMT+8）
取证方式Playwright + 系统 Edge（msedge，headless）·9 种视口 · 原生 DOM 实测
站点形态当前由 vite dev server 承载（非生产托管）
登录态本地签发 ES256 JWT，注入 access_token Cookie（uid=23 / admin）
只读声明全程未提交订单、未保存、未真删；删除流程走到确认框后取消
问题计数severe 6 medium 11 mild 5

1 · 一句话结论

页面骨架、视觉分层、空态与弹窗礼仪做得相当好（弹窗焦点陷阱、Escape、焦点归还、滚动锁定、prefers-reduced-motion 兜底、9 种视口零横向溢出全部实测通过）。真正的问题不在"长得怎么样"，而集中在三条根因：

  1. 异常被渲染成"没有数据"。记录查询「订单」接口实测返回 HTTP 500，界面给用户的是「暂无订单记录」——没有错误条、没有 toast、没有重试入口。同一模式在本页另有 3 处静默 catch。用户永远无法区分"确实没有"和"加载失败"。
  2. 校验反馈缺位，关键按钮变成静默死路。「新增订单」在条件不足时只是变灰——没有必填提示、没有字段级错误、没有原因说明，而且点击连一个 toast 都不产生（实测 toast 数 0→0）。因为校验文案写在按钮的 click 里，而按钮已被 disabled，那段代码永远不可达。
  3. 可访问名 / 语义 / 键盘可达性被统一忽略。整个 Excel 批量导入区键盘完全不可达（无 tabindex/role，文件 input display:none 且不在 label 内）；UiButton 把 aria-label="操作按钮" 硬编码到每个按钮上，导致删除确认框里的「取消」与「确认」对读屏器完全同名；5 个必填星号没有任何程序化语义；数量输入框连可访问名都没有。

另有一项必须先讲清的前提：当前 3000 端口跑的是 dev 构建（HTML 命中 /@vite/client + /src/main.ts，首屏 247 个 script 请求 / 9.84 MB）。所以本次测到的 FCP 224ms 等数字不代表用户代价；生产侧改用产物静态核算（首屏关键 JS 135 KB gzip），结论见 §7。

4 · 严重问题详述

S1 · 记录查询「订单」接口 500，被渲染成「暂无订单记录」severe

现象。切到「记录查询」页签，订单列表显示空态「暂无订单记录」，看起来像是业务上没有订单。

成因。useOrderList.ts:70-88 的 fetchOrders 没有 try/catch；请求失败时 orderRecords 保持 []，finally 又把 loading 清掉，于是 OrderRecordTable.vue:16-21 的 #empty 槽正好被渲染出来。错误信息只落在控制台，页面上一层兜底都没有。

实测（浏览器 response 事件 + 直连复验，两者一致）
GET /api/v1/orders/list?page=1&per_page=20 → 500
{"success":false,"detail":"获取订单列表失败: greenlet_spawn has not been called; can't call await_only() here. Was IO attempted in an unexpected place?"}
对照：GET /api/v1/stock/in/list → 200（4 条数据，表格正常渲染）→ 说明是订单链路的契约/懒加载缺陷，不是权限、不是网络
用户可见：cellText = "暂无订单记录"　anyErrorBanner=false　anyToast=false　retryButton=false
控制台：[Unhandled Rejection] AxiosError: Request failed with status code 500 + pageerror

影响。「记录查询」的订单视图对这个用户完全不可用，而且以最糟的方式失败——它主动告诉用户"没有订单"。业务侧会据此得出错误结论（例如误判订单未录入）。这是本次审查中优先级最高的一项：后端修契约 + 前端修兜底，两边都要改。

改法。前端最小改动：

// useOrderList.ts · fetchOrders
async function fetchOrders() {
  const seq = ++requestSeq
  const isInitial = orderRecords.value.length === 0
  if (isInitial) isLoadingRecords.value = true
  else isFetchingRecords.value = true
  errorMessage.value = ''                        // ← 新增：错误态
  try {
    if (recordType.value === 'stockin') await fetchStockins(seq)
    else await fetchOrderRecords(seq)
  } catch (e) {
    if (seq === requestSeq) {
      errorMessage.value = getErrorMessage(e, '订单列表加载失败')   // ← 不再吞掉
      if (isInitial) orderRecords.value = []      // 只在无数据时清空，避免闪掉已有列表
    }
  } finally {
    if (seq === requestSeq) { isLoadingRecords.value = false; isFetchingRecords.value = false }
  }
}
// OrderRecordTable.vue · 空态槽加错误分支
<template #empty>
  <div v-if="errorMessage" class="co-state-placeholder co-state-error">
    <p>{{ errorMessage }}</p>
    <UiButton variant="outline" @click="fetchOrders()">重试</UiButton>   // ← 必须给出口
  </div>
  <div v-else class="co-state-placeholder co-state-empty">…暂无记录…</div>
</template>

后端侧：500 的 greenlet_spawn has not been called 是 SQLAlchemy 异步会话里发生同步惰性加载（典型是序列化时关系属性未预加载）。修法是补 selectinload/joinedload 或在响应模型中避免触发惰性关系。此项属于后端范畴，报告只做记录，不在此处展开。

S2 · Excel 批量导入整条链路键盘不可达severe

现象。用键盘无法触达"拖拽文件到标题栏 / 模板 / 导入"这条导入链路。

成因。OrderExcelImport.vue:3-10 的投放区是一个带 @click 的 <div>：没有 tabindex、没有 role、没有键盘事件，所以它进不了 Tab 序列。文件 input（:22-28）是 style="display:none"，既不在 Tab 序列里，也没有嵌在 label 内；同位那个 <label>（:11-15）没有 for，点它本身什么都不会发生（真正打开文件框的是父 div 的 click）。

实测
投放区：{tag:"div", tabindex:null, role:null, ariaLabel:null}
文件 input：{display:"none", focusable:false, inLabel:false, id:null, labelled:false}
搜索"模板"按钮的 Tab 序列路径可证：Tab 能到「模板」按钮，但永远到不了投放区与文件选择

影响。只用键盘的岗位（内网 ERP 很常见：纯键盘批量录入）完全无法使用批量导入，只能退回逐条手工录入——而这正是导入功能要解决的场景。同时它也让"导入"这条路径在自动化可访问性扫描里必然报错。

改法。

// OrderExcelImport.vue · 把投放区变成真正的 button 语义 + 把 input 挂进 label
<div class="co-section-header co-droppable"
     role="button" tabindex="0"
     :aria-label="`批量导入：${excelFile ? excelFile.name : '未选择文件'}，支持 .xlsx / .xls`"
     @keydown.enter.prevent="excelInputRef?.click()"
     @keydown.space.prevent="excelInputRef?.click()"
     @click="excelInputRef?.click()" …>
  <!-- 让 label 真正关联到 input，而不是靠父 div 的 click 兜着 -->
  <label class="co-droppable-label" for="co-excel-input">…</label>
  …
  <input id="co-excel-input" ref="excelInputRef" type="file" accept=".xlsx,.xls" class="sr-only" />
</div>

注意 class="sr-only" 而非 style="display:none"：display:none 的元素连焦点都拿不到，要用视觉隐藏。@dragleave 在子元素间移动时也会触发（高亮闪烁），建议改成计数器或判断 relatedTarget 是否仍在容器内。

S3 · 「新增订单」禁用态零反馈，校验文案是死代码severe

现象。填了客户、日期、数量却还没选产品时，主按钮「新增订单」是灰的。点它没有任何反应——没有提示、没有抖动、没有说明缺哪一项。

成因是一条"自我否定"的链路。CustomerOrderView.vue:221-229 写了三段很贴心的校验文案（「请从下拉列表中选择产品」/「请填写日期、客户和产品」），但它们位于 addStaged() 内部；而 OrderInputPanel.vue:105 的按钮是 :disabled="!canAdd" —— 条件不足时按钮就被禁用，click 事件根本不会派发，于是那三句文案永远执行不到。

实测
按钮态：disabled=true　aria-disabled=null　title=null　cursor=pointer　opacity=0.5
点击"新增订单"：toast 容器子节点数 0 → 0（零反馈）
对照：品牌色按钮的禁用态在视觉上只是变淡，光标却是手型（cursor-not-allowed 未生效），进一步暗示"可以点"

影响。这是本页最主要的一种挫败感来源：用户不知道卡在哪、只能瞎试。对不熟悉"必须先点下拉项、打字不算"这个隐藏规则的新人尤其致命。

改法。把"为什么不能提交"从按钮内部搬到字段上，并允许点击获得解释：

// 方案 A（推荐）：按钮不再 disabled，改为可点 + 明确报错
<UiButton variant="primary"
          :aria-disabled="!canAdd"          // 语义上仍提示不可提交
          :class="{ 'is-blocked': !canAdd }"  // 视觉上用弱化样式，但保留 pointer
          @click="emit('add-staged')">          // 让 addStaged 的校验文案真正可达
  {{ isOrder ? '新增订单' : '新增备货' }}
</UiButton>

// 方案 B：保持 disabled，但把原因写到字段级 + 顶部提示
// canAdd 拆成 missingFields 计算属性，逐个字段渲染 .co-field-error
<div v-if="missingFields.length" class="co-form-hint" role="status">
  还差：{{ missingFields.join('、') }}
</div>

顺带修 cursor：UiButton.vue:53 的 cursor-not-allowed 与基础类的 cursor-pointer 同 specificity，实测 computed cursor = pointer，需要把禁用分支的选择器提权（如 !cursor-not-allowed 或改写基础类）。

S4 · 必填语义只存在于视觉层severe

现象。5 个必填项用红色 * 标注，但这套信息只给眼睛看。

实测
.co-required 数量 = 5　但　aria-required = 0　required = 0　label[for] = 0（label 总数 8）
8 个 label 全部未关联控件，列表：订单类型* / 订单时间* / 客户名称* / 产品名称* / 订单数量* / 抵扣备货数量 / 备注 / 拖拽文件…
数量输入框：{aria:null, placeholder:null, id:null, labelled:false} → 唯一的标识是相邻的视觉文本，读屏器读不出来

成因。OrderInputPanel.vue 里所有 <label class="co-label">（第 11、20、36、44、55、71、85 行）既没有 for，控件也没有 id；数量框（第 72 行）只有 name="quantity"，没有 aria-label/aria-labelledby。

影响。读屏器用户听到的是一串没有名字的编辑框，无法知道哪个是数量、哪些是必填；表单填写成本成倍上升。同时这也让自动化表单校验（E2E）失去了稳定的选择器锚点。

改法。最小侵入式：给控件加 id、给 label 加 for，必填项统一加 aria-required="true"。

<label class="co-label" for="co-order-type">订单类型 <span class="co-required" aria-hidden="true">*</span></label>
<UiSelect id="co-order-type" aria-required="true" … />

<label class="co-label" for="co-quantity">订单数量 <span class="co-required" aria-hidden="true">*</span></label>
<input id="co-quantity" aria-required="true" v-model.number="form.quantity" type="number" … />

星号本身加 aria-hidden 是必要的：否则读屏器会把"星号"读进字段名。

S5 · 新增一条后焦点被弹到 <body>severe

现象。用键盘提交一条后，焦点丢失——下一次按 Tab 会从文档开头（框架层）重新开始。

成因。点击「新增订单」后 resetFormAfterAdd()（useOrderForm.ts:153-163）清空产品与数量，canAdd 立刻变 false，按钮渲染为 disabled；而被禁用的元素无法保持焦点，浏览器把焦点回退到 <body>。

实测
新增后：cards=1（数据确实进去了）　同时　addDisabled=true　且　focusNow="body"
回到表单需要重走 16 个框架层 Tab 位（§L3）

影响。本页的核心操作是"连续录入多条然后批量提交"。焦点被弹回页首意味着每条录入要多按 17 次 Tab；一次填 20 条就是 340 次多余按键。这是"操作流畅度"维度的头号问题。

改法。录入后把焦点显式交还给"下一个该填的字段"，而不是让浏览器随手丢掉：

// CustomerOrderView.vue · addStaged 末尾
resetFormAfterAdd()
// 焦点送到产品输入框（连续录入的下一个起点），并保持按钮不被禁用
await nextTick()
document.getElementById('co-product-search')?.focus()

// 配套：把"重置后按钮变灰"这一步去掉（见 S3 方案 A），
// 否则下一次点击仍会因为按钮 disabled 而再次丢失焦点。

完整修法需要 S3 一起处理：只要按钮仍在"提交后被禁用"，焦点就会反复丢失。两条应合并为一个改动单元。

S6 · UiButton 硬编码 aria-label="操作按钮"severe

现象。全站每一个 UiButton 的可访问名都是同一个字符串「操作按钮」。

成因。components/ui/UiButton.vue:2：

<button :class="buttonClasses" :disabled="disabled" :type="htmlType" aria-label="操作按钮">

按可访问名计算规则，aria-label 的优先级高于元素内的文本，所以按钮里写的中文全部被这个常量覆盖掉了。

实测（本页命中的按钮，可访问名一律为 操作按钮）
「新增订单」→ aria-label="操作按钮"　「筛选」→ "操作按钮"（且 aria-expanded=null，展开状态也不播报）
「提交订单 (1)」→ "操作按钮"　国家「+」按钮（仅图标，60×36）→ "操作按钮"
删除确认框：「取消」与「确认」两个按钮同为 "操作按钮"

影响。对读屏器用户来说，页面上的按钮没有任何信息量；而在删除确认框里，取消和确认无法区分——这是一个不可恢复操作的错误率放大器（WCAG 4.1.2 Name, Role, Value 失败）。由于这是共享组件，影响面是全部 13 个使用 UiButton 的视图。

改法。删掉这一行即可，让按钮文本自然成为可访问名；仅图标按钮由调用方按需传 aria-label：

<button :class="buttonClasses" :disabled="disabled" :type="htmlType"
        v-bind="iconOnly ? { 'aria-label': ariaLabel } : {}">
  <slot />
</button>

// 删除确认框（UiConfirmDialog.vue）：给两个按钮显式命名
<UiButton variant="outline" aria-label="取消删除" @click="…">取消</UiButton>
<UiButton variant="danger"  aria-label="确认删除" @click="…">确认</UiButton>

这条是"一行删除换全站可访问性"的高性价比修复，建议排在 P0。

5 · 其余问题与改法

M1 · 「模板」按钮的 mustache 字符串泄漏到可访问名

OrderExcelImport.vue:17 写的是 aria-label="模板 {{ importing ? '导入中…' : '导入' }}"。Vue 的模板插值只在文本节点生效，不支持属性值内插值——所以这串字面量原样进了 DOM（实测 Tab 到该按钮，可访问名为 模板 {{ importing ? '导入中…' : '导入' }}）。改为 :aria-label="importing ? '正在导入模板' : '下载导入模板'"，并顺手纠正语义：这个按钮是下载模板，不是导入。

M2 · 「抵扣备货」误报「暂无可用备货」

// useOrderForm.ts:110-114 — 前置条件不全时提前返回，availableStock 停留在 0
async function fetchAvailableStock() {
  if (!form.productId || !form.customer) { availableStock.value = 0; return }
  …
}
// OrderDeductControl.vue:29 — 于是模板把"没检查"渲染成了"没有库存"
<small v-else …>暂无可用备货</small>

实测：未选客户/产品时点开抵扣，infoText = "暂无可用备货"。这是对用户说了假话——比"没反应"更糟。

改法。给 fetchAvailableStock 增加三态（idle / loading / ready），并用不同文案区分：idle → "请先选择客户与产品"；loading → 骨架/spinner；ready 且 0 → "该客户暂无可用备货"。同时给 handleDeductPreview 加 pending 禁用（防连点发两次请求），给开关加 aria-pressed。

M3 · 数量越界静默禁用

输入 99999999 后 rangeOverflow=true / valid=false，但边框仍是正常焦点蓝、aria-invalid=null，唯一变化是提交按钮变灰。修法：input:user-invalid（或监听 validity.rangeOverflow）时套红色边框 + 下方文案「数量不能超过 9,999,999」，并加 aria-invalid + aria-describedby 指到该文案。

M4 · 三处切换器缺 tab 语义

顶部「录入 / 记录查询」、记录类型「订单 / 备货」、表单类型「订单 / 备货」都是"用颜色表示当前项"的按钮组。实测三者 role=null、aria-selected=null、aria-pressed=null，页面 [role=tab] 计数为 0。修法二选一：真做成 Tabs（role=tablist/tab + aria-selected + 左右方向键切换），或保守地给按钮组加 role=group + 当前项 aria-pressed="true"。

M5 · UiSelect 聚焦即展开 + 额外 Tab 位

UiSelect.vue:5-6 同时开了 open-on-click 与 open-on-focus。实测 Tab 一落到两个下拉，panelOpen 立即为 true——面板会盖住下面的字段，键盘用户必须按 Escape 才能继续；顺带每个下拉还多出一个 15×24 的 trigger 焦点位（可访问名与下拉本体重复，实测 "选择选项" ×2）。修法：去掉 open-on-focus（保留 open-on-click），并把 trigger 设为 tabindex="-1"（它只是鼠标用的装饰件，键盘用 Alt+↓/Enter 即可）。

M6 · 日期字段占用 2 个 Tab 位，其中一位无焦点环

DOM 里只有 1 个 .date-input（实测 dateInputCount=1），但连续两次 Tab 的 document.activeElement 都指向它，第 2 次 outline: none 3px（无焦点环）。截图里该字段内可见两个日历图标：一个是自绘的 .date-icon 按钮，另一个是 Chromium 原生 picker indicator——UiDatePicker.vue:79-80 的 -webkit-appearance:none 在 Edge 这版内核里没把它藏掉，而它恰好是可聚焦的。合计一个逻辑字段吃掉 3 个 Tab 位（input ×2 + icon）。修法：::-webkit-calendar-picker-indicator{ display:none } 明确隐藏，.date-icon 提到 width/height: 32px 的命中区，并让它成为唯一的"打开选择器"入口。

M7 · 错误 toast 2.5 秒消失且不可关闭

useToast.ts:24-28 的全局默认是 duration: 2500, closable: false，本页所有 showToast 调用都未覆写。于是「订单创建失败（0/3）：实际原因…」在 2.5 秒后消失，既不能手动关也不能复看，用户来不及读完原因。改法：错误级 toast 默认 duration: 0（常驻）或 ≥8000ms 且 closable: true；成功级保持短时。顺带修 useToast.ts:96 与 :143 的礼貌级冲突——容器 aria-live="polite" 而每个 toast 又 role="alert"（assertive），建议二者取其一。

M8 · 暂存区增删没有任何播报

新增一条后实测 cards=1 而 toast=null，列表容器 aria-live=null，全页 live region 只有 toast 容器 1 个。对键盘/读屏用户来说，点击「新增订单」后屏幕上的唯一反馈发生在视野之外（右栏列表）。修法：给暂存列表外层加 aria-live="polite"，并在计数徽章上给 role="status"（"共 1 个"），或至少补一句成功 toast（"已加入暂存：产品 × 12"）。

M9 · ≤768px 双列表单不折行

外层网格在 1024px 折为单列（CustomerOrderView.vue:301-305），筛选行在 768px 折行（OrderRecordFilter.vue:168-171），但表单内部的 .co-form-row 从未折行（OrderInputPanel.vue:206-211）。实测 390px 视口下两列各 139px，客户下拉仅剩约 83px 文本空间。修法：给 .co-form-row 加 @media (max-width:768px){ grid-template-columns:1fr }；若判定平板/手机应由 /m/customer-order 承载，则在 768px 以下直接路由重定向，避免两套 UI 同时可维护。

M10 · 三处 catch 把失败说成"空"

// useOrderForm.ts:28-30　产品搜索失败 → 面板显示"无匹配结果"（实测）
catch { return [] }
// useOrderForm.ts:119-121　可用备货失败 → 0（再叠加 M2 就是"暂无可用备货"）
catch { availableStock.value = 0 }
// UiAutocomplete.vue:165-170　联想失败 → 空列表
.catch(() => { internalSuggestions.value = []; loading.value = false })

三处与 S1 是同一个根因家族。建议统一约定：请求失败必须产生一个可区分的状态（错误态 / 重试），不得降级为"空数据"。至少应把失败向上抛或写入一个 error ref，由调用方决定是否提示。

M11 · 表格语义与可读性

实测：表头 fontSize 12px < 表体 14px（层级倒置）；9 个 th 全部无 scope、无 aria-sort；表体容器 scrollWidth 1822px 而 thead 为 position: static——横向滚动时列头会滚走，长行数据失去列对齐参考。修法：表头字号提到 13px 并加深字重/颜色；给列头补 scope="col"；可排序列补 aria-sort；给表头加 position: sticky; top: 0 + 背景色。

L1–L5 · 低优先项

  • L1 点击目标：34 个可点元素中 7 个 <32px。最小者 .date-icon 18×14；UiSelect 的 trigger 15×24；模板/导入 40×26；记录类型切换 h=27。建议统一到 ≥32px（图标按钮 36px 已是页面里更合理的档位，向它看齐即可）。
  • L2 hover 位移：.co-staged-card:hover、.co-btn-icon:hover、.co-tab-btn:hover、.co-type-btn:hover 都用 translateY(-1px)。在可滚动的密集列表里，鼠标移动会造成行位抖动，破坏扫读。建议改为背景/边框/阴影变化。（正面：app.css:660-667 已有全局 prefers-reduced-motion 兜底，实测生效——这条只是默认动效本身偏多：全页 94/344 个元素带 transition。）
  • L3 入口路径：首个内容 Tab 位是整页第 17 位。已有 skip-link（href="#main-content"，目标存在）作为兜底，实测可用；但配合 S5 的焦点丢失，问题会被放大。建议把 #main-content 设为可聚焦（tabindex="-1"）以确保跳转后焦点真正落进去。
  • L4 分页总数：OrderRecordTable.vue:12 传 :total-records="totalPages * perPage"，最终由 UiPagination.vue:13 渲染成「共 N 条」。这是估算值而非真值（21 条会显示 40 条）。修法：让 useOrderList 暴露真实的 total 并透传。当前数据量不足以渲染分页器，本项未在渲染层复现，属源码级判断。
  • L5 同文件重选：useOrderImport.ts:195 把 excelFile 置 null，但没有复位 <input type=file> 的 value。按浏览器规范，再次选择同一个文件不会触发 change，表现为"导入按钮点了没反应"。修法：handleImport 成功后 excelInputRef.value.value = ''。属源码推导，未做浏览器复现（Playwright 程序化设置 value 无法反映真实选择行为）。
