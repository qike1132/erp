## 2. 为什么五项会被误判（模式识别）

原方案的错误有**共同模式**：把"未显式声明"当成"不存在"，把"已完成的治理成果"当成"待办债务"。

| 误判类型 | 实例 | 真相 |
|---|---|---|
| **契约已存在但未集中声明** | A1：以为"196 处内联 `success` = 无契约" | 契约在 `schemas/` 里声明（163 处 `success: bool`），内联 dict 是**实现**，不是缺失 |
| **已完成的治理被当成债务** | A6：以为"两个空壳待合并" | 拆分**早已完成**，两文件是刻意保留的兼容层（`order_crud.py:3-5` 写明"既有 52 处引用零改动"） |
| **框架语义被误读** | A8：以为 `lazy='select'` = N+1 风险 | async 下它是**安全标记**（未预加载即抛错），不是性能陷阱 |
| **既有能力被漏看** | A2：以为"轮子只用在一处" | 轮子本身**已很完善**（自动切换 + fallback），只是没铺开 |
| **只 grep 局部目录** | T02：只查 `api/` 判定"request_id 仅 1 处" | 实现位于 `core/middleware.py` + `main.py` |

**教训**：二手结论必须落到 `文件:行号` 实证，且**搜索范围要覆盖实现层而非只查调用层**。P0 的教训（4 项前提错 3 项）在 P1 重演（6 项错 5 项 + 1 项追加证伪）。

### 3.3 QA 三轮独立验证发现并修复的 2 个真实缺陷

| # | 缺陷 | 裁定与修复 |
|---|---|---|
| **1** | 失效发生在 **commit 之前**（观测序 `flush,flush,refresh,invalidate,commit`）→ 竞态窗口 | **修**。推演：T1 提交前失效 → 并发 T2 读库（看不到未提交数据）→ T2 把**旧数据写回缓存** → T1 提交后不再失效 → **脏数据留到 TTL**。改 post-commit 后，T1 提交时会把 T2 刚写的脏数据一并清掉。依据：`core/exceptions.py:176-180` docstring **原文写明** post-commit 回调"适用于**缓存失效**" |
| **2** | 库存/订单写路径不清 `product:list:*`，而 `Product.to_dict()` 含 `current_stock` → 首屏库存**必然**陈旧 | **修**。这是**本次改动引入的确定性回归**（改动前列表无缓存，不可能陈旧）。先补 `invalidate_stock_and_order()`，后经 QA 发现 `order/deduction.py:248` 走 `ORDER_AND_INVENTORY` 域路径仍漏，最终改为**域级方案**（见 3.5） |
| **3** | 新路径用裸 `safe_get/safe_set`，**无 Lua 防击穿**；冷缓存 20 并发实测回源 **20 次** | **不改**。与 `customer.py`/`supplier.py` 模板同构，属项目既定取舍。**但架构师报告"100 并发仅 1 次 DB 查询（Lua 防击穿）"的说法是错的**，已在此更正 |

### 3.4 附带修正：一条会导致缓存静默失效的误导注释

`api/v1/endpoints/customer.py:37-40` 原注释声称缓存模式最终匹配 Redis 中的 `'erp:erp:customer:list:*'`（双前缀）。**该推理是错的**：

- `utils/redis_cache.py:110-112` 的 `_make_key` 对**已带** `erp:` 前缀的 key **原样返回**（幂等性由 `tests/test_redis_key_namespace.py:135` 断言），对**未带**的才补前缀；
- 故物理模式是**单前缀** `erp:customer:list:*`，与 `build_cache_key` 生成的键同层。

**代码本身是对的，但这条注释会误导后人把模式"修正"成双前缀，从而静默失效。** 已改为如实描述 + 引用幂等性断言。

### 3.5 域级方案（B）的裁定过程

`order/deduction.py:248` 走 `cache_mgr.invalidate(DOMAIN, ORDER_AND_INVENTORY)`，不经 `invalidate_stock_and_order()`。审计发现改 `current_stock` 的位置有 **15+ 处**，逐个打补丁不可行。

架构师与 QA 提出两方案，我初判 A（定点），**被两位成员联合推翻**——我的驳回理由针对的是 B-as-PRODUCT，而实际路径用的是 `ORDER_AND_INVENTORY`（**不含 PRODUCT**），那个变体确实无效。

我重新推演唯一剩下的顾虑（"提交前被清 → 削弱 post-commit 保证"）后**改判 B(INVENTORY)**：

- `product:list:*` 挂入 `INVENTORY` 域后，product 写路径确实会在**提交前**多清一次；
- 但竞态**仍被修复**——post-commit 回调在**提交之后**执行，会把并发读回写的脏数据一并清掉；
- 所以提交前那次清理只是**冗余**，不是错误。

**语义依据**：`current_stock` 本就属库存域；`_DOMAIN_PATTERN_MAP` 只有 `cache.py:100` 定义 + `:126` 循环两个消费者，改动面可控。

### 3.6 测试语义失真（已纠正）

工程师的 `test_invalidation_deferred_until_commit` 曾断言并声称"**事务提交前缓存不得被清**"。B(INVENTORY) 后这句话在**缓存层面已不成立**（域级路径会在提交前清），该用例之所以仍通过，是因为它只追踪回调用的 `safe_delete_pattern`，而域级路径走 `invalidate_cache` → `redis.delete_pattern`，**未被追踪**——**名不副实，且与 QA 用例直接矛盾**（一个说"没清"、一个说"清了"）。

已纠正为只声明真正成立的属性：**回调未在提交前执行**；docstring 明确"此处验证的是回调触发时机，不代表缓存整体在提交前未被清"，并指向 `TestPostCommitRaceE2E` 作为竞态兜底的证据。

> **这是一类比测试失败更隐蔽的风险：绿灯通过，却让后人以为防护机制是 A，实际是 B。**

## 6. 经验教训

1. **二手结论必须落到 `file:行号` 实证，且搜索范围要覆盖实现层。** P1 六项错五项，加一项追加证伪。误判的共同模式是"把未显式声明当不存在""把已完成治理当债务""只 grep 调用层不看实现层"。
2. **"约定"要读原文。** A1 的证伪关键不是数字（196 处属实），而是发现 `success` 是**已声明契约**（163 处 `success: bool` + 前端 `ApiResponse<T>`）。数字对≠结论对。
3. **测试的断言范围必须与它的声称一致。** 绿灯但名不副实的测试，比失败的测试更危险——它让后人以为防护机制是 A，实际是 B。已纠正 1 处。
4. **"提交前未清"从来不是目的，"提交后必定已清"才是消除竞态的那个属性。** 混淆两者会导致误判 #1 白做。
5. **后人对注释的信任度很高。** 一条推理错误的注释（`customer.py` 双前缀）不会让代码出错，但会诱导后人把对的代码改错——**注释的正确性也需要被验证**。
6. **团队协作的价值在于互相证伪。** 本轮我推翻架构师 1 项前提（T02）、架构师与 QA 联合推翻我 1 项裁定（B 方案）。若只走单向汇报，这两处都会带着错误结论交付。
