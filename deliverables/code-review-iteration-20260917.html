S1契约只在 groups 强制，扁平字段完全不受校验

位置：fastapi_app/schemas/purchase_center.py 第 170–175 行

filling: list = []          # 无类型 → Pydantic 不校验内容
fabric: list = []
accessory: list = []
packaging: list = []
groups: list[MaterialCalcScopeGroup] = []   # 强类型 → 校验 → 本次 500 在此暴露

为什么值得改：同一份数据、同一次响应， 在 groups 里是"契约"，在扁平字段里是"任意 list"。这正是本缺陷长期潜伏、 直到新增 groups 才爆的结构性原因——不是运气问题，是校验面的不对称。

建议：把四个扁平字段改为 list[MaterialCalcRow]。 数据现已归一，改后不会产生新的 500，且能把同类缺陷在扁平层就拦住。

注意：这会新增校验，属行为收紧。建议先本地跑一次真实 payload （_verify_fix_prod_data.py 已有现成入口）确认全绿，再提交。

S2CSRF 测试并非隔离测试：通过与否取决于本机 .env（已复现）

位置：test_csrf_cookie_secure_scheme.py 第 55–70 行

机理：_csrf_secure 在 _setup_csrf() 内 只求值一次（middleware.py 第 87–90 行），即 app 创建/import 时冻结； 而测试的 monkeypatch.setenv("APP_ENV","production") 发生在之后。 于是第 58–59 行的守卫断言 assert settings.is_production is True 只能证明属性是动态的，证明不了中间件处于生产态——它断言了一个自己控制不到的条件。

复现（实测）： APP_ENV=development 强制运行时 → 
E AssertionError: HTTPS 下应带 Secure：fastapi_csrf_token=...; Path=/; SameSite=lax
1 failed in 1.84s        # 代码正确，测试却红了
APP_ENV=production → 1 passed；不干预（本机）→ 1 passed
即在开发配置的机器/CI 上会假红，维护者一旦"顺手改绿"，就会丢掉 HTTPS 侧的防退化断言。

建议（择一）： ① 在 conftest.py 里给该测试设置 CSRF_COOKIE_SECURE=true 后再 import app；或 ② 把 _csrf_secure 的读取从 _setup_csrf 移入请求处理内（每次请求读 env）， 顺便让该测试真正隔离。方案 ② 同时消除"S1 类"的 import 期固化隐患。

S3"这个 origin 是否放行"一个概念、四处实现，且规则发散

同一逻辑目前有四份实现，差异刚好落在容易踩的边界上：

实现位置规则
config._is_production_allowed_originhttps 全放 / http 仅 localhost 与私有 IP 字面量
middleware._is_allowed_origin生产=精确成员匹配，但做 rstrip('/') 归一
Starlette CORSMiddlewarereturn origin in self.allow_origins —— 精确匹配，不归一（已核实源码第 105 行）
auth._set_login_cookieshttps 判定用严格全等；CSRF 用 split(',')[0].strip().lower()

后果一（可复现）：若 CORS_ORIGINS 里写成 http://192.168.0.95:3000/（带尾斜杠），filter_cors_origins 会判"放行"并保留该串， 但 Starlette 永不匹配、浏览器 CORS 照旧失败——**过滤器说允许，中间件却拒绝**， 而 CSRF 分支又容忍它。排障时三方口径不一致，极难定位。

后果二：多跳/大写 X-Forwarded-Proto: https, http 或 HTTPS 时，CSRF 判定为 https、登录 cookie 判定为非 https → 同一请求内 access_token 与 fastapi_csrf_token 的 Secure 属性不一致。

提交信息称 CSRF 判定"与 _set_login_cookies 同源"——实际是两份独立实现， 只是当前 nginx 恰好发单值 $scheme 才没暴露差异。

建议：抽公共工具并在载入时归一， 例如 core/security_utils.py 提供 is_secure_request(request) 与 normalize_origin(origin)， 四处统一调用；filter_cors_origins 出口即 rstrip('/')。

S4文本字段已加固，数值字段仍裸露：Decimal(str(None)) 会炸

位置：purchase_product_service.py 第 289 行 per_unit = Decimal(str(mat.get('unit_usage', 0)))

风险：若某生产者给出 unit_usage=None， str(None) → Decimal('None') → 抛 InvalidOperation。 它是 ArithmeticError 子类，不在接口的捕获元组 (ValueError, OperationalError, DisconnectionError, RuntimeError) 内 （product_routes.py 第 311 行）→ 又一个无友好文案的 500。

当前安全的原因不对称：之所以现在不炸，是三张表的 to_dict() 各自写了 float(x) if x else 0 兜底（已逐处核实）—— 是生产者自觉，不是聚合内核保证。文本字段走的是内核显式归一，两者防护层级不同。 packaging 分类目前靠 accessory 的 material_category 复用， 一旦将来接入新的包材表，这个缺口就会打开。

建议：内核对称加固，一行即可：

per_unit = Decimal(str(mat.get('unit_usage') or 0))   # 与文本字段同一处理哲学

S5注释与实现不符：CSRF_COOKIE_SECURE=true 已不能"强制开启"

middleware.py 第 186 行注释称"CSRF_COOKIE_SECURE=true 仍可强制开启"， 但第 193 行是：

_csrf_sec = _csrf_secure if (_is_https and not _has_bearer_resp) else False
# _is_https=False 时，无论 _csrf_secure 为何值，结果恒为 False

影响：安全相关开关的语义被悄悄改写而文档未动。 运维若在明文 HTTP 上设 CSRF_COOKIE_SECURE=true 期望"强制 Secure"，实际不会生效。 建议二者取一：实现真正的 force 语义（if _csrf_secure and _is_https or _csrf_force）， 或把注释改为"仅决定 https 下是否打 Secure，不再具备强制力"。

S6实测数字漂移：文档写"11 行 NULL"，实测为 10

test_calculate_material_null_code.py 第 12、74、80、86 行与提交信息均写 「生产实测 11 行 material_code 为 NULL」，本次复测为 10 行 = product_fabric 8 + product_material 1 + product_accessory 1。

数字本身不影响正确性，但它是回归文档的"事实锚"。 建议在 docstring 里补上测量时间与查询语句，让后续复测可自证，而不是逐年漂移。
