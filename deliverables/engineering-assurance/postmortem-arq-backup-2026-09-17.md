## 一页摘要

当天夜里 22:09–22:16，一次例行生产环境复核中，一条较早的观测记录给人一个**错误印象**：「生产环境的 ARQ 任务队列 worker（负责备份、告警等定时任务）**没有在运行**」。

我们做了只读的独立复核，实际结论是：

1. **ARQ 一直在正常运行，备份任务链没有中断。** 在线服务（API、前端、Redis、数据库）全部健康。
2. 那条「ARQ 未运行」的记录，出自仓库里的一个诊断脚本 `runtime_mode_probe.py`——**该脚本会谎报**。我们当场复现了它：对一个**明明在运行**的 ARQ，它输出「not running」。
3. 21:46 前后确实发生过一次**约 13–16 秒的全栈短暂不可用**，但它不是 ARQ 宕机，而是**一次被「紧急停止」中途打断的「切换到开发模式」操作，随后又切回生产**。
4. **真正值得记录的隐患不是「曾经宕机」，而是「用来发现宕机的工具本身不可信」，以及若干观测盲区**——它们会让真正的故障更难被发现。

**一句话**：服务没坏，但**发现故障的能力**有洞。本报告记录这些洞并给出整改项。

## 背景：这套系统长什么样

- 这是一套 ERP 系统，**运行在生产服务器本机**（Windows + NSSM 把若干程序注册为 Windows 服务），前端由 nginx 托管在 `:3000`，后端是 FastAPI/Uvicorn 在 `:5002`（多 worker）。
- **ARQ** 是一个基于 Redis 的异步任务队列。后端把「备份、告警、报表导出、数据同步」等**定时/后台任务**丢进队列，由独立的 **ARQ worker 进程**消费执行。**如果 ARQ worker 停了，这些定时任务会静默不再执行**——这正是我们最担心的一类「静默降级」。
- **两个 Redis 实例**：`:6379` 作缓存，`:6380` 作 ARQ 的**消息代理（broker）**。ARQ 的在线心跳写在 **broker（6380）** 上，不是缓存上。
- **健康哨兵键**：ARQ 官方机制——worker 存活时，会周期性（本项目 60 秒）把一条心跳写进 Redis 的一个键（`arq:queue:health-check`）。**看这个键的新鲜度**，就能权威判断 worker 是否在线。本项目已有这个判活函数（`check_worker_health()`）。
- **NSSM 环境变量坑**：NSSM 服务的环境变量应「每个变量一条」。本项目被误写成「一条字符串里塞了多个变量」，导致这些变量**实际都没注入**到子进程（包括 `PYTHONUNBUFFERED`、`UVICORN_WORKERS` 等）。
- **「模式切换」**：项目提供工作台 GUI，可在「开发模式」与「生产模式」之间切换。切到开发模式会先**停掉生产服务**。

## 二、真正的发现：三个「能力缺陷」

### 缺陷 1（核心）：诊断脚本会谎报——「有正确契约却没有接线」

**现象**：仓库里的诊断脚本 `scripts/diag/runtime_mode_probe.py`，对一个**正在运行**的 ARQ worker 报了「未运行」（`verdict = "not running"`）。

**我们当场复现**：22:14:17 只读运行该脚本，它对一个明明健康运行的 ARQ 输出「not running」（原始输出见 **附录 B**）。

**人话版根因**：这个脚本靠「**读进程的命令行信息**」来判活。而本项目里 ARQ 由 NSSM 以**提权方式**拉起，其命令行对普通读取者**不可见**——脚本读不到就抛错，错误又被静默吞掉，于是保留了默认答案「未运行」。项目里其实**早有一个权威的判活函数**（读 ARQ 官方心跳哨兵键；代码名 `check_worker_health()`），但这个脚本**没有用它**；而那个函数也**只被「备份」相关端点使用**，从未接进任何通用健康检查或监控。**一句话：正确的判活契约存在，却没有接到该用的地方。**（逐步根因链见 **附录 B**）

**后果（这是重点）**：**当 ARQ 真的宕机时，这个脚本会输出和今天一模一样的结果。运维无法区分「真宕机」与「探针误报」。** 这是「有正确的契约，却没有接到该用的地方」的典型。

### 缺陷 2：ARQ 不在任何通用健康/监控端点上

我们对全部健康端点做了核对：

- `/api/health`、`/api/health/db`、`/api/health/live`、`/api/health/ready`、`/api/health/startup`、`/metrics` —— **没有一个检查 ARQ**。
- `/api/health` 内部只检查 `database` 和 `redis` 两项。

**后果**：**外部监控即使一直轮询 `/api/health`，ARQ 死掉也表现为「healthy」**。也就是说，备份链路可以**静默停摆**而监控无感——这正是「静默降级无人察觉」。

### 缺陷 3：启动期「无日志可查」

- 实测 `logs/erp-prod.log` **大小为 0 字节**（mtime 21:46:31），而生产栈明明在健康运行。
- 原因：NSSM 环境变量「一条塞多个」的 bug 导致 `PYTHONUNBUFFERED` **未注入** → 监督进程 `prod_runner` 自己的标准输出被**块缓冲**，启动信息全留在内存里，没落盘。
- 佐证：它派生的**子进程**日志正常（`后端(uvicorn).out.log` 有 143 KB），因为它给子进程**显式**设了 `PYTHONUNBUFFERED=1`，却没管住自己。
- 另有 GUI 在 21:46:24 执行「日志已清空」，使 0 字节看起来「像刚启动」，更难分辨。

**后果**：**一旦启动期出问题，磁盘上没有任何证据可查，重启还会破坏现场。** 这会把「分钟级可定位的故障」变成「无从下手的故障」。

## 三、另外两处「会误导运维」的问题（未定级，非 SEV-3）

### 3.1 `prod_runner.json` 的 `started_at` 字段名不副实
- 该字段**不是进程启动时刻**，而是「**本次写状态的时刻**」，每几秒刷新一次。
- 实测：文件里写着 `started_at = 2026-09-17T22:14:16`，而进程真实启动是 **21:46:31**——**差 28 分钟**。
- 后果：任何用这个字段判断「服务是不是刚重启」的逻辑，**结论必然错误**。

### 3.2 `UVICORN_WORKERS=8`「改了没用」的真相（常见误解澄清）
- 有一种常见误解认为「8 是代码里的默认值」。**实测不支持**：
  - 代码默认在无环境变量时是 `max(1, min(4, CPU数))`，**最多 4**。
  - 生效值 8 来自配置文件 **`.env` 的第 171 行 `UVICORN_WORKERS=8`**，由 `_load_dotenv()` 加载。
- 同时，**NSSM 里也声明了 `UVICORN_WORKERS=8`，但因前述 NSSM 环境变量 bug，它从未生效**。
- **准确的结论**：同一个参数**有两个声明处，只有 `.env` 生效，NSSM 那处被静默忽略**。因此「改 NSSM 里的 `UVICORN_WORKERS` 不会有任何效果」成立；但「8 来自代码默认值」不成立，**8 来自 `.env`（属配置生效）**。当前两处恰好都是 8，掩盖了这个隐患。

## 六、做得好 / 做得不好

**做得好**
- ARQ 采用了官方**心跳哨兵键**做权威判活，且已有可复用的 `check_worker_health()`。
- 备份**确实在产出产物**，数据保护未失效。
- 监督进程对「探针超时」与「进程真死」做了区分，避免误杀（代码中的防护值得肯定）。

**做得不好**
- **正确的判活契约没有被接到监控/诊断面上**，导致出现**第二套并不可靠的判活逻辑**（写进了诊断脚本）。
- **健康端点只看 DB/Redis，不看 ARQ**，等于默认「ARQ 永不挂」。
- **同一参数多处声明**（NSSM + `.env`），且其中一处静默失效。
- **监控字段（`last_status`）不会被验证**，长期卡在 `running` 无人察觉。
- **生产机被当作开发机频繁切换**：当天 GUI 日志（`logs/server_manager_20260917.log`）记录到 **17 次「启动开发/生产模式」动作**，其中 **8 次进入开发模式**——而按本项目设计，**进入开发模式会先停掉生产服务**（当日日志明确记录了 **4 次「已自动停止生产模式」**；其余几次应为已在 dev 态下的重启或开机首启，无对应停止记录），故每次进入开发模式都打开一个生产中断窗口（逐条摘录见附录 A：`_rex_mode_switches.txt`）。

## 附录 B：技术根因与复现原始输出

> 本附录收纳第 2 节「缺陷 1」的技术细节，供需要逐条核对的读者；不关注实现细节的读者可直接跳过，不影响正文结论的理解。

**复现输出（22:14:17，只读运行 `runtime_mode_probe.py`，原样）**：

```json
{
  "api_listening_pids": [7676],
  "api_processes": [ { "pid": 7676, "error": "(pid=7676)" } ],
  "verdict": "not running",
  "arq_worker_processes": []
}
```

**逐步根因链（连续追问）**：

1. 为什么说「没运行」？→ 脚本读进程的命令行（cmdline）时**读不到**，抛错，但错误被吞掉，脚本保留了默认答案 `not running`。
2. 为什么读不到？→ 进程由 **NSSM 以提权方式派生**，其命令行对普通读取者不可见。
3. 为什么用「命令行」当判据？→ 脚本把「5002 端口监听进程的命令行」当成**唯一可靠依据**——这个前提在 NSSM 环境下**不成立**。
4. 为什么没发现前提错了？→ 它**没有复用项目里已有的、权威的判活函数** `check_worker_health()`（读 ARQ 官方心跳哨兵键）。
5. 为什么有函数不用？→ 因为 `check_worker_health()` **只被「备份」相关端点使用**（入队前预检，ARQ 不在线就返回 503），**从未接入任何通用的健康检查或监控端点**。
