## 二、顺带收敛：`*INFRA_EXCEPTIONS` 变通方案（3 文件）

`except (RuntimeError, *INFRA_EXCEPTIONS)` 这个写法在项目里存在 **3 处**：

| 位置 | 原状态 |
|---|---|
| `core/purchase_cache.py` | P0 时已用本地副本 `_LOCAL_INFRA_EXCEPTIONS` 绕过（5 处使用） |
| `core/event_bus.py:27` | 直接星号解包（**未纳入类型门禁，故未暴露**） |
| `services/order/_common.py:39` | 直接星号解包（本次被门禁报出） |

**处理**：在 `core/exception_handler.py`（`INFRA_EXCEPTIONS` 的定义处）新增共享常量：

```python
# ⚠️ 不能直接写 `except (RuntimeError, *INFRA_EXCEPTIONS)`：mypy 无法推导
#    星号解包后的 except 元组类型（misc: Exception type must be derived from BaseException）
RUNTIME_INFRA_EXCEPTIONS: tuple[type[BaseException], ...] = (RuntimeError, *INFRA_EXCEPTIONS)
```

三处统一改用该常量，`purchase_cache.py` 的本地副本已删除。

> **收敛价值**：同一个"因 mypy 盲区而不得不写的变通方案"，此前在两个文件里各写了一遍，
> 第三个文件则因为不在门禁里而一直没被发现。**收敛到一处 + 让门禁覆盖** 才是根治。

## 三、★ 又一次自我证伪

我在《未修复项清单》里写：

> `daily_production_service.py:263,265` 值得优先：**金额/数量用 `float` 而非 `Decimal`
> 是典型的精度隐患。**

**这个判断是错的。** 实测：

```python
# shared_models/daily_production_record.py:33
unit_price: Mapped[float] = mapped_column(
    Numeric(10, 2), nullable=False, default=0,   # ← DB 列是精确十进制，正确
)
```

**数据库层用的是 `Numeric(10, 2)`（精确十进制），完全正确。**
错的只是 Python 侧的类型注解（`Mapped[float]`）—— SQLAlchemy 实际返回 `Decimal`。

同一模式还有两处（本次未改，因不在门禁内）：

```
shared_models/customer_sampling.py:291   Mapped[float | None] = mapped_column(Numeric(12, 2))
shared_models/purchase_order.py:151      Mapped[float | None] = mapped_column(Numeric(12, 2))
```

> **教训**：我从 mypy 的错误信息「got float, expected Decimal」**倒推**出"存的是 float"，
> 而没有去看**列定义**。mypy 报的 "float" 是**注解里的 float**，不是**运行时类型**。
> → **从类型检查器的报错反推运行时事实，是危险的**。

## 六、经验教训

1. **★ 不要从类型检查器的报错反推运行时事实。** mypy 说 "got float"，
   指的是**注解里的 float**，不是运行时类型。要判断"存的是不是 float"，必须**看列定义**。
   我因为跳过这一步，把一个"注解写错"误判成"精度隐患"。
2. **注解错误会误导两方**：调用方（以为返回值恒非 None）与类型检查器本身
   （报在调用方而非定义处）。修注解的收益不只是"消错误"。
3. **同一变通方案重复出现 = 应该收敛 + 让门禁覆盖。**
   `*INFRA_EXCEPTIONS` 写了 3 遍，第 3 遍因不在门禁内一直隐形。
4. **"疑似真缺陷"清单必须先甄别再动手。** 这份清单我标了约 15 个"疑似"，
   甄别后**真实缺陷为 0**。若不先甄别就批量改，会浪费在非问题上。
