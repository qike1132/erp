三、严重问题详述

S1 · 默认全选（severe）

现象：打开「批量发货」弹窗，未做任何操作，底部即显示"已选 325 道工序 · 涉及 60 个订单 · 本次共发 25,626,469 件"。

成因：旧实现 OutsourceShipDialog.vue 加载后 rows = list.map(r => ({ ...r, checked: true, shipQty: r.remaining }))——每行默认勾选、数量默认取满剩余；且无订单级选择层，提交即全量。

实测（temp/ship-redesign/evidence.json） rowCount = 325 summary = 已选 325 道工序 · 涉及 60 个订单 · 本次共发 25,626,469 件 orderSelect = false stepIndicator = false

影响：把"批量发货"做成"全量发货"。用户在 325 行里几乎不可能逐行取消，一旦误触确认，会对 60 个订单同时发起发货，不可逆。

改法：拆出 Step 1 选择订单（订单级勾选，默认全不选），未选订单时"下一步"禁用。

S2 · 无步骤 / 无分组（severe）

现象：弹窗内是一张 325 行的大表，需滚动约 40 屏；没有"先选订单 → 再填明细 → 最后确认"的分段。

成因：旧实现把 shippable() 的 325 行直接平铺，仅加一个关键字过滤框，缺少订单分组与确认环节。

实测 tableWrap.scrollHeight = 16873 clientHeight = 418 ratio = 40.37 thead = ["", "订单号", "客户", "SKU", "工序", "订单数量", "已发", "剩余未发", "本次发货数量"] 键盘序列 = 过滤框 → 勾选 → 勾选 → 数量 → 勾选 → 数量 …（650+ 个输入平铺交替）

影响：流程混乱不直观；无法按订单整体操作（如"整个订单 A 全发/全不发"）；没有二次确认，易错。

改法：Step 2 填写明细仅展示已选订单，按订单分组（订单头显示"已选 x/y 道工序 · 共 N 件"，可整组开关）。

M1 · 数量框无焦点环（medium）

键盘序列停点：oss-qty → outline: none 3px（无可见焦点）；复选框 → outline: solid 2px

改法：新实现的 .osw-qty:focus 与 .osw-filter:focus 显式加 box-shadow: 0 0 0 3px rgba(37,99,235,.12) 焦点环。

M2 · 无批量结果反馈（medium）

现象：提交后只弹一条 toast，成功/失败都在弹窗关闭或保留的状态里"一闪而过"。

改法：新增结果态——成功显示每订单一张发货单的清单（单号 / 客户 / 工序数·件数 / "待贝乐收货"徽章）；失败显示后端错误明细 + "返回修改"（已填数据保留）。

五、三步交互流程（改后）

① 选择订单

  • 订单级勾选，默认全不选
  • 每单显示：订单号 · 客户 · N 道工序 · M 件待发
  • 关键字过滤 + 全选 / 清空
  • 未选订单时"下一步"禁用

② 填写明细

  • 仅显示已选订单，按订单分组
  • 订单头：已选 x/y 道工序 · 共 N 件 + 整组开关
  • 逐工序：勾选 + 数量（缺省=剩余，未勾选时禁用输入）

③ 确认提交

  • 只读汇总：N 张发货单 / M 道工序 / X 件
  • 提交 → 单事务原子（每订单一张发货单）
  • 结果态：成功清单 / 失败明细 + 返回修改
