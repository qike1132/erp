## 一、两处事实修正

### 1.1 ❌ 原判断"webVitals 采集但从未回传"—— **不准确**

实测链路**已完整打通**：

| 环节 | 位置 | 状态 |
|---|---|---|
| 采集 | `utils/webVitals.ts`（`onLCP/onCLS/onINP/onTTFB`） | ✅ 存在 |
| 回传 | `navigator.sendBeacon('/api/v1/monitoring/vitals', ...)` | ✅ 存在 |
| 接收 | `endpoints/monitoring.py: POST /vitals` | ✅ 存在 |
| 查询 | `endpoints/monitoring.py: GET /vitals/summary` | ✅ 存在 |
| 挂载 | `router.py:272` `prefix="/monitoring"` | ✅ 存在 |
| CSRF 豁免 | `middleware.py:145-147` 专门豁免该端点 | ✅ 存在 |
| 启动接入 | `main.ts:149` 动态导入并调用 `initWebVitals()` | ✅ 存在 |

**真正的问题不是"没回传"，而是"回传了但没存"**：

```python
# 改造前 monitoring.py
_vital_stats: dict[str, deque[float]] = {}   # ← 进程内存，maxlen=500

@router.post("/vitals")
async def receive_vitals(...):
    for v in payload.vitals:
        if v.rating in ("poor", "needs-improvement"):
            logger.warning(...)              # ← 只对"差"样本打日志
        key = f"{v.name}:{v.rating}"
        _vital_stats[key].append(v.value)    # ← 好样本只进内存
```

三个硬伤（原 docstring 自认第 2 条）：

1. **重启即丢** —— 无跨时间基线；
2. **多 worker 各自独立** —— `"per-worker stats (multi-worker deployments aggregate separately)"`；
3. **只有 poor 样本落日志** —— 正常样本不落任何地方，算不出真实分布与 p50。

## 二、实施内容

### 2.1 新增表 `web_vital`

**模型**：`fastapi_app/shared_models/web_vital.py`（已注册进 `__init__.py` 与 mypy 门禁）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | SERIAL PK | |
| `name` | VARCHAR(16) NOT NULL | LCP / CLS / INP / TTFB / FCP |
| `value` | DOUBLE PRECISION NOT NULL | LCP/TTFB/FCP 单位 ms；CLS 为无量纲分数 |
| `rating` | VARCHAR(24) NOT NULL | good / needs-improvement / poor |
| `delta` | DOUBLE PRECISION | web-vitals 增量语义 |
| `navigation_type` | VARCHAR(24) | navigate / reload / back-forward / prerender |
| `path` | VARCHAR(500) | 取自 Referer，支持按页面维度分析 |
| `created_at` | TIMESTAMPTZ NOT NULL | 上报时间 |

**索引**（3 个，与模型声明**完全一致**）：

- `idx_wv_name_created (name, created_at DESC)` —— 基线查询主路径
- `idx_wv_rating_created (rating, created_at DESC)` —— 劣化排查
- `idx_wv_created_desc (created_at DESC)` —— 保留期清理

> 实现细节：`created_at` 刻意**不加** `index=True`。DESC 索引可反向扫描服务升序查询，
> 再加单列索引是冗余，且会导致"模型建 4 个索引、迁移建 3 个"的不一致。

**迁移**：`migrations/versions/pg_standalone_041_web_vital.py`（链至当前 head `pg_standalone_040`）

### 2.2 端点改造 `endpoints/monitoring.py`

**`POST /vitals`**：新增持久化，响应增加 `persisted: bool`（前端 sendBeacon 不读响应，用于排查"表为空"）

**`GET /vitals/summary`**：改为**优先读持久化表**（跨 worker、跨重启），新增 `hours` 时间窗参数（1h ~ 30d，默认 24h），返回 `count / avg / p95`；表不可用时回退进程内统计并在 `note` 中说明。

> 前端**只发不读** `/vitals/summary`（已确认无消费方），故改动零前端风险。

### 2.3 安全设计（未认证端点必须自带防护）

`sendBeacon` 无法携带 auth header，故该端点**按设计不认证**。而全局限流
（`core/limiter.py`）在内网环境下 `enabled=False`，**不可依赖**。因此写入侧自带三层防护：

| 防护 | 机制 | 目的 |
|---|---|---|
| **批次上限** | `_MAX_BATCH = 50` / 请求 | 单请求写入量封顶 |
| **保留期清理** | `_RETENTION_DAYS = 30`，进程内节流至 `_CLEANUP_INTERVAL_SECONDS = 3600` 一次 | 表不会无限增长 |
| **自愈熔断** | 失败后 `_PERSIST_RETRY_SECONDS = 300` 内短路写入 | 不刷日志、不拖慢上报；**迁移执行后无需重启即自愈** |

两个实现要点：

1. **节流标志在 `await` 之前同步置位** —— asyncio 单线程下这可正确阻止并发请求同时触发清理（防惊群）；
2. **熔断带冷却而非永久** —— 若因"迁移尚未执行"而失败，执行迁移后 300 秒自动恢复，不必重启进程。

## 四、⚠️ 待用户执行（我未自动执行的部分）

### 4.1 应用迁移（**必要**，否则落库不生效）

按项目约定（迁移由用户在合适时机执行），我**没有**自动对生产库执行：

```bash
cd migrations
PYTHONPATH=.. alembic upgrade head
```

> **注意**：数据库当前停在 `pg_standalone_039`，而 head 是 `pg_standalone_041`
> —— 即 **040（notification 索引）也尚未应用**，本次 `upgrade head` 会一并应用 040 与 041。

执行前可先确认：

```bash
cd migrations && PYTHONPATH=.. alembic current   # 看当前版本
cd migrations && PYTHONPATH=.. alembic heads     # 看 head（应只有 1 个）
```

**未执行迁移也不会导致故障** —— 端点会熔断并只告警一次，上报链路照常返回 `ok: true`。

### 4.2 数据库侧观测（**需 DBA / 超级用户**）

```sql
-- 1) 以超级用户执行
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
ALTER SYSTEM SET pg_stat_statements.track = 'all';
ALTER SYSTEM SET pg_stat_statements.max = 5000;
-- 2) 重启 PostgreSQL 实例（必须，shared_preload_libraries 非 reload 参数）
-- 3) 重启后在目标库执行
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- 4) 验证
SELECT calls, round(mean_exec_time::numeric,2) AS mean_ms,
       round(total_exec_time::numeric,0) AS total_ms, left(query,80)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

> 另外建议：`ALTER SYSTEM SET log_min_duration_statement = 200;`（记录 >200ms 的语句，
> 该参数支持 `pg_reload_conf()` 生效，**无需重启**）。

SELECT date_trunc('day', created_at) AS day,
       count(*) AS n,
       round(avg(value)::numeric, 1) AS avg_ms,
       round(percentile_cont(0.95) WITHIN GROUP (ORDER BY value)::numeric, 1) AS p95_ms
FROM web_vital
WHERE name = 'LCP' AND created_at > now() - interval '30 days'
GROUP BY 1 ORDER BY 1;

## 六、经验教训

1. **"没回传"与"没存"是两回事。** 我上一轮断言"webVitals 采集但从未回传"，
   实测发现链路早已完整打通（含 CSRF 豁免、main.ts 接入），真正的缺口是**持久化**。
   → **断言链路缺失前，先把每一环都 grep 到。**
2. **给未认证端点加写操作，必须自带防护。** 该端点按设计不认证（sendBeacon 限制），
   而全局限流在内网下是关闭的 —— 不能假设"有限流兜底"。
3. **熔断要能自愈。** 永久熔断在"迁移后未重启"场景下会静默失效；
   带冷却的熔断让部署顺序不再成为陷阱。
4. **模型与迁移必须逐项对齐。** `index=True` 与显式 `Index()` 会建出两套索引集合，
   这类不一致平时无感，直到有人用 `create_all()` 而不是迁移时才会暴露。
