1 · 一句话结论

这个页面有 7 个 severe，但它们不是「没做交互」——恰恰相反：交互代码写得很全，却有 4 处关键接线断了，于是「精心写好的反馈」在运行时到不了用户面前。

三条根因，而非现象罗列：
  1. RC-1 异常在两层被吃掉，失败被渲染成「空」。页面级 fetchOrders 没有 catch，全局 unhandledrejection 只打 console（main.ts:70-72），空态槽因此被点亮。结果：后端 500 时界面说「暂无订单记录」——它主动告诉用户「没有订单」。当前该接口 4/4 次全部 500，记录查询订单视图完全不可用。
  2. RC-2 校验与反馈挂在不可达的路径上。「新增订单」按钮 disabled 使 addStaged() 里的提示成为死代码；实测 Enter 也不会隐式提交（toast 0→0），鼠标与键盘两条路都到不了那条提示。
  3. RC-3 复合动作缺少分支收敛。批量提交在「订单失败 + 暂存区同时有备货」时：备货从未发出请求，却被移出暂存列表，同时提示「备货已提交成功」——数据静默丢失 + 误报成功。

真正做得好的部分也值得说明：焦点环系统一致（32 个 Tab 停点里 31 个有可见焦点环）、有 skip-link、prefers-reduced-motion 有全局兜底、弹窗焦点陷阱与 Escape 实测均正常、生产首屏在局域网下 TTFB 4ms / load 158ms——性能不是这个页面的短板，交互反馈的接线才是。

5 · 严重问题详述

S1 · 记录查询「订单」接口 500，被渲染成「暂无订单记录」severe 错误处理 · P0

现象。切到「记录查询」页签，订单列表显示空态「暂无订单记录」，看起来像业务上没有订单。

成因（三层叠加）。

  1. useOrderList.ts:70-88 fetchOrders() 只有 try/finally，没有 catch → 请求失败时异常逃逸，orderRecords 保持 []，而 finally 照常把 loading 清掉。
  2. main.ts:70-72 全局 unhandledrejection 只执行 console.error，不产生任何 UI。
  3. OrderRecordTable.vue:16-21 的 #empty 槽因 data 为空而渲染 → 空态被点亮。
实测（浏览器 response 事件 ＋ httpx 直连复验，两侧一致）
GET /api/v1/orders/list?page=1&per_page=20 → 500　（连续 4/4 次全部 500，含无参、per_page=5、带 factory 三种变体）
{"success":false,"detail":"获取订单列表失败: greenlet_spawn has not been called; can't call await_only() here. Was IO attempted in an unexpected place?"}
用户可见：emptyText = "暂无订单记录"　errorBanner=false　toast=""　retryBtn=false
控制台：[Unhandled Rejection] AxiosError: Request failed with status code 500
反向对照：合成 200 返回 1 行时，同一张表正常渲染出「2026-09-18 | 订单AUDIT-FAKE-1 | 审计合成客户 | 东莞 | 1 | 合成产品 | 10」→ 证明是数据链路失败，不是渲染故障

影响。订单视图对该用户完全不可用，且以最糟的方式失败——它主动告诉用户「没有订单」。业务侧可能据此得出错误结论（例如误判订单未录入）。这是本次审查优先级最高的一项。

根因定位（后端）。fastapi_app/api/v1/endpoints/order.py:91-94 把 SQLAlchemyError 统一转 500；greenlet_spawn 属 MissingGreenlet（SQLAlchemyError 子类）。这与项目既有结论一致：异步会话里的同步惰性加载，需在订单列表查询补 selectinload／改用已加载列。

改法。前端最小改动——不再吞掉错误：
// useOrderList.ts · fetchOrders
async function fetchOrders() {
  const seq = ++requestSeq
  const isInitial = orderRecords.value.length === 0
  if (isInitial) isLoadingRecords.value = true
  else isFetchingRecords.value = true
  errorMessage.value = ''                        // ← 新增：错误态
  try {
    if (recordType.value === 'stockin') await fetchStockins(seq)
    else await fetchOrderRecords(seq)
  } catch (e) {
    if (seq === requestSeq) {
      errorMessage.value = getErrorMessage(e, '订单列表加载失败')   // ← 不再吞掉
      if (isInitial) orderRecords.value = []
    }
  } finally {
    if (seq === requestSeq) { isLoadingRecords.value = false; isFetchingRecords.value = false }
  }
}

改善方向。失败从「静默伪装成空」变为「可识别 + 可重试」。建议同时把空态与错误态在视觉上分开，并在错误态提供「重试」按钮与 request_id（后端响应已带 request_id，便于运维对号）。注意：后端 greenlet_spawn 必须同步修，否则重试仍会失败。

S2 · 批量提交：订单失败时备货被静默删除且误报成功severe 操作路径 / 数据正确性 · P0　★ 本次新增

现象。暂存区同时有订单与备货时，若订单提交失败，备货条目会从暂存列表消失，并弹出提示「备货已提交成功，但订单提交失败，请重新提交订单」。

成因。useStagedItems.ts:93-114 的两个守卫条件不闭合：

// :93 —— 订单失败时，备货分支被整体跳过（备货从未发出请求）
if (!orderFailed && stockinPayload.length) { await post('/aux/batch-submit-stockins', …) }
…
// :106 —— 但 stockinFailed 仍为 false，于是备货被从暂存区删除
if (!stockinFailed) stagedItems.value = stagedItems.value.filter(i => !stockinUids.includes(i.uid))
…
// :111 —— 于是走进这个分支，播报与事实相反的成功
if (orderFailed && !stockinFailed && stockinPayload.length)
    showToast('备货已提交成功，但订单提交失败，请重新提交订单', 'warning')

证据（控制流穷举：4 种输入组合逐一求值）。

订单失败 + 有备货　→ 备货是否真的POST=False　保留策略=['orders kept', 'stockins removed']　toast="备货已提交成功，但订单提交失败，请重新提交订单"　← 缺陷
订单失败 + 无备货　→ 备货是否真的POST=False　保留策略=['orders kept', 'stockins removed']　toast=（仅 catch 内已提示）
订单成功 + 备货失败　→ 备货是否真的POST=True　保留策略=['orders removed', 'stockins kept']　toast="订单已提交成功，但备货提交失败…"　✓ 正确
全成功　　　　　　→ 备货是否真的POST=True　保留策略=['orders removed', 'stockins removed']　✓ 正确

影响。三重伤害叠加：① 备货数据从未提交；② 备货条目被移出暂存区，用户失去重试入口；③ 用户被告知「已提交成功」。这是本次审查中唯一会造成静默数据丢失的缺陷——用户在只查看 toast 的情况下会认为任务完成。

改法。把「是否尝试过」与「是否失败」分开记录，三者要保持一致：
let stockinAttempted = false
if (!orderFailed && stockinPayload.length) {
  stockinAttempted = true
  try { await post('/aux/batch-submit-stockins', …) }
  catch (e) { showToast(getErrorMessage(e, '备货提交失败'), 'error'); stockinFailed = true }
}
// 只有「尝试过且成功」才移除与播报成功
if (stockinAttempted && !stockinFailed) {
  stagedItems.value = stagedItems.value.filter(i => !stockinUids.includes(i.uid))
