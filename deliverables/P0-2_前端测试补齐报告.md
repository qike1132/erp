## 三、为什么先补这四层，而不是视图组件

补测试的 ROI 由「复用广度 × 失败影响面 ÷ 测试成本」决定。按此排序：

1. **`utils/`（最高）**：纯函数、无 DOM/网络依赖、零 mock 成本，且被大量视图复用。一个 `formatCurrency` 的 bug 会同时污染所有金额展示。
2. **`stores/`（高）**：全局单例状态，一处 bug 影响全站；`auth` 更承载权限与跨账号数据隔离，属安全相关。
3. **`api/request.ts`（高）**：所有请求的唯一出口，CSRF 注入、401 刷新、GET 去重都在此，且历史注释显示这里出过多个 bug（见文件内 5 处 TODO 与告警注释）。
4. **通用 `composables/`（中高）**：跨视图复用，但部分依赖 Vue 生命周期与响应式调度，测试成本略高。

**刻意跳过 `src/views/**`（239 文件）**：视图组件多为"事件处理器 + 模板"的胶水代码，单测需要大量 mock 且断言脆弱（改样式就红），性价比低。这类代码更适合用**端到端测试**覆盖关键流程，而非堆组件单测。若强行补齐视图以冲高总覆盖率，得到的是"好看但无用"的数字。

## 四、本轮发现的 3 个真实缺陷

### 4.1 ⚠️ `useDebouncedRef` 契约失效 → 库存页产品筛选完全不工作（已修复）

**文件**：`src/composables/useDebouncedRef.ts`（原实现）

```ts
// 修复前
export function useDebouncedRef<T>(source: { value: T }, delay = 300) {
  return refDebounced(ref(source.value) as Ref<T>, delay)
}
```

`ref(source.value)` 只读取**一次当前值**，之后传入的源再变化也不会传播。

**真实影响**：`src/views/stock/InventoryTab.vue:100`

```ts
const debouncedProduct = useDebouncedRef(computed(() => filters.product), 300)
// 第 115 行
product: debouncedProduct.value || undefined,   // 恒为 undefined
```

`debouncedProduct` 恒为空串 → 第 115 行永远发送 `undefined` → **库存页"按产品筛选"输入后毫无效果**（静默失效，无报错）。

**修复**：对传入的 Ref/ComputedRef 直接建立响应式绑定；普通对象保留快照语义并在 DEV 下告警；另导出 `useDebouncedRefReactive` 供需要跟随普通对象的场景使用。

**验证**：`useDebouncedRef.regression.test.ts` 的 ComputedRef 用例在修复前失败、修复后通过。

### 4.2 ⚠️ `/auth/me` 返回 `{user: null}` 会造出 id=0 的伪用户（已记录，未修）

`stores/auth.ts::fetchUser` 用 `res.user ?? res` 取值。当 `user` 为 `null` 时，`null ?? res` 得到的是**外层对象** `{user: null}`（因外层 `res` 本身非空），它能通过 `setUserInfo` 的 `typeof === 'object'` 校验，于是生成：

```js
{ id: 0, username: '', is_super: false, permissions: [] }
```

后果：`user.value` 变为 truthy → `loaded = true` → 前端呈现"已登录空壳态"（用户名为空、全站无权限入口），且不触发 401 登出流程。

**安全影响有限**：`is_super=false` 且权限为空，不会误授权。
**修复建议**：将 `res.user ?? res` 改为显式判空，例如 `res.user === undefined ? res : res.user`。
本轮以 `authStore.test.ts` 中「⚠️ 记录既有缺陷」用例锁定现状，避免重构时无意改变；修复时需同步更新该用例。

### 4.3 `formatDate(0)` 返回 `'-'`（记录）

守卫是 `if (!date) return '-'`，故数值时间戳 `0`（Unix 纪元）与 `''` 同样被当作"空"。对本系统无实际影响（不存在 1970 年的业务时间戳），已在测试中注明：若将来格式化可能为 0 的字段，须改为 `if (date == null)`。

## 五、测试编写过程中的两类坑（供后续参考）

### 5.1 VueUse `refDebounced` 在 fake timers 下需先 flush 微任务

`refDebounced` 内部是 `watch` + 定时器：**watch 回调在微任务（`nextTick`）中执行，之后才注册定时器**。若直接 `vi.advanceTimersByTime()`，定时器尚未注册，不可能触发更新。正确顺序：

```ts
source.value = 'x'
await nextTick()             // 让 watcher 结算，注册定时器
vi.advanceTimersByTime(300)  // 再推进虚拟时间
```

### 5.2 `vi.mock` 工厂内不能引用块级 `const`

`vi.mock` 会被提升到文件顶部，工厂函数引用下方 `const` 会报 `Cannot access 'x' before initialization`。须用 `vi.hoisted()` 一起提升：

```ts
const mocks = vi.hoisted(() => ({ api: { me: vi.fn() } }))
vi.mock('@/api', () => ({ authApi: mocks.api }))
```

### 5.3 jsdom 的 `Blob` 无 `text()` 方法

若需断言 Blob 内容，不能 `await blob.text()`，应拦截构造函数捕获入参：

```ts
vi.stubGlobal('Blob', class {
  constructor(parts, options) { capturedParts = parts; capturedType = options?.type }
})
```

## 六、与「修 backup 测试失败」的方法论呼应

本轮再次验证了 `deliverables/ERP_架构优化方案.md` 第十章提出的两条原则：

1. **断言要锁定契约的反面**。例如 `authStore.test.ts` 不仅断言"切号时清缓存"，还断言"同一账号刷新时**不**清缓存"；`apiRequest.test.ts` 不仅断言"同参 GET 去重"，还断言"参数不同**不**去重、失败后**不**永久复用"。
2. **从没失败过的测试不能算测试**。`useDebouncedRef` 的缺陷之所以能潜藏至今，正是因为此前没有任何测试覆盖它。新增回归测试后，已确认其在修复前**确实会失败**。

> 附：`deliverables/ERP_架构优化方案.md` 第十章记录的是后端同类问题——重构中"函数搬家"却漏改调用点，导致增量备份被误删。两轮共同指向同一结论：**"调用点与实现的一致"必须由入口级测试保证，纯函数单测对此免疫。**
