# ERP 系统迁移到新服务器方案（Windows 单机 · 只迁结构）

> 目标：把整个 ERP 项目完整搬到一台**新的 Windows 单机服务器**上。
> 部署方式与当前完全一致（Windows + NSSM + Nginx + FastAPI + Vue + PostgreSQL + Redis）。
> **只迁移数据库结构，不迁移业务数据**；数据库配套插件与现在完全一致。
> 本手册可直接复制给新服务器上的 Trae 执行。

---

## 1. 当前系统架构与组件清单（本次需迁移/重建的内容）

| 组件 | 现状 | 说明 |
|------|------|------|
| 后端 | FastAPI + Uvicorn（多 worker，httptools） | `start.py` → `prod_runner.py` 监督器守护 |
| 异步任务 | ARQ worker（内建 cron） | `fastapi_app.core.arq_app.WorkerSettings` |
| 前端 | Vue3 + Vite 7（`frontend-vite/`），生产构建 `dist/` | 由 Nginx 托管，反代 `/api`、`/ws`、`/static` |
| 数据库 | PostgreSQL 18，主库 `erp_system`（5432，用户 `erp_app`） | 只读 5433 副本本次**不建**（单机、只迁结构） |
| 迁移工具 | Alembic（`migrations/`） | 同步用 psycopg3 |
| 缓存/队列 | Redis 3 个逻辑库（6379 缓存 / 6381 broker / 6382 results） | 密码 `ERP_Redis_2026_Secure_Password` |
| Web 服务 | Nginx for Windows（`config/nginx-windows.conf`） | 监听 3000 |
| 进程守护 | NSSM 服务：`erp-prod`、`erp-arq`、`erp-redis` | 开机自启 + 崩溃自愈 |
| 监控(可选) | Prometheus / Alertmanager / OTel / PgBouncer | 见 `config/`，可按需部署 |

---

## 2. 数据库插件清单（必须与现在一致）

这些是 PostgreSQL 扩展/配置，**新库必须保证完全相同**：

- **pg_trgm**（必装）：GIN 模糊搜索索引。多个迁移（`pg_standalone_004`、`pg_standalone_026`）依赖。
- **pgaudit**：当前**未启用**（Windows 版需源码编译），用 PostgreSQL 内置 `log_statement='mod'` 做审计兜底。
- **PostgreSQL 内置审计配置**：`postgresql.auto.conf` 中应用了 `log_statement`、`log_connections`、`log_disconnections`。
- **流复制角色**：`erp_replicator`（复制）、`erp_readonly`（只读）——本次单机不建副本，可跳过，但如后续要加副本需保留。

> 说明：`pg_trgm` 由迁移脚本自动 `CREATE EXTENSION IF NOT EXISTS pg_trgm`，因此**只要迁移成功，插件即自动就位**。推荐用 `pg_dump --schema-only` 方案可一次性把所有扩展/索引/物化视图/分区/授权原样带过去，最保真。

## 3. 迁移步骤（分阶段）

### 阶段 0：新服务器基础软件安装

1. **Python 3.11+**（建议 3.12，与当前依赖版本匹配），勾选加入 PATH。
2. **Node.js 20.19+ / 22.12+**（Vite 7 要求），用于前端构建。
3. **PostgreSQL 18 for Windows**，端口 5432。安装后配置 `postgresql.auto.conf`（与旧库一致）：
   ```
   log_statement = 'mod'
   log_connections = on
   log_disconnections = on
   ```
4. **Redis for Windows**，端口 6379，设置密码 `ERP_Redis_2026_Secure_Password`（与 `.env` 一致）。
5. **NSSM**：解压到 `C:\nssm\nssm.exe`（`server_manager.py` 默认探测路径）。
6. **Nginx for Windows**：解压到 `C:\nginx\nginx.exe`（`prod_runner.py` 默认探测路径）。
7. （可选）Git，用于拉取代码。

### 阶段 1：代码迁移

把整个项目目录复制到新服务器（去掉体积大的非必需目录，可重新生成）：

- **必需保留**：`fastapi_app/`、`frontend-vite/`（源码）、`migrations/`、`config/`、`requirements/`、`start.py`、`server_manager.py`、`reset_admin.py`、`scripts/init_permissions.py`、`scripts/add_*.py`（导航授权脚本）、`.env.example`。
- **可删除/重建**：`frontend-vite/node_modules`、`frontend-vite/dist`（需重新 build）、`logs/`、`backups/`、`static/uploads/`、`static/releases/`、`.env`（需重建）。
- 若用 git：直接在新机 `git clone` 后检查 `.gitignore` 是否排除 `.env`、`node_modules`、`dist`。

### 阶段 2：数据库结构与插件（二选一）

先建库与用户（用 psql / pgAdmin 管理员执行）：

```sql
CREATE ROLE erp_app LOGIN PASSWORD '新强密码';
CREATE DATABASE erp_system OWNER erp_app;
```

> 若后续要读写分离，再补建只读用户：`CREATE ROLE erp_readonly LOGIN PASSWORD '...'; GRANT USAGE ON SCHEMA public TO erp_readonly; ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO erp_readonly;`

**路线 A（推荐，最保真）：旧库 schema 导出再恢复**

在旧服务器上导出结构（不含数据）：

```bash
pg_dump -U postgres -h old_host -p 5432 -d erp_system --schema-only --no-owner --no-privileges -F p > erp_schema.sql
```

把 `erp_schema.sql` 拷到新服务器，恢复：

```bash
psql -U postgres -h localhost -p 5432 -d erp_system -f erp_schema.sql
```

这会一次性带过去：所有扩展（含 pg_trgm）、表、索引、约束、物化视图、分区、序列、授权。**结构与原库完全一致**。

**路线 B（替代，纯迁移）：Alembic 跑迁移建表**

```bash
cd 项目根目录
pip install -r requirements/base.txt        # 需先装依赖以提供 psycopg3
# 确保 .env 已配置 DB 连接（见阶段 3）
alembic heads                                  # 确认唯一 head（应为 merge/最新链）
alembic upgrade head                           # 自动建 pg_trgm 扩展 + 全部表结构
```

> 若 `alembic heads` 显示多个 head，说明迁移图有分叉，需重点核对（当前以 `merge_resolve_all_heads` 合并 + `pg_standalone_*` 链为主）。**推荐优先路线 A**，避免迁移图分叉带来的结构差异。

无论哪条路线，随后**验证插件**：

```sql
SELECT extname FROM pg_extension WHERE extname='pg_trgm';   -- 期望返回 pg_trgm
```

### 阶段 3：后端依赖与环境配置

1. 安装依赖：

```bash
pip install -r requirements/base.txt
# 如需要 OCR 导入功能（约 500MB）：
pip install -r requirements/ocr.txt
# 开发/测试（可选）：
pip install -r requirements/dev.txt -r requirements/test.txt
```

2. 创建 `.env`（复制 `.env.example`，按新机填写）：

| 变量 | 说明 |
|------|------|
| `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME` | 指向新库，`DB_PASSWORD` 用强密码 |
| `SECRET_KEY` | 生成：`python -c "import secrets; print(secrets.token_hex(32))"` |
| `REDIS_HOST/REDIS_PORT/REDIS_PASSWORD` | Redis 地址与密码 |
| `REDIS_URL/REDIS_CACHE_URL/REDIS_BROKER_URL/REDIS_RESULT_URL` | 对应 6379/0、6379/1、6379/2 |
| `ASYNC_DATABASE_REPLICA_URL` | 单机不建副本，**置空**（读操作回退主库） |
| `JWT_ALGORITHM` | RS256 |
| `JWT_PRIVATE_KEY_PATH / JWT_PUBLIC_KEY_PATH` | 指向 RSA 密钥对 |
| `ALLOWED_HOSTS` | 新服务器 IP/域名（JSON 数组格式） |
| `CORS_ORIGINS` | 新服务器访问地址 |
| `APP_ENV` | `production` |
| `UVICORN_WORKERS` | 视内存（默认 4） |

3. **JWT RSA 密钥对**：把旧服务器的 `config/jwt/private.pem`、`public.pem` 一起拷过来（否则登录签发/校验会失败）。若想重新生成：
   ```bash
   openssl genpkey -algorithm RSA -out config/jwt/private.pem -pkeyopt rsa_keygen_bits:4096
   openssl rsa -pubout -in config/jwt/private.pem -out config/jwt/public.pem
   ```

### 阶段 4：前端构建

```bash
cd frontend-vite
npm install
npm run build        # 生成 dist/（Vite 7 构建）
```

> 若本机 `vite build` 卡死（见历史经验），改用 `npx vite preview --host 0.0.0.0 --port 3000` 对已有 dist 预览，或排查 Vite/Rolldown + PWA 冲突后重试。

### 阶段 5：初始化数据（管理员 / 权限 / 导航）——只迁结构必须执行

新库无业务数据，需手动建立初始账号与权限体系：

1. **创建管理员账号**（采用项目内常用写法，密码可改）：
   ```python
   # 参考根目录 _tmp_verify_user.py 的写法，在项目根执行：
   import asyncio
   from fastapi_app.core.database import _init_async_engine, _AsyncSessionLocal
   from fastapi_app.core.security import hash_password
   from sqlalchemy import text
   async def main():
       _init_async_engine()
       pw = hash_password("admin123")
       async with _AsyncSessionLocal() as s:
           await s.execute(text('INSERT INTO "user" (username, password, is_super, status) VALUES (:u,:p,true,true) ON CONFLICT DO NOTHING'), {"u":"admin","p":pw})
           await s.commit()
   asyncio.run(main())
   ```
2. **初始化权限数据**：
   ```bash
   cd scripts && python init_permissions.py
   ```
3. **补充导航与授权脚本**（按需逐项运行，幂等）：`scripts/add_*.py`，例如 `add_pattern_room_nav.py`、`add_purchase_center_nav.py`、`add_batch_nav.py`、`add_backup_nav.py`、`add_supplier_nav.py`、`add_production_plan_nav.py`、`add_outsource_nav.py`、`rename_dev_section.py` 等。运行后会自动清 nav Redis 缓存。
4. 建议运行 `python reset_admin.py` 重置 `admin` 密码为已知值（`admin123`）。

### 阶段 6：NSSM 服务 + Nginx 启动

启动顺序遵循 `prod_runner`：**后端 → ARQ → 前端**，以 `/api/health` 为就绪门。

1. **NSSM 安装（两步法，避免 `' '.join` 单参错误）**：

```bash
# 用补丁出真实绝对路径，以下以 <PY> 代表 python.exe 绝对路径
nssm install erp-prod <PY>
nssm set erp-prod AppParameters "-m fastapi_app.core.prod_runner --no-arq"
nssm set erp-prod AppDirectory <项目根>
nssm set erp-prod AppEnvironmentExtra PYTHONIOENCODING=utf-8 PYTHONUTF8=1

nssm install erp-arq <PY>
nssm set erp-arq AppParameters "-m arq fastapi_app.core.arq_app.WorkerSettings"
nssm set erp-arq AppDirectory <项目根>
nssm set erp-arq AppEnvironmentExtra PYTHONIOENCODING=utf-8 PYTHONUTF8=1

nssm install erp-redis <redis-server.exe>
nssm set erp-redis AppParameters "redis.windows.conf"
nssm set erp-redis AppDirectory <redis目录>
```

2. **启动服务**：
   ```bash
   nssm start erp-redis
   nssm start erp-prod
   nssm start erp-arq
   ```
3. **Nginx**：`prod_runner` 会自动探测并拉起 `config/nginx-windows.conf`（监听 3000，反代 5002）。若未自动启动：
   ```bash
   nginx -p <项目根> -c config/nginx-windows.conf -e logs/nginx-error.log
   ```
4. （可选）验证监督器环境：
   ```bash
   python -m fastapi_app.core.prod_runner --check
   ```

### 阶段 7：验证

- [ ] 后端健康：`curl http://127.0.0.1:5002/api/health` → 200
- [ ] 前端：浏览器访问 `http://<新服务器IP>:3000` 能打开登录页
- [ ] 数据库插件：`SELECT extname FROM pg_extension WHERE extname='pg_trgm';` → 有返回
- [ ] Alembic：`alembic current` 与 `alembic heads` 一致（路线 B）
- [ ] 登录：`admin / admin123` 可登录，权限/导航正常
- [ ] 备份模块可手动触发一次（验证 pg_dump 路径可用）
- [ ] 异步任务：触发一次导出/报表，确认 ARQ 正常消费

## 4. 一键恢复——给新服务器 Trae 的提示词

把上面手册放到新服务器项目目录后，对 Trae 说：

> 请按 `docs/迁移到新服务器方案.md` 在当前 Windows 服务器上完成 ERP 系统迁移重建。
> 执行顺序：阶段0 验证基础软件已装 → 阶段1 代码就位 → 阶段2 建库并恢复结构（推荐路线A schema-only，若没有 dump 文件用路线B alembic upgrade head）→ 阶段3 装依赖并写 .env → 阶段4 前端 npm install + build → 阶段5 初始化 admin/权限/导航 → 阶段6 安装 NSSM 服务并启动 → 阶段7 逐项验证。
> 只迁移数据库结构，不迁移业务数据；pg_trgm 等数据库插件必须与旧环境一致。
> 每完成一个阶段向我汇报结果，出现错误按手动册中的回滚/替代方案处理。

## 5. 风险与回滚

| 风险 | 应对 |
|------|------|
| Alembic 迁移图分叉（多 head） | 优先用路线 A（schema-only dump）；路线 B 需先 `alembic heads` 核实 |
| 前端 `vite build` 卡死 | 用 `vite preview` 对已有 dist，或排查 Vite/Rolldown+PWA 冲突 |
| 只迁结构导致缺初始账号/权限 | 必须执行阶段 5 的 admin/权限/导航初始化 |
| 端口冲突（5002/3000/5432/6379） | 释放旧进程，或改 `.env`/Nginx 端口 |
| Redis 三实例不一致 | 核对 `.env` 中 `REDIS_URL/CACHE/BROKER/RESULT` 指向 6379/0、/1、/2 |
| 回滚 | 阶段2 前保留旧库；失败可 `DROP DATABASE erp_system` 重建重跑；业务无数据，重建成本低 |
