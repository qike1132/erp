#### 缓存架构（三级）

| 层级 | 技术 | TTL | 容量 |
|---|---|---|---|
| **L1 进程内存** | Python dict | 30s | 10,000 条 |
| **L2 Redis** | redis.asyncio + hiredis | 60s | 无硬限制 |
| **L3 数据库** | PostgreSQL | — | — |

**缓存特性**：
- `CacheDomain` 位标志枚举：ORDER / INVENTORY / STOCKIN / PRODUCT / CUSTOMER / SEARCH / STOCKOUT
- `@cache_result` 装饰器：L1 → L2 → L3 逐级查找 + 回写
- 跨进程失效：Redis Pub/Sub `erp:cache_invalidation` 频道
- 优雅降级：Redis 不可用时回退进程内缓存
- 2s Redis 操作超时

### 3.3 技术匹配度分析

**得分：4.17 / 5**

**优势：**
- Vue 3 + TypeScript + Vite 是 2024-2026 中小型 ERP 的最优前端组合
- FastAPI + asyncpg + SQLAlchemy 2.0 异步栈匹配 I/O 密集型 ERP 场景
- TanStack Vue Query 解决了 SPA 数据同步痛点，与后端 REST API 匹配度高
- Pinia 3 轻量级客户端状态管理，符合 ERP 非复杂交互场景
- Reka UI + 自定义设计系统避免了 Element Plus 等重框架的样式覆盖痛点

**不足：**
- Celery 是同步任务框架，与 FastAPI 全异步架构存在割裂（需独立 worker 进程）
- 无实时数据同步层（WebSocket 仅用于通知推送，非业务数据推送）
- 前端无 SSR/SSG，SEO 不适用但 ERP 内部系统无此需求

### 3.4 性能表现分析

**得分：3.00 / 5**（最大改进空间）

#### 前端性能瓶颈

| 问题 | 位置 | 影响 |
|---|---|---|
| 硬编码 `per_page: 200` 全量加载 | `CustomerView.vue:169`, `CustomerOrderView.vue:575` | 大数据量时首屏慢 + 内存占用高 |
| 无虚拟滚动 | 所有表格使用 `v-for` 全量渲染 | 大列表 DOM 节点过多 |
| 2000+ 行重复 CSS | 每个视图重复 `.xxx-container/.xxx-card` | 增大 bundle 体积 |
| composable 返回 `reactive()` | `usePurchaseOrders.ts:63` 等 | 破坏细粒度响应式追踪 |
| Auto-Refresh 未基于 Page Visibility | `useAutoRefresh.ts:9-16` | 隐藏标签页仍运行定时器 |

#### 后端性能瓶颈

| 问题 | 位置 | 影响 |
|---|---|---|
| **N+1 查询：get_purchase_orders** | `purchase_order_service.py:175-205` | 每页额外 20+ 次 DB 查询 |
| **N+1 查询：export_completed_orders** | `purchase_order_service.py:726-730` | 导出时可能触发数百次查询 |
| **N+1 查询：get_factory_order_summary** | `purchase_order_service.py:663-668` | 汇总查询逐行嵌套 |
| 同步文件 I/O 阻塞事件循环 | `staging_service.py:108-110` | 大文件上传阻塞所有请求 |
| 全量加载计数 | `purchase_order_service.py:47-61` | 加载当日全部订单仅计序号 |
| `_resolve_products` 无限加载 | `stock_service.py:312-318` | 无搜索条件时加载全部产品 ID |
| 批量删除逐条操作 | `purchase_order_service.py:304-307` | 应使用 bulk delete |

## 五、替代技术方案建议

### 方案A：渐进优化（推荐）

**核心思路**：在现有技术栈基础上系统性优化，不更换任何核心技术。

| 改进项 | 具体措施 | 预期收益 |
|---|---|---|
| **消除 N+1 查询** | `selectinload` / 批量 `IN` 查询替代循环查询 | API 响应时间减少 40-60% |
| **组件拆分** | 按 PurchaseView 模式拆分 ProductList/CustomerOrder/StockOut | 代码复用率从 ~40% 提升至 80% |
| **虚拟滚动** | 引入 `@tanstack/vue-virtual` 或 `vue-virtual-scroller` | 大列表渲染时间减少 70% |
| **服务层基类** | 抽取 `BaseCRUDService` + `BaseSearchService` | 减少 30% 服务层代码量 |
| **统一缓存体系** | 合并 `core/cache.py` 和 `utils/redis_cache.py` | 降低维护复杂度 |
| **TypeScript 严格化** | 消除所有 `as any`，使用 `types/index.ts` 统一接口 | 编译期错误捕获率提升 50% |
| **CSS 提取** | 创建 `PageCard` / `FilterBar` / `DataTable` 布局组件 | 减少 2000+ 行重复 CSS |
| **修复 ORM 不匹配** | 同步 Service 代码与 ORM 模型字段名 | 消除运行时 AttributeError 风险 |
| **异步文件 I/O** | `aiofiles` 或 `run_in_executor` | 消除事件循环阻塞 |

**预期量化收益**：

| 指标 | 改善幅度 |
|---|---|
| 页面加载速度 | 提升 30-40% |
| API 响应时间 | 减少 50-200ms（N+1 修复） |
| 服务器资源占用 | 降低 20%（查询优化 + 缓存统一） |
| 代码量 | 减少 15-20% |
| 风险等级 | **低** |

### 方案B：中度升级

**核心思路**：替换存在架构性局限的组件，提升系统整体能力上限。

| 替换项 | 当前 | 替换为 | 理由 |
|---|---|---|---|
| **任务队列** | Celery 5.6 | ARQ / TaskIQ | 原生异步，无需独立 worker，与 FastAPI 一体化 |
| **表格组件** | 手写 `v-for` 表格 | TanStack Table / AG Grid Community | 内置虚拟滚动、排序、过滤、列固定 |
| **状态管理** | Pinia + Vue Query | + Valtio（局部复杂表单） | 复杂表单场景细粒度响应式 |

**迁移路径**：

```
Phase 1（1-2 月）：引入 ARQ 替换非核心 Celery 任务，并行运行验证
Phase 2（2-3 月）：视图逐个迁移至 TanStack Table
Phase 3（1 月）：下线 Celery，清理遗留代码
```

**预期量化收益**：

| 指标 | 改善幅度 |
|---|---|
| API 响应时间 | 额外减少 30%（异步任务无进程间通信开销） |
| 大表格渲染时间 | 减少 80%（虚拟滚动 + 列虚拟化） |
| 运维复杂度 | 降低（减少 Celery worker + Flower 监控） |
| 风险等级 | **中等**（需任务队列迁移验证） |

### 方案C：重度重构（不推荐短期实施）

| 替换项 | 替换为 | 风险 | 评估 |
|---|---|---|---|
| **前端框架** | Nuxt 3（SSR + SEO） | 全面重写，ROI 低 | ERP 内部系统无 SEO 需求 |
| **ORM** | Tortoise ORM | 生态不成熟，迁移成本极高 | SQLAlchemy 2.0 已是最佳选择 |
| **消息队列** | Kafka / RabbitMQ | 过度设计 | 当前规模不需要 |

**结论**：当前技术栈选择合理，无需框架级替换。方案 C 的收益不能覆盖迁移成本。

## 九、总结与建议

### 技术栈总体评价：良好（3.72 / 5）

项目技术栈选型**整体合理**，Vue 3 + FastAPI + PostgreSQL + Redis 是 2024-2026 年中小型 ERP 的主流成熟组合，社区活跃、生态完善。核心问题不在技术选型，而在**实现质量**。

### 三个最紧迫的改进方向

1. **后端 N+1 查询** — 当前最紧迫的性能瓶颈，修复后 API 响应可减少 50-200ms
2. **前端巨型组件 + 重复 CSS + `as any`** — 可维护性的最大障碍
3. **服务层重复代码**（库存更新 12+ 处、订单删除 2 处 70 行重复）— 增加了 BUG 风险和维护成本

### 推荐路线

**短期（1-3 月）**：执行方案 A 的 P0 + P1 项，消除 N+1 查询、修复 ORM 不匹配、拆分巨型组件、提取共享代码。预期 BUG 减少 40%、线上故障降低 50%。

**中期（3-6 月）**：执行方案 A 的 P2 项 + 方案 B 的部分升级（虚拟滚动、统一缓存），进一步提升性能和可维护性。

**长期（6-12 月）**：根据业务规模决定是否执行方案 B 的 Celery → ARQ 迁移。若任务量增长显著，建议迁移；若保持当前规模，Celery 足够。
