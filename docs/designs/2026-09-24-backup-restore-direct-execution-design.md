# 数据备份中心 · 还原按钮直接执行改造

> 范围：`/backup` 页面还原入口交互改造——取消"先选备份点"的向导步骤，改为点击即针对该备份直接进入确认与执行。
> 验收：`npm run type-check` + `npm run build` 通过，并交付手工回归清单（不在生产库执行真实还原）。

## Intent Contract

intent: 让 `/backup` 页面点击某个备份记录的「还原」按钮时直接针对该备份进入还原确认与执行，不再弹出需要用户重新选择备份点的向导；同时保留既有安全校验、明确操作确认与执行进度反馈。

constraints:
- 不得削弱既有安全机制：影响范围预览（覆盖表数、差异明细）、危险后果提示、输入「确认还原」二次确认、加密包解密密码、敏感配置显式勾选，五项均须保留。
- 不得改动后端接口契约与还原执行语义：预览仍走 `POST /backup/restore/plan`，入队仍走 `POST /backup/async-restore-by-name/{name}?confirm=true`，进度仍走 `GET /backup/progress/{task_id}`。
- 不得改动同一记录行的下载、删除行为，以及全量/增量备份、定时任务、路径设置等其它模块。
- 沿用现有 UI 令牌与组件风格，不引入新的运行时依赖。

success_criteria:
- 记录行「还原」与页面顶部还原入口打开同一个确认弹窗；由记录行触发时已自动带出该备份点，用户无需再选。
- 弹窗打开后自动拉取该备份的差异预览；预览未成功时禁止执行并显示原因。
- 执行按钮仅在「确认还原」文本完全匹配、且预览成功、且加密包已填写密码时可用。
- 确认后弹窗内展示进度条与阶段文案，终态展示还原成功/失败的结果报告。
- 执行期间弹窗不可被关闭或误关；完成后的结果报告不因父级任务状态复位而丢失。
- `npm run type-check` 与 `npm run build` 均通过。

risk_level: medium

## Verification Contract

verify_steps:
  - run: `cd frontend-vite && npm run type-check` → 期望 exit 0
  - run: `cd frontend-vite && npm run build` → 期望成功产出 dist
  - check: 全仓检索确认对已被替换的旧组件的引用已清理干净，自动生成的全局组件声明与实现文件一一对应
  - check: 逐条走查确认弹窗分支——明文包 / 加密包（未填密码不可执行）/ 预览失败 / 确认文本未匹配 / 勾选敏感配置 / 执行中禁止关闭 / 终态结果报告
  - manual: 按交付的手工回归清单在生产外环境验证全量包、增量包、加密包、损坏包、无差异包、敏感配置六类流程
  - confirm: success_criteria 各项均满足，且手工回归清单全部通过

## Governance Contract

approval_gates:
  - 本设计文档评审通过（当前步骤）
  - writing-plans 生成的 workflow 拆解确认后进入实现
  - 实现收尾后代码评审 + type-check/build 通过再合入
  - 真实还原执行须在获得明确授权并确认目标数据可被覆盖后进行，默认不执行
rollback: 改动集中在前端单视图与一个弹窗组件；出现异常可回退该次提交，前端变更不影响后端服务与既有备份文件。
ownership: 备份模块前端负责人；后端还原契约与维护窗口不变。

## Scope

| In | Out |
|----|-----|
| 记录行「还原」直接针对该备份进入确认与执行 | 后端还原逻辑、接口契约、权限与维护窗口 |
| 顶部还原入口收敛为同一确认弹窗（弹窗内提供备份点下拉） | 上传文件还原、下载、删除等其它记录操作 |
| 差异预览并入确认弹窗的影响范围区 | 全量/增量备份、定时任务、路径设置模块 |
| 统一轮询终态快照，保证进度与结果报告可靠呈现 | 统一轮询机制本身的改动（含既有终态复位行为） |
| 执行期间弹窗锁定与关键操作禁用 | 页面顶部备份任务卡在还原期间的文案（既有行为，本次不处理） |

## Decisions

| # | 决策 | 选择 | 理由 / 备选 |
|---|------|------|------------|
| 1 | 入口范围 | 记录行还原与顶部入口统一为同一确认弹窗 | 两处行为一致、减少两套流程的认知成本；备选「只改记录行」被否（用户要求两处统一） |
| 2 | 备份点选择 | 弹窗内下拉选择；由记录行触发时预填该备份点 | 既满足"点击即针对该备份"，又保留顶部入口自选能力 |
| 3 | 交互形态 | 单弹窗三段式：确认 → 进度 → 结果，移除步骤条 | 直接执行不再需要"选择/预览"步骤导航；备选「保留向导跳步」被否（步骤条语义与直接执行自相矛盾） |
| 4 | 差异预览去向 | 并入同一弹窗的影响范围区，保留覆盖表数与差异明细 | 安全可见性不下降；备选「完全移除预览」被否（削弱既有安全机制） |
| 5 | 二次确认强度 | 保留"输入「确认还原」"文字校验；切换备份点后需重新输入 | 覆盖生产库属高危操作，防护强度不降级 |
| 6 | 进度与结果归属 | 由父级在任务终态时快照任务状态并下传，弹窗内渲染 | 统一轮询在终态会复位任务状态，不快照则结果报告必然丢失 |
| 7 | 组件命名 | 由 `RestoreWizard.vue` 更名为 `RestoreConfirmDialog.vue` | 组件职责已从"向导"变为"确认与执行弹窗"，避免名实不符；备选「沿用旧文件名」被否 |

## Surface

APIs：无新增或变更。复用既有还原预览、异步按名还原、任务进度三个既有绑定，签名与参数语义保持不变。

Storage：无持久化变更；任务进度仍由后端承载，前端仅在内存中快照终态用于渲染结果报告。

Components：新增还原确认与执行弹窗组件（承载备份点下拉、影响范围预览、危险确认、进度、结果报告），并在页面视图中统一两个还原入口、注入终态任务快照；原向导组件随之移除。

Files-touched：`frontend-vite/src/views/backup/BackupView.vue`、`frontend-vite/src/components/backup/RestoreConfirmDialog.vue`（新增）、`frontend-vite/src/components/backup/RestoreWizard.vue`（移除）、`frontend-vite/src/components.d.ts`（自动生成，随构建同步）。

## Risks & Open Questions

- 备份点来源不一致：顶部入口的列表来自服务器备份清单，而记录表来自备份记录接口，两者集合可能不完全重合。需保证从记录行进入时，被触发的备份点一定出现在下拉中（不足时按触发项补齐）。
- 还原期间页面顶部的备份任务卡也会显示进度，且其标题固定为「备份」，与弹窗内的还原进度并存。这是既有行为，本次不处理；若希望一并收敛，请另行确认。
- 终态复位是既有修复的产物（避免按钮终身禁用），本次以父级快照规避，未改动该机制本身。
- 手工回归需要可用于覆盖的测试备份与生产外环境；真实还原默认不执行，需显式授权。
