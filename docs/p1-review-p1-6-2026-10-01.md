## §3 评审对象 ③——`fastapi_app/shared/stock_concurrency.py` 的条件化守卫与 rowcount==0 分流

### 3.1 守卫确实挂在策略条件之下（独立 AST 复算，非转述）

自研 AST 遍历 `stock_concurrency.py`，查找「`if` 条件含 `allow_negative_stock()`，且函数体内有 `conditions.append(...current_stock + delta >= 0...)`」：


两处、且都在 `if not allow_negative_stock():` 之下 ⇒ 策略为真时不附加守卫，与 `ALLOW_NEGATIVE_STOCK` 口径一致。

### 3.2 真实编译出的 UPDATE（探针 1：真实现 + `before_cursor_execute` 捕获 SQL，连测试库）

```
策略缺省（默认拒绝），delta=-5：

 WHERE product.id = $4::INTEGER AND product.version = $5::INTEGER AND product.current_stock + $6::INTEGER >= $7::INTEGER
ALLOW_NEGATIVE_STOCK=true，delta=-5：
UPDATE product SET current_stock=$1::INTEGER, version=$2::INTEGER, updated_at=$3::TIMESTAMP WITH TIME ZONE

```

两个入口（`apply_stock_delta_locked` / `update_stock_with_optimistic_lock`）形态一致（C1/C2 与 D1/D2）。参数化后 SQL 文本里没有字面量 `>= 0`，判据须是「含 `current_stock +` 且含 `>=`」——评审最初按字面量断言导致 5 个假失败，已在探针内校正。

### 3.3 rowcount==0 的两种分流（行为实证）

```
C5  策略缺省、库存 5、delta=-10：预检直接 ValueError('库存不足！当前库存: 5，需要: 10')，且**未发出 UPDATE**；库存未变 (5,0)
C6  内存视图陈旧（内存 5/version 0，DB 被旁路改成 2，delta=-5）：守卫使 rowcount=0 -> _classify_update_miss -> ValueError('库存不足！当前库存: 2，需要: 5')（不误报并发冲突）；库存未被覆盖 (2,0)

D1-D5 未持锁入口同口径，全部通过
```

### 3.4 与 ALLOW_NEGATIVE_STOCK 的一致性、以及与 DB 约束的互斥

```
C3/D3 策略=true 且 DB 约束存在、delta=-10：UPDATE 无守卫 -> IntegrityError（应用层放行、DB 层拒绝）
C4    事务内 DROP CONSTRAINT 后策略=true、delta=-10：成功 after=(-5,1)，UPDATE 无守卫；回滚后约束仍在
```

代码层面无矛盾：开关只解除应用层两道闸门（统一入口预检 + 061 守卫），DB 兜底与开关无关，且该互斥语义已在 `.env.example:187-197` 明写（含「置 true 前须手工 `ALTER TABLE product DROP CONSTRAINT ...`（不可逆）」）。见 F-03（运维口径提示，非代码缺陷）。
