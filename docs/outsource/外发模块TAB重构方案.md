> 配套交互效果图:[外发模块TAB重构效果图.html](./外发模块TAB重构效果图.html)(浏览器直接打开,可切换 TAB / 角色 / 弹窗)

## 1. 现状盘点(代码走读结论)

外发协作的业务链路:订单(工厂=湖北)→ 按 SKU 配置工序预设 → 订单按工序逐道「发货给外协方(贝乐)→ 加工 → 收货回厂」,每次发货生成发货单,贝乐确认收货闭环。

| TAB | 路由 | 页面主体 | 头部动作 | 弹窗内动作 | 主要角色 |
|---|---|---|---|---|---|
| 发货 | `/outsource/shipments` | 发货单台账(待收货/已完成 切换) | 待收货提醒、**批量发货**(右上角按钮) | 批量发货(双栏大弹窗)、发货单明细、确认收货 | 贝乐(收货方) |
| 外发工序 | `/outsource` | 湖北订单列表 + 外发进度条 | 产品/客户搜索、**导出未到货、打印未到货** | 订单外发工序弹窗(进度/台账 子TAB、行内发货/收货数量输入、一键发货、一键收货) | 工厂/管理员(发货方) |
| 工序预设 | `/outsource/presets` | SKU 工序模板表格 | 产品搜索 | 添加工序、删除工序 | 管理员(低频) |

底层接口现状(乱的根源所在):

| 动作 | 入口 | 接口 |
|---|---|---|
| 发货 ① | 发货页右上「批量发货」弹窗 | `POST /outsource/processes/ship-multi`(跨订单挑产品,合并生成发货单) |
| 发货 ② | 订单弹窗「一键发货」 | `POST /outsource/orders/{id}/processes/ship-batch`(单订单按工序) |
| 收货 ① | 发货单列表「确认收货」 | `POST /outsource/shipments/{id}/receive`(按发货单整单收) |
| 收货 ② | 订单弹窗「一键收货」 | `POST /outsource/orders/{id}/processes/receive-batch`(按工序批量收) |

## 2. 乱的根源(按影响排序)

1. **发货动作有两个入口、两套模型。** 同样是"把货发给贝乐",一个在发货页右上角弹窗(跨订单挑产品),一个在订单工序弹窗里(单订单按工序),命名一个叫「批量发货」一个叫「一键发货」。用户无法判断该用哪个,实际上两者最终都生成发货单。
2. **收货动作也有两个入口、两种口径。** 按发货单整单收 vs 按工序批量收,按钮分别叫「确认收货」「一键收货」,界面上没有任何地方解释两者的关系与适用场景。
3. **TAB 名与页面内容语义错位。** TAB1 叫「发货」但主体是台账+收货确认,真正的发货动作缩在右上角按钮里;TAB2 叫「外发工序」但主体是订单列表;「外发」与「发货」两个业务词混用,新用户分不清两个 TAB 的分工。
4. **落地页与 TAB 顺序矛盾。** TAB 条上「发货」排第一,但裸路径 `/outsource`(也是侧边栏唯一入口)落在第二个 TAB「外发工序」(2026-10-01 已核实现网行为)。
5. **「未到货导出/打印」挂错了地方。** 未到货 = 订单数量 − 已发数量 的跨订单聚合视图(`useOutsourceUnshipped.ts`),与发货侧同源,却挂在订单列表页头部。
6. **数字口径三套并存。** 订单列表的"外发进度%"、发货单的"明细数/发货总量"、工序台账的"工序累计已发/已收",同一业务三种说法,没有一个统一的在途/未到总览。
7. **发货单列表缺「发货单号」列。** 后端 `shipment_no` 字段已有(`schemas/outsource.py:212`),前端台账只显示发货时间,无法口头对单。

## 3. 角色动线分析

- **发货方(管理员/湖北工厂,`outsource_ship`)**:查进度 → 发货 → 等收货 → 对账。高频动作 = 发货 + 看进度。
- **收货方(贝乐,`outsource_receive`,只收不发)**:打开页面 → 看待收货单 → 确认收货。唯一高频动作是收货,却要面对 3 个 TAB(工序预设对其隐藏)。

现状对两个角色都不友好:发货方的高频动作藏在弹窗与第二个 TAB;贝乐进来先看到的是"发货单台账",但它的"待收货"提醒只是一条小字横幅。

## 4. 方案 A(推荐):发货工作台 + 外发进度 + 工序预设

### 4.1 新信息架构

```
TAB1 发货   /outsource          ← 发货工作台(原发货单页升级 + 统一发货入口 + 未到货总览)
TAB2 外发进度 /outsource/orders   ← 原「外发工序」订单列表,只读化(看进度/台账)
TAB3 工序预设 /outsource/presets  ← 不变
```

### 4.2 各 TAB 职责

**TAB1 发货(工作台)** —— 「要发的和在途的都在这」
- 顶部三张待办卡:
  1. **待发货**:N 单 · M 道工序 · K 件(可发货工序聚合)→ 主按钮 **「去发货」**(唯一发货入口)
  2. **待收货**:N 张发货单在途(点击滚动/过滤到下方台账的待收货页)
  3. **未到货**:X 件未发完 → 「导出未到货」「打印未到货」从订单页挪到这里
- 下方 = 发货单台账(待收货/已完成 切换,沿用现列表,补「发货单号」列)。
- 贝乐视角:待发货卡隐藏,待收货卡成为主视觉;行操作只保留「明细 + 确认收货」。

**TAB2 外发进度**(原「外发工序」改名)—— 「每张订单走到哪一步」
- 订单列表与进度条保持不变(这是它做得好的部分)。
- 订单工序弹窗改造:**去掉行内发货数量输入与「一键发货」**,改为底部「去发货」按钮 → 跳工作台并预选该订单(深链 `/outsource?ship_order=<id>`);「一键收货」改名**「按工序收货」**保留(补录场景),与整单收货明确区分。
- 「导出/打印未到货」从本页头部移除。

**TAB3 工序预设** —— 不变(低频配置,现状合理)。

### 4.3 统一后的动作规则

| 动作 | 唯一/主入口 | 口径 |
|---|---|---|
| 发货 | 工作台「去发货」(双栏弹窗,支持订单深链预选) | 全部走 `ship-multi`,每订单一张发货单 |
| 收货(主) | 工作台台账「确认收货」 | 按发货单整单收 |
| 收货(补录) | 订单弹窗「按工序收货」 | 按工序批量收,文案明确"补录" |
| 未到货 | 工作台第三卡 | 订单数量 − 已发数量,跨订单聚合 |

### 4.4 路由与权限

- 侧边栏零改动:后端 `nav_context.py` 外发权限仍映射 `/outsource`,落地即工作台(同时解决落地页矛盾)。
- 贝乐:`outsource_ship` 无 → 待发货卡与「去发货」自动隐藏;工序预设 TAB 维持隐藏;外发进度页只读可见。
- 工序弹窗深链参数需校验该订单确有可发货工序,否则按钮置灰。

### 4.5 改动清单(文件级)

| 文件 | 改动 |
|---|---|
| `router/index.ts` | `/outsource` → 工作台组件;新增 `/outsource/orders` → 原 OutsourceOrderView |
| `HubeiRouteTabs.vue` | TAB_PATHS、activeTab 推导、TAB2 文案「外发工序」→「外发进度」 |
| `OutsourceShipmentView.vue` → 改名 `OutsourceWorkbenchView.vue` | 加三张待办卡;接 `useOutsourceUnshipped`(导出/打印迁入);台账补发货单号列 |
| `OutsourceOrderView.vue` | 头部移除导出/打印按钮 |
| `OutsourceProcessDialog.vue` | 移除一键发货/行内发货输入;「一键收货」→「按工序收货」;新增「去发货」深链 |
| `OutsourceShipDialog.vue` | 支持订单预选参数(打开时预勾选该订单可发货工序) |
| 测试 | `HubeiRouteTabs.test.ts`、`routerNavAccess.test.ts` 更新路径断言 |
| 后端 | **零改动**(`shipment_no` 已有;ship-multi/receive 接口不动) |

工作量:前端约 1.5~2 天(含 vitest 回归),上线走 build + 强刷。

## 5. 方案 B(保守):只调顺序、命名与落地

> 交互效果图:[外发模块TAB重构方案B效果图.html](./外发模块TAB重构方案B效果图.html)(2026-10-01 补充,应用户要求出 B 版可视稿)

不动任何功能,只做四件事:
1. TAB 顺序改为「外发进度 / 发货单 / 工序预设」,`/outsource` 落「外发进度」;
2. TAB1「发货」改名「发货单」(诚实反映台账属性);
3. 「导出/打印未到货」挪到发货单页头部;
4. 发货单列表补「发货单号」列。

**2026-10-01 用户反馈:不喜欢方案A工作台的大卡片待办区,太占纵向空间。** 因此 B 版效果图完全去掉卡片区:待发货/待收货/未到货压缩为台账上方**一行信息条**(约 40px 高,含导出/打印按钮)。若最终选 A,同样可把三张待办卡替换为该一行信息条(即 A + 紧凑待办条),保留统一发货入口的同时不占空间。

工作量:半天。**但双发货入口、双收货入口的乱根仍在**(B 版订单弹窗保留行内数量输入与一键发货/一键收货),只适合作为 A 之前的过渡或 A 被否时的兜底。

> **2026-10-01 落地记录**:用户选定方案 B,已实施到前端源码(未构建上线):
> - `HubeiRouteTabs.vue`:TAB 顺序改为 外发进度 → 发货单 → 工序预设,「发货」改名「发货单」并取消贝乐双名;
> - `OutsourceShipmentView.vue`:页头精简为仅 Tab 导航,新增 `OutsourceShipmentStrip.vue` 单行信息条(台账标题 + 待收货 X 张 + 未到货 X 件 + 状态切换 + 导出/打印未到货 + 批量发货),台账补「发货单号」列;
> - `OutsourceOrderView.vue`:移除页头「导出/打印未到货」;
> - 测试:`HubeiRouteTabs.test.ts` 重写(新顺序/新命名)、`OutsourceShipmentView.test.ts` 适配信息条类名;
> - 门禁:vue-tsc、vitest 1117/1117、eslint 0 errors、quality_gate PASS。
> 效果图中的「860 件在途」因现接口无在途件数聚合未展示(仅展示待收货张数与未到货件数);如需在途件数需后端补聚合字段。

## 6. 对比与推荐

| 乱的根源 | 方案 A | 方案 B |
|---|---|---|
| 1 发货双入口 | ✅ 收敛为唯一入口 | ❌ 保留 |
| 2 收货双口径 | ✅ 主/补录分层+改名 | ❌ 保留 |
| 3 TAB 语义错位 | ✅ 工作台化 | ⚠️ 仅改名 |
| 4 落地页矛盾 | ✅ 落工作台 | ✅ 落外发进度 |
| 5 未到货挂错位 | ✅ 迁至工作台 | ✅ 迁至发货单页 |
| 6 口径三套 | ✅ 待办卡统一总览 | ❌ 保留 |
| 7 缺发货单号 | ✅ 补列 | ✅ 补列 |

**推荐方案 A。** 它把"发货"从一个藏在按钮里的动作升级为页面的第一视觉,发货/收货各归其位;后端零改动,风险集中在前端路由与两个弹窗的交互串联上,可一次上线。方案 B 可作为灰度过渡:先 B 后 A,B 的四项改动全部是 A 的子集,不会返工。

## 7. 实施顺序(按 A)

1. 路由与 TAB 骨架(含两个测试文件)——先行可独立上线;
2. 工作台三卡 + 未到货迁移 + 发货单号列;
3. 订单弹窗改造(去发货深链 + 按工序收货改名)+ `OutsourceShipDialog` 预选;
4. `npm run type-check && npm test && npm run lint` → build → 强刷验证贝乐与发货方两个角色视角。
