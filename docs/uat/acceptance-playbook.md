# 核心业务验收剧本（UAT Playbook）

**建立日期**：2026-11-03（整改 2026-11-03 全栈测试审查阻断项 S1）
**适用系统**：滨发协同系统（`D:/erp_system`，内网生产 ERP）
**验收人**：业务负责人（系统实际使用者）
**记录归档**：`evidence/uat-run-<YYYY-MM-DD>.md`（模板见文末）

---

## 一、这份文档要解决什么

审查发现：全仓**没有任何 UAT 资产**——无验收剧本、无判定标准、无签收记录。
后果是任何一个需求都无法回答三个问题：**验收条件是什么？谁确认的？记录在哪？**

「备份还原能用」「订单流程正常」这类表述不可判定。本剧本把每个场景写成
「操作 → 可观察结果 → 通过/不通过」的三段式，让验收变成**可判定**动作。

> 这是 2026-10-31 审查遗留的同一个缺口，本次为第二次提出。落地本剧本即视为闭环。

## 二、与自动化 E2E 的分工边界（重要，避免重复劳动）

| | 自动化 E2E（`tests/e2e_api`、Playwright） | 本 UAT 剧本 |
|---|---|---|
| 判定者 | 机器 | 人（业务负责人） |
| 判定对象 | 接口返回码、回库数据、页面渲染 | 用户能否在真实页面上完成业务、结果是否符合业务预期 |
| 执行频率 | 每次 push（CI） | 每次上线前 / 重大改动后 |
| 失败含义 | 代码回归 | 业务不可用 or 判据未达成 |

**UAT 不重复断言 SQL 级细节**（那是 E2E 的职责）。UAT 只回答：**人按真实页面操作，业务是否成立。**

## 三、执行环境与准入

- 环境：CI 同款隔离拓扑（专用后端 5502 + `*_test` 库 + 前端产物），**不得在生产主机上对生产库执行**。
- 账号：至少两个角色——超管 + 普通业务角色（验证权限差异）。
- 数据：每轮从空库开始；场景内自造数据，命名带 `UAT-<日期>-<序号>` 前缀，便于追溯。
- 准入：`pytest tests/e2e_api` 全绿（接口层无回归）后才开始人工 UAT。
- 准出：本剧本 12 个场景全部有判定结果与签收人；「不通过」项必须有缺陷单号。

## 四、A. 采购域（3 场景）

### UAT-P01 采购下单（一键生成采购单）
1. 以业务角色登录 → 进入**采购中心** → 选中一条状态为「待备货」的客户订单。
2. 点击「一键生成采购单」。
3. **判定**：
   - 该订单**恰好生成 1 张**采购单（不多不少）；
   - 订单列表状态变为「已备货」；
   - **重复点击同一条订单**不再新增采购单（幂等）。
- 不通过示例：生成 2 张、或状态未变、或重复点击又生成一张。

### UAT-P02 采购完成
1. 对 UAT-P01 生成的采购单执行「完成」。
2. **判定**：
   - 采购单状态 = 已完成；
   - 对应客户订单「确认」按钮可点击，确认后状态仍为「已备货」；
   - 采购单在列表中可被筛选到（不因完成而消失）。

### UAT-P03 来料登记（入库）
1. 对已完成的采购单登记到料（数量按要求填写）。
2. **判定**：
   - 登记记录出现在**来料登记**列表，采购单号/数量与录入一致；
   - 对应产品的「库存（结余）」**增加登记数量**；
   - 库存流水中出现本次入库记录。
- 说明：此场景是「采购→入库→结余」链路的唯一人工验收点。

## 五、B. 客户订单域（3 场景）

### UAT-O01 录单
1. 进入 **/customer-order** 录入页，用页面表单填写：产品、数量、客户。
2. 提交。
3. **判定**：
   - 订单出现在订单列表，状态 = 待备货；
   - 产品/数量/客户与录入**完全一致**（无静默截断或改写）；
   - 列表页无需刷新即出现（或刷新后出现，二者取一致口径并记录）。

### UAT-O02 确认门控（业务规则拦截）
1. 对一条**未在采购中心下单**的湖北订单，点击「确认」。
2. **判定**：
   - 界面给出**明确拒绝提示**（对应 409 语义，文案可读，不是空白或未捕获异常）；
   - 订单状态**不变**；
   - 页面无控制台报错横幅。

### UAT-O03 订单确认幂等
1. 承接 UAT-P02（订单已备货可确认），点击「确认」。
2. 再次点击「确认」。
3. **判定**：
   - 第二次仍给出成功提示（不报错）；
   - **确认时间不被改写**、状态不倒退；
   - 报表中的确认时间与第一次一致。

## 六、C. 出货域（4 场景）

### UAT-S01 部分出货
1. 对 UAT-O01 的订单（数量 10）执行出库 4。
2. **判定**：订单状态变「待出货」；产品结余**减 4**。

### UAT-S02 出满转态
1. 再出库 6（累计 10）。
2. **判定**：订单状态**精确**变「已出货」（不是「待出货」）；结余累计减 10。

### UAT-S03 超量拦截
1. 对已出完的订单再次出货（任意数量）。
2. **判定**：界面拒绝并说明原因（对应 400 语义）；结余**不变**；无 500。

### UAT-S04 退货回冲
1. 对 UAT-S02 的出库记录退货 4。
2. **判定**：结余**加 4**；订单状态回到「待出货」。
3. 再取消该退货。
4. **判定**：结余与状态**复原**（结余累计减 10、状态「已出货」）。

## 七、D. 系统操作域（2 场景 · 高危操作，对应历史 High ④）

> 这两个场景是当前**唯一没有人工验收闭环**的高危操作，务必执行。

### UAT-B01 上传还原的二次确认
1. 进入备份页 → 选择本地备份文件 → 在弹出的确认框点「取消」。
2. **判定**：**不发还原请求**、数据库无任何变化（可用列表页数据是否有变动佐证）。
3. 重新选择文件 → 在确认框点「确定」。
4. **判定**：还原启动；进度可见；完成后报告含 `pre_restore_backup`（回滚点）信息。

### UAT-B02 还原向导的勾选门
1. 打开还原向导 → **不勾选**「我已知晓：还原将覆盖当前数据库全部数据且无法撤销」。
2. **判定**：「确认还原」按钮**不可点击**（灰态）。
3. 勾选后再验证按钮可点击（不必真的执行还原）。

## 九、缺陷回流规则

任何「不通过」项必须按仓库铁律 1 处理：**先补一条能红的自动化回归用例（Red），再修（Green）**，
不允许只改代码不留测试。UAT 发现的问题因此会自动沉淀为长期防线，而不是一次性修完就忘。
