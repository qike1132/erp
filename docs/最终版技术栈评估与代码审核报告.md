### 3.2 各维度详解

**技术匹配度（4.17/5）：** 选型合理，Vue 3 + FastAPI + PostgreSQL 是中小型 ERP 的主流成熟组合。扣分项：Celery 同步任务框架与 FastAPI 全异步架构存在割裂；前端无 WebSocket 业务数据推送。

**性能表现（3.00/5 — 最大改进空间）：** 3处 N+1 查询、同步文件 I/O 阻塞、无虚拟滚动、硬编码大分页，是性能瓶颈的核心来源。

**可扩展性（3.33/5）：** 三级缓存架构合理，读写分离就绪。扣分项：31 个服务模块缺少抽象基类，CRUD 模式重复实现。

**安全性（3.83/5）：** Argon2id + JWT + CSRF + XSS 清理 + 限流。扣分项：`ALLOWED_HOSTS` 默认 `"*"`，`SECRET_KEY` 默认空字符串，supplier 端点缺少细粒度权限控制。

**社区支持（4.67/5）：** 所有核心依赖社区活跃。msgspec 和 Reka UI 社区较小但增长速度良好。

#### P0-1：N+1 查询 — `get_purchase_orders`

| 属性 | 内容 |
|------|------|
| **文件** | `fastapi_app/services/purchase_order_service.py:175-205` |
| **严重程度** | P0 — 影响性能和数据查询效率 |
| **发现轮次** | 第一轮 |

**问题描述：**

```python
# 当前实现：每条订单额外 1 次查询
for order in orders:                         # 循环 N 个订单
    items_result = await db.execute(         # +1 查询/订单
        select(PurchaseOrderItem).where(PurchaseOrderItem.order_id == order.id)
    )
    items = items_result.scalars().all()
```

每页 20 条订单触发 1 + 20 = 21 次数据库查询。P95 响应时间增加 50-200ms。

**根因：** 同文件的 `get_completed_purchase_orders`（L546-L553）已正确使用批量 `IN` 查询 + `items_by_order` 字典，但此函数未同步更新。

**修复方案：**

```python
order_ids = [o.id for o in orders]
items_result = await db.execute(
    select(PurchaseOrderItem).where(PurchaseOrderItem.order_id.in_(order_ids))
)
all_items = items_result.scalars().all()
items_by_order = defaultdict(list)
for item in all_items:
    items_by_order[item.order_id].append(item)
# 然后在循环中使用 items_by_order[order.id]
```

**验证标准：** SQL 日志确认查询数从 N+1 → 2（总查询）

#### P0-4：ORM 模型字段与 Service 代码不匹配（数据正确性Bug）

| 属性 | 内容 |
|------|------|
| **文件** | `fastapi_app/services/purchase_order_service.py` |
| **涉及行号** | L100, L199, L200, L244, L245, L292, L293, L300, L366, L592, L593, L742 |
| **严重程度** | P0 — 导致 `total_price` 和 `material_category` 始终为默认值 |
| **发现轮次** | 第一轮，第二轮确认所有 12 处受影响的代码位置 |

**ORM 模型实际字段：**

```python
# shared_models/purchase_order.py:116-117
total_price: Mapped[float | None] = mapped_column(...)      # 此字段存在
material_category: Mapped[str | None] = mapped_column(...)  # 此字段存在
# 注意：模型中没有 amount、category、supplier_id 字段
```

**错误代码 vs 正确代码：**

| 行号 | 错误字段名 | 应为 | 所在函数 |
|------|-----------|------|---------|
| L100 | `amount=amount` | `total_price=amount` | `create_purchase_order` |
| L199 | `item.amount` | `item.total_price` | `get_purchase_orders` |
| L200 | `item.category` | `item.material_category` | `get_purchase_orders` |
| L244 | `item.amount` | `item.total_price` | `get_purchase_order` |
| L245 | `item.category` | `item.material_category` | `get_purchase_order` |
| L292 | `item.amount = ...` | `item.total_price = ...` | `update_purchase_order` |
| L293 | `item.category = ...` | `item.material_category = ...` | `update_purchase_order` |
| L300 | `total_amount += item.amount` | `total_amount += item.total_price` | `update_purchase_order` |
| L366 | `category=item.category` | `category=item.material_category` | `complete_purchase_order` |
| L592 | `item.amount` | `item.total_price` | `get_completed_purchase_orders` |
| L593 | `item.category` | `item.material_category` | `get_completed_purchase_orders` |
| L742 | `item.amount` | `item.total_price` | `export_completed_orders` |

**根因分析：** `expire_on_commit=False`（`database.py:55`）使得 SQLAlchemy 在 commit 后不刷新对象属性。这导致代码中虽然使用了不存在的 `amount`/`category` 属性，但不会立即报错——SQLAlchemy 允许对 undeclared 的属性进行赋值和读取，但这些值**不会持久化到数据库**。实际的 `total_price` 和 `material_category` 列始终保持默认值（0 或 NULL）。

**修复方案：**

1. 全局搜索替换：`item.amount` → `item.total_price`，`item.category` → `item.material_category`
2. 移除所有 `supplier_id` 对 `PurchaseOrderItem` 的赋值（该模型无此字段）
3. 考虑将 `expire_on_commit=False` 改为 `True`，以便未来类似问题能被更早发现

**验证标准：** 创建采购订单后，在数据库中直接查询 `purchase_order_item` 表，验证 `total_price` 和 `material_category` 不等于默认值。

```python
temp_fd, temp_path = tempfile.mkstemp(suffix='.xlsx')
```

大文件上传时将阻塞所有异步请求处理。

**修复方案：** 使用 `aiofiles`：

```python
    await f.write(file_content)
    temp_path = f.name
```

#### P2-2：`expire_on_commit=False` 掩盖 ORM 字段不匹配（新发现）

| 属性 | 内容 |

#### P2-3：composable 返回 `reactive()` 破坏响应式

| 属性 | 内容 |
|------|------|
| **涉及文件** | `usePurchaseOrders.ts:63`, `useAutoRefresh.ts:29`, 及其他 |
| **发现轮次** | 第一轮 |

```typescript
return reactive({ orders, loading, page, ... })
```

问题：解构后失去响应式；任意属性变更触发所有消费者重渲染；阻止细粒度依赖追踪。

**修复方案：** 返回包含 ref 的普通对象，消费者使用模板自动解包或 `storeToRefs`。

#### P2-4：无虚拟滚动

| 属性 | 内容 |

| **发现轮次** | 第一轮 |

**修复方案：** 引入 `@tanstack/vue-virtual` 或 `vue-virtual-scroller`。

#### P2-5：Auto-Refresh 定时器在隐藏标签页仍运行

#### P2-6：异常处理不一致

| 属性 | 内容 |
|------|------|
| **发现轮次** | 第一轮 |

多种模式混用：`raise ValueError()` 用于业务错误和验证错误；自定义异常仅在部分模块使用；`PermissionDeniedError` 本地定义而非共享；缓存/同步失败仅 warn，可能掩盖问题。

**修复方案：** 建立统一异常层级（`BusinessError`, `ValidationError`, `PermissionError` 等），全局异常处理器统一转发。

## 五、架构级优化建议

### 5.1 推荐路线：渐进优化（方案A）

**核心思路**：在现有技术栈基础上系统性优化，不更换核心技术。

| 改进项 | 措施 | 收益 |
|------|------|------|
| 消除 N+1 | `selectinload` / 批量 `IN` | API 响应时间减 40-60% |

| 组件拆分 | PurchaseView 模式推广 | 代码复用率 40%→80% |
| 虚拟滚动 | `@tanstack/vue-virtual` | 大列表渲染时间减 70% |
| 服务基类 | `BaseCRUDService` | 服务层代码减少 30% |
| TypeScript 严格化 | 消除 62 处 `as any` | 编译期错误捕获率提升 50% |
| CSS 提取 | PageCard/FilterBar/DataTable | 减少重复 CSS |
| 异步 I/O | `aiofiles` | 消除事件循环阻塞 |
| 权限补全 | supplier 端点加 `require_permission` | 修复授权漏洞 |

### 5.2 可选升级：中度升级（方案B）
