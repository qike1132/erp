| 项目 | 内容 |
|---|---|
| 文档编号 | EQR-PLAN-001 |
| 版本 | v1.0 |
| 状态 | 待评审 → 生效 |
| 制定日期 | 2026-10-22 |
| 适用范围 | 滨发协同系统（binfa-erp）全仓：后端、前端、迁移、脚本、桌面壳、测试、文档 |

**本方案与既有文档的关系**：`AGENTS.md` 是协作契约（不可协商的约束），`docs/CODE_REVIEW_OPTIMIZATION_PLAN.md` 是一次性的问题清单，`docs/TRANSACTION_BOUNDARY_GUIDE.md`、`docs/architecture-review-*.md`、`docs/reviews/*` 是专题结论。本方案是**常设流程**：规定"谁、在什么时点、用什么标准、拿什么工具、按什么节奏审查与整改"，不重复罗列具体缺陷。

## 1. 目标与原则

### 1.1 目标

| 编号 | 目标 | 可验证的达成标志 |
|---|---|---|
| G1 | 缺陷左移：在提交与合并阶段拦住问题，而非上线后靠用户发现 | 门禁拦截率稳定在 5%–15%，上线后 P0/P1 逃逸率 < 10% |
| G2 | 质量只紧不松：存量债务可量化、可偿还，新增问题零容忍 | `scripts/gate_baseline.json` 各计数每季度只降不升 |
| G3 | 审查结论可执行、可复现、可审计 | 每条问题带文件:行号、复现方式、修复建议、责任人与期限 |
| G4 | 生产安全边际：本机即生产，任何改动不得以牺牲可回滚性换取速度 | 变更前有备份/回滚路径，破坏性操作前有明确确认 |
| G5 | 团队能力沉淀：问题模式转化为规则，规则转化为自动化 | 每季度至少 3 条高频问题从"人审"下沉为"机审" |

### 1.2 原则

1. **机器优先于人**。凡是能由脚本判定的（格式、复杂度、裸 except、N+1、密钥、依赖漏洞），一律不占用人审注意力；人审只处理"机器判不了"的权衡与设计问题。
2. **棘轮语义（ratchet）**。存量违规登记基线、不阻断；新增违规立即阻断；基线只允许下调。禁止为提高通过率而上调基线（提交钩子已对基线上调做拦截）。
3. **证据先于结论**。审查结论必须能被第三方复现：给出命令、退出码、日志片段或截图。不接受"我觉得这里有问题"。
4. **本机即生产**。无独立测试/预发环境，因此审查前置：先只读分析，再变更；破坏性操作前必须确认；代码变更后必须真实浏览器 E2E 验证。
5. **审查不是审判**。审查对象是代码与决策，不是人；每条 P0/P1 必须附"最小可行修复"，而非仅指出缺陷。

## 2. 适用范围

### 2.1 范围内（In Scope）

| 范围 | 路径 | 审查重点 |
|---|---|---|
| 后端 API 与服务 | `fastapi_app/api/`、`fastapi_app/services/`、`fastapi_app/core/`、`fastapi_app/models/`、`fastapi_app/shared_models/` | 鉴权与越权、事务边界、N+1、异常收窄、分层依赖方向 |
| 数据库迁移 | `migrations/versions/` | 单一 head、可回滚、锁表风险、数据回填幂等性 |
| 前端 | `frontend-vite/src/`（Vue 3 + TS） | 类型安全、组件规模、接口契约对齐、渲染性能、请求防抖与竞态 |
| 质量与运维脚本 | `scripts/`、`server_manager/`、`.githooks/` | 门禁自身正确性（恒失败自检）、绕过路径、误报率 |
| 测试代码 | `tests/`、`fastapi_app/tests/`、前端 `*.spec.ts` | 断言有效性（防"假绿"）、关键路径与失败路径覆盖 |
| 文档 | `docs/`、`AGENTS.md`、`.env.example`、`README` | 与代码一致性、可执行性（命令能跑通）、契约变更记录 |

### 2.2 范围外（Out of Scope）

| 项 | 理由 | 替代做法 |
|---|---|---|
| 第三方依赖源码（`node_modules/`、`site-packages/`） | 不属自研代码 | 用 `pip-audit` 与依赖锁定审查"版本与漏洞"，不审源码 |
| `deliverables/`、`.archive/`、`docs/` 下历史归档 | 历史快照，非现行真相 | 仅在被引用为决策依据时核对，不与现行代码比对 |
| 运行期数据（`backups/`、`logs/`、`evidence/`） | 不入库的运行时产物 | 审查"生成逻辑"，不审数据内容 |
| 生产环境的即时配置值 | 敏感，且以 `.env` 为准 | 审查 `.env.example` 模板完整性（`env_drift` 门禁） |
| 纯文案/视觉设计定稿 | 非工程缺陷 | 走产品验收流程 |

### 2.3 触发即审的变更类型（无论大小）

鉴权与权限判定、金额与数量计算、库存扣减、事务边界、数据库迁移、文件上传与下载路径、外部请求（SSRF/超时）、日志脱敏、`.env`/密钥相关、门禁脚本自身、NSSM 服务启停逻辑。

## 3. 审查维度与判定标准

七个维度均有"看什么 / 判定红线 / 承载工具 / 输出物"。红线项一律不低于 P1。

### 3.1 代码规范

| 项 | 内容 |
|---|---|
| 看什么 | ruff 规则集口径（`ruff.toml`）、命名、导入顺序、无用代码、BOM、编码、行宽 |
| 红线 | 新增裸 `ignore` 绕过规则；命令行 `--select/--ignore` 覆盖仓库口径；`.py` 带 UTF-8 BOM（AST 工具会静默跳过该文件） |
| 工具 | `ruff check`（pre-commit + CI）、`scripts/check_bom.py`、`scripts/quality_gate.py --only ruff` |
| 已知约束 | 全仓 `ruff-format` 因约 1000 个 `.py` 从未格式化、且存在一批"源码文本级守卫测试"（实测一次全仓 format 会打断 16 个测试）而**禁用**。因此格式审查只对**本次变更文件**做增量要求，不做全仓重排 |
| 输出物 | 违规清单（文件:行号 + 规则号）或"规范通过"结论 |

### 3.2 架构设计

| 项 | 内容 |
|---|---|
| 看什么 | 分层依赖方向（api → services → models；`core/` 为组合根，允许 import services）、事务边界归属、模块耦合与循环依赖、组合根唯一性、扩展点设计、迁移与模型一致性 |
| 红线 | service 层擅自 `commit()` 造成事务边界泄漏；新增跨层反向依赖；产生双 Alembic head；把业务逻辑写进 endpoint 层 |
| 工具 | 人工评审（架构维度主战场）+ `scripts/check_service_commit.py`、`scripts/check_alembic_heads.py`、`scripts/check_orphan_modules.py`（孤儿模块）、`scripts/audit_tx_patterns.py` |
| 判定方法 | 变更若引入新模块/新依赖方向/新事务语义，必须给出"为什么这样切"的一句话理由；写不出即视为设计未收敛，退回补充 |
| 输出物 | 架构结论（通过/带条件通过/退回），重大决策升级为 ADR 存入 `docs/` |

> **现状差距（须在 M2 补齐）**：当前无"分层依赖方向"的自动化门禁——`scripts/` 下无对应检查器，`.pre-commit-config.yaml` 也未接入。架构维度目前 100% 依赖人工，这是本方案识别出的最大结构性缺口。

### 3.3 可维护性

| 项 | 内容 |
|---|---|
| 看什么 | 函数长度、文件长度、Vue 组件规模、圈复杂度、循环变量遮蔽、重复逻辑、异常处理收窄、命名与职责单一性 |
| 红线（阈值来自 `pyproject.toml [tool.code-quality]`） | 单函数 > 80 有效行；单 `.py` > 1600 行；单 `.vue` > 400 行；圈复杂度超 `ruff.toml [lint.mccabe]` 阈值（25）；新增宽泛 `except Exception` 无 `# defensive: <理由>` 标注 |
| 工具 | `check_function_length.py`、`file_size_gate.py`、`check_vue_component_length.py`、`check_bare_except.py`、`ruff --select C901`、`ruff --select PLW2901`，全部经 `quality_gate.py` 汇总 |
| 判定方法 | 允许"存量超限"，不允许"变更使其更差"；确需保留大函数时必须在 PR 说明中写理由并在 `ruff.toml` 集中登记 |
| 输出物 | 规模/复杂度增量报告 + 拆分建议 |

### 3.4 性能

| 项 | 内容 |
|---|---|
| 看什么 | N+1 查询、缺失索引、无分页的全表扫描、循环内 IO、缓存失效策略、前端包体与首屏、列表渲染与请求竞态、防抖/节流 |
| 红线 | 循环内 `execute/scalar/scalars`；新增无 `limit` 的列表接口；同一页面重复请求未做防抖或缓存键冲突；把同步阻塞调用放进 async 路径 |
| 工具 | `scripts/check_n_plus_one.py`（基线 0，新增即红色）、`scripts/perf_benchmark.py`、`scripts/verify_perf_cache*.py`、`scripts/perf_add_indexes.py`、前端 `rollup-plugin-visualizer`、真实浏览器 E2E 计时 |
| 判定方法 | 涉及报表、库存、外包、订单等重查询模块的变更，必须给出"预期 QPS / 数据量级 / 是否命中索引"三项说明；无法说明则按 P2 退回补充 |
| 输出物 | 性能结论 + 索引/分页/缓存的具体动作项；必要时附 `EXPLAIN` 结果 |

### 3.5 安全性

| 项 | 内容 |
|---|---|
| 看什么 | 鉴权与越权（横向/纵向）、SQL 注入、路径遍历、SSRF、文件上传类型与大小限制、密钥硬编码、日志脱敏、依赖漏洞、`nosec` 压制是否经核验 |
| 红线 | 凭据入库（含 `_ops/credentials/`、`.env.production`）；未校验 `../` 的文件路径拼接；未鉴权的管理端点；新增 `# nosec` 未写明规则号与理由；`pip-audit` 豁免条目缺 `reason`/`expires` 或已过期 |
| 工具 | `bandit`（`fastapi_app/` + `utils/`）、`ruff` 的 S 规则、`scripts/scan_secrets.py`、提交钩子第 1 层（危险路径守卫）与第 2 层（密钥内容扫描）、`pip-audit` 豁免策略门禁、`scripts/check_nosec_budget.py` |
| 判定方法 | 安全发现一律按 P0/P1 处理，不设"观察期"；误报只能在当行加 `nosec`（规则号 + 理由），且受 nosec 预算约束（当前预算 80，长期目标压回 70） |
| 输出物 | 安全结论（含未修复项的风险接受签字人）+ 复现步骤 |

### 3.6 测试覆盖

| 项 | 内容 |
|---|---|
| 看什么 | 关键业务路径（订单/库存/外包/审批/权限）是否有回归测试；失败路径与边界是否覆盖；断言是否有效（是否只断言状态码不校验数据）；契约是否与前端对齐；测试是否可独立运行 |
| 红线 | 新增接口无任何测试；测试断言被弱化以换取通过；用 `--no-verify` 或 `skip` 掩盖失败；测试写生产库 |
| 工具 | `pytest`（`pytest.ini` 已配 markers：unit/integration/api/model/db/contract）、`vitest`（前端 207 个 spec）、`--cov`（`.coveragerc` 限定 `fastapi_app` + `utils`）、契约快照（`contract` marker，需 `CONTRACT_BASE_URL`）、`scripts/_selftest_contract.py` |
| 判定方法 | 覆盖率门禁当前 `COVERAGE_MIN=20`，作用是"防归零"而非质量门槛，因此**覆盖率不得作为唯一验收依据**；以"关键路径是否有测试"为主判据 |
| 执行约束 | 单文件 pytest 运行（避免全量噪音与假失败）；不使用 shell 管道（编排器输出捕获上限 256KB，历史上 stdout 2.1MB 曾导致 `exit=-999` 假失败）；日志默认 `log_cli=false` |
| 输出物 | 覆盖清单（关键路径 → 用例）+ 缺失用例动作项 |

### 3.7 文档

| 项 | 内容 |
|---|---|
| 看什么 | 契约变更是否同步文档；命令是否可复制执行；ADR 是否记录了"为什么"；`.env.example` 是否补齐新增变量；上线/回滚步骤是否可操作 |
| 红线 | 代码改了但契约/接口文档未更新；文档里的命令跑不通；新增环境变量未进 `.env.example`（`env_drift` 门禁，基线 0） |
| 工具 | `scripts/ops/check_env_drift.py`、`scripts/check_openapi_frontend_alignment.py`、前端 `check:api` / `check:routes` / `check:types`、人工核对 |
| 判定方法 | "能跑通"是唯一标准：文档中的命令必须在提交者本机实际执行过（审查时可要求贴退出码） |
| 输出物 | 文档更新点清单；缺失项按 P2 记录 |

## 4. 角色与职责（RACI）

R = 负责执行，A = 最终裁决，C = 需征询，I = 需知会。

| 活动 | 工程监督(QA) | 技术负责人 | 模块 Owner | 审查者 | 提交人 | 文档负责人 |
|---|---|---|---|---|---|---|
| 制定/修订本方案 | A/R | C | C | C | I | I |
| 提交前自检（清单 C0） | I | I | I | I | A/R | — |
| 自动门禁执行与判读 | C | I | C | I | R | I |
| 人工审查（常规变更） | C | I | R | R | I | I |
| 架构类变更审查 | C | A | R | C | R | I |
| 安全类问题定级 | A | C | R | C | R | I |
| 结论发布与归档 | A/R | I | I | C | I | C |
| 整改跟踪与逾期升级 | A/R | C | R | I | R | C |
| 复验（关闭问题） | A/R | C | R | C | I | I |
| 月度质量报告 | A/R | I | I | I | I | C |
| 季度基线收紧 | A | A/R | C | C | I | I |
| 事故复盘 | R | A | R | C | C | R |
| 文档一致性核查 | C | I | C | R | R | A/R |

### 角色卡

**工程监督（QA）— 方案 Owner**
维护本方案、主持周度审查会、判定问题等级、跟踪整改 SLA、发布月度质量报告、对"是否放行"给出结论。拥有对 P0/P1 的**定级权**与对基线的**收紧提议权**；不拥有对架构决策的最终裁决权。

**技术负责人 — 技术裁决**
裁决架构方向、事务边界、性能与安全的权衡取舍；对"带条件通过"的条件是否成立做最终判断；批准基线例外（如历史上 `service_commit` 9→12 的唯一一次上调，需附书面理由）。

**模块 Owner（后端/前端/数据/运维）**
对本模块变更的正确性与可维护性负责；提供审查所需的上下文（数据量级、调用方、影响面）；在 SLA 内完成整改；对跨模块影响主动知会相邻 Owner。

**审查者（交叉审查）**
由非本模块开发者担任，按第 7 节清单逐项过；只对"证据充分的问题"下结论；每条结论必须可复现。审查者轮值，季度校准一次（同一 PR 双人盲审比对，纠偏宽严不一）。

**提交人**
提交前完成 C0 自检；提供变更说明（改了什么/为什么/怎么验证/怎么回滚）；不得以 `--no-verify` 作为常规通过手段（非常规绕过须在当日审查会说明原因）。

**文档负责人**
维护 ADR 索引、Runbook、`.env.example` 模板；对"文档与代码不一致"发起问题单。

## 5. 审查流程

### 5.1 主流程（七步，含时限）

| 步骤 | 输入 | 动作 | 输出 | 时限 | 责任 |
|---|---|---|---|---|---|
| S1 触发与分级 | 变更清单 / 需求单 / 事故单 | 按 2.3 判定是否"触发即审"；确定审查类型（常规/架构/安全/专项） | 审查任务单（类型、范围、审查者） | 提交当日 | QA |
| S2 提交前自检 | 变更内容 | 执行清单 C0；跑本地门禁 | 自检记录（命令 + 退出码） | 提交前 | 提交人 |
| S3 自动门禁 | git 暂存内容 | 三层钩子：危险路径 → 密钥扫描 → ruff + 质量门禁（14 项基线棘轮） | 通过/拒绝 + 违规计数 | 秒级 | 钩子（机器） |
| S4 人工审查 | diff + 上下文 | 按第 7 节清单逐维度过；必要时本地复现 | 审查结论（P0/P1/P2/P3 清单） | 常规 ≤ 4 工作小时；架构类 ≤ 1 工作日 | 审查者 |
| S5 结论发布 | 审查结论 | 定级、定 SLA、指定责任人；架构类须技术负责人签字 | 结论单（附模板见附录 B1） | 审查完成后当日 | QA |
| S6 整改 | 结论单 | 按级修复；修复后附复现证据 | 修复提交 + 证据 | 按第 9 节 SLA | 提交人/Owner |
| S7 复验与归档 | 修复提交 | 复跑门禁 + 针对该问题的定向验证（必要时真实浏览器 E2E） | 关闭记录；未通过则退回 S6 | 1 工作日内 | QA + 审查者 |

### 5.2 四类审查通道

| 通道 | 适用 | 流程裁剪 | 产出 |
|---|---|---|---|
| **提交级（每次提交）** | 所有变更 | S2 → S3，机器判定，人不介入 | 通过/拒绝 |
| **迭代级（每周）** | 本周合并的功能与修复 | S1 → S4（抽样深审 2–3 个变更）→ S5 → S7 | 周度审查纪要 |
| **专项级（每两周）** | 性能 / 安全 / 依赖 / 测试有效性轮转 | 全量扫描 + 定向深挖 + 基线巡检 | 专项报告（如 `docs/reviews/2026-10-22-performance-and-bug-review.md`） |
| **发布级（上线前）** | 生产变更 | 清单 C8 全项 + 回滚演练 + 数据备份确认 | 放行/阻断结论（技术负责人签字） |

### 5.3 阻断与升级规则

- 门禁失败 → 直接拒绝提交，不进入人工审查。工具自身故障（如 ruff 退出码 2）**视同失败**，不得当作"跳过"。
- 人工审查发现 P0 → 立即停止合并/发布，已在生产的按事故流程处理（检测 → 分级 → 缓解 → 修复 → 复盘）。
- 审查结论分歧 → QA 定级、技术负责人裁决；仍不一致则记录双方理由并按"更严"执行。
- 逾期未整改 → 自动升级一级（见 9.3）。

## 7. 检查清单

清单是审查的**最小完备集**：不做"逐条打勾走过场"，只要求"每条都能回答是/否/不适用"，"否"必须转成问题单。

### C0 提交前自检（提交人，8 项）

- [ ] 变更目的能用一句话说明（改了什么、为什么）
- [ ] 本地已跑 `python scripts/quality_gate.py` 且退出码 0
- [ ] 涉及前端：`npm run type-check` 与相关 `vitest` 单文件通过
- [ ] 涉及后端接口：对应 pytest 单文件通过（单文件，不全量）
- [ ] 无新增密钥、无 `.env` 实值入库、无 `nosec` 新增
- [ ] 影响面已评估（被哪些页面/接口/定时任务调用）
- [ ] 回滚方式明确（回退提交 / 迁移降级 / 配置还原）
- [ ] 文档与 `.env.example` 已同步

### C1 正确性（通用）

- [ ] 边界条件：空集合、单元素、超大值、零值、负数、时区（naive/aware）
- [ ] 失败路径：外部依赖不可用、超时、部分成功、重试是否幂等
- [ ] 并发：是否有竞态、重复提交、库存超扣
- [ ] 类型：`None` 传播、`Optional` 未判空、前端 `any` 逃逸
- [ ] 数据一致性：事务边界内是否包含所有写操作

### C2 安全（8 项）

- [ ] 每个新增/修改端点都有明确鉴权依赖，且做了数据归属校验（防横向越权）
- [ ] SQL 一律参数化（无字符串拼接、无 f-string 进 SQL）
- [ ] 文件路径与文件名经过规范化与白名单校验（防 `../` 遍历）
- [ ] 上传限制类型 + 大小（单文件 5MB 口径），存储路径不可控
- [ ] 外部请求有超时、有目标域白名单（防 SSRF）
- [ ] 日志与异常响应不含密钥、口令、令牌、完整身份证/手机号
- [ ] 新增依赖无已知漏洞（`pip-audit` 干净），且锁定版本
- [ ] 新增 `# nosec` 已核验并写明规则号 + 理由（受预算约束）

### C3 性能

- [ ] 无循环内查询（N+1），关联数据用 `selectinload/joinedload` 或批量 IN
- [ ] 列表接口有分页且有上限；排序字段有索引
- [ ] 重查询（报表/库存/外包）已说明数据量级与预期耗时
- [ ] 前端无重复请求、无竞态覆盖、搜索有防抖、缓存键含全部筛选维度
- [ ] 大列表使用虚拟滚动或分页渲染；无全量 `watch` 深比较

### C4 架构

- [ ] 依赖方向正确（api → services → models），未在 endpoint 写业务逻辑
- [ ] service 层不自行 `commit()`（flush-only，事务交给 `get_async_db`/`db_transaction`；确需独立事务按 `docs/TRANSACTION_BOUNDARY_GUIDE.md` 标注 `# manual-tx: <理由>`）
- [ ] 迁移单一 head、有降级路径、大表变更评估锁表影响
- [ ] 无新增孤儿模块（新模块必须被 `api/v1/router.py` 或明确的调用方引用）
- [ ] 新抽象有存在理由（避免为单点需求引入框架级复杂度）

### C5 可维护性

- [ ] 函数 ≤ 80 有效行、文件 ≤ 1600 行、组件 ≤ 400 行、复杂度未超阈值
- [ ] 异常已收窄到具体类型；兜底异常有 `# defensive: <理由>`
- [ ] 命名表达意图（无 `data`、`tmp`、`obj2`、`handle2`）
- [ ] 无复制粘贴式重复（≥3 处相似逻辑应抽取）
- [ ] 无死代码、无被注释掉的旧实现、无遗留 TODO（除已登记的技术债）

### C6 测试

- [ ] 关键路径至少一条端到端断言（不只断言状态码）
- [ ] 失败路径至少一条（权限不足、参数非法、资源不存在）
- [ ] ORM 关系访问在 `lazy='raise'` 下不会炸（用 `sa_inspect().unloaded` 验证加载状态）
- [ ] 测试可独立运行（单文件通过），不依赖执行顺序
- [ ] 前端契约类型与后端 OpenAPI 一致（`check:types` / `check:api`）

### C7 文档

- [ ] 接口契约变更已更新 OpenAPI/前端类型
- [ ] 新增环境变量已进 `.env.example`（占位值）
- [ ] 运维相关变更已更新 Runbook（启停、回滚、排查）
- [ ] 重大决策已写 ADR（背景/方案对比/权衡/后果）

### C8 上线前（发布级）

- [ ] 全量门禁绿（提交钩子 + CI 全步骤）
- [ ] 数据已备份且验证可读（备份文件存在且大小合理）
- [ ] 迁移在只读副本或本地 dry-run 验证过
- [ ] 回滚步骤可在 10 分钟内完成，且已确认执行人
- [ ] 关键页面真实浏览器 E2E 通过（非 curl 代替）
- [ ] 监控与日志级别就绪，异常可定位
- [ ] 利益相关方已知会上线窗口

## 8. 工具链与门禁矩阵

### 8.1 分层防线

| 防线 | 位置 | 内容 | 失败后果 |
|---|---|---|---|
| L1 编辑器/本地 | 开发者本机 | ruff（保存时）、`vue-tsc`、单文件 pytest | 自觉修正 |
| L2 提交钩子（`.githooks/pre-commit`，三层） | `git commit` | ① 危险路径守卫 ② 密钥内容扫描 ③ 既有门禁（ruff + `quality_gate.py` 14 项 + 基线上调拦截） | 拒绝提交 |
| L3 CI | push / PR | ruff、mypy（渐进白名单）、pytest + `--cov`、bandit、pip-audit、契约快照、前端 lint/type-check/vitest | 阻断合并 |
| L4 人工审查 | 合并前 | 第 7 节清单 | 退回或带条件通过 |

### 8.2 质量门禁清单与当前基线

`scripts/quality_gate.py` 汇总 14 项门禁，基线存于 `scripts/gate_baseline.json`：存量不阻断，**超过基线即失败**，低于基线会提示收紧。

| # | 门禁 key | 内容 | 当前基线 | 目标（12 个月） |
|---|---|---|---|---|
| 1 | `n_plus_one` | 循环内 execute/scalar/scalars | 0 | 0（保持） |
| 2 | `bare_except` | 裸 except / 宽泛 Exception | 0 | 0（保持） |
| 3 | `function_length` | 后端超长函数（>80 有效行） | 30 | ≤ 12 |
| 4 | `vue_component_length` | 巨型 Vue 组件（>400 行） | 6 | 0 |
| 5 | `service_commit` | service 层手动 commit() | 10 | ≤ 4 |
| 6 | `bom` | UTF-8 BOM 开头 .py | 0 | 0（保持） |
| 7 | `alembic_heads` | 迁移单 head / root 数不增 | 0 | 0（保持） |
| 8 | `env_drift` | 代码引用 vs `.env.example` | 0 | 0（保持） |
| 9 | `ruff` | scripts/ + server_manager/ 违规 | 18 | 0 |
| 10 | `complexity` | C901 圈复杂度（阈值 25） | 4 | 0 |
| 11 | `loop_shadow` | PLW2901 循环变量遮蔽 | 12 | 0 |
| 12 | `pip_audit` | 依赖漏洞豁免策略 | 0 | 0（保持） |
| 13 | `nosec_budget` | `nosec` 压制预算 | 80 | ≤ 70 |
| 14 | `bandit` | 安全发现（fastapi_app + utils） | 23 | ≤ 8 |

**门禁自身可信度要求**：
- 违规计数只能来自机器可读来源（`--json`、退出码、ruff JSON），拿不到计数按"环境异常"保守失败，**不得记 0**。
- 每个门禁必须通过 `--self-test`（在临时目录制造真实违规、断言失败、移除后断言通过），证明它真的会红。
- 门禁脚本变更（`scripts/check_*.py`、`quality_gate.py`、`.githooks/*`、`gate_baseline.json`）本身属于"触发即审"变更，需双人复核——门禁被改坏是最隐蔽的质量事故。

## 9. 问题分级与整改跟进

### 9.1 分级定义

| 级别 | 定义 | 典型示例 | 响应时限 | 修复 SLA | 放行影响 |
|---|---|---|---|---|---|
| **P0 阻断** | 数据损坏/丢失、资金或库存算错、鉴权绕过、凭据泄露、生产不可用 | 未鉴权删除端点、`../` 路径遍历、库存超扣、密钥入库 | 立即 | 24 小时内（含验证） | 立即停线；已在生产的按事故流程 |
| **P1 严重** | 核心流程错误但有临时规避；明显安全弱项；性能劣化到影响使用 | 事务边界错误导致部分写入、列表无分页致超时、SSRF 无白名单 | 4 小时内确认 | 3 个工作日 | 阻断发布；特殊情况需技术负责人书面风险接受 |
| **P2 一般** | 局部功能缺陷、可维护性明显劣化、缺少必要测试 | 新增接口无测试、组件超 400 行、异常过宽 | 1 个工作日 | 当前迭代内（≤2 周） | 可发布，进迭代待办 |
| **P3 建议** | 优化项、风格建议、文档完善 | 命名可读性、注释补充、重复逻辑抽取 | 3 个工作日 | Backlog，季度评估 | 不影响发布 |

**定级三问**（QA 使用，避免主观）：会不会错数据或漏权限？会不会让用户在正常使用中失败？会不会让下次修改更容易出错？三个"会"→ P0/P1；两个 → P1/P2；一个 → P2/P3。

### 9.2 问题单必填字段

`编号 | 级别 | 维度 | 位置（文件:行号）| 现象 | 复现方式（命令/步骤/输入）| 根因 | 建议修复 | 责任人 | 期限 | 状态 | 复验证据`

缺任一项的问题单不进入跟踪队列（退回补充），避免"无法验证的结论"堆积。

这条规则的实际意义：审查最贵的成本不是发现问题，而是**问题单无法被执行**——没有复现方式，责任人只能猜；没有根因，修复只能打补丁；没有复验证据，关闭就是口头承诺。

### 9.3 整改跟进机制

1. **登记**：结论单发布当日进入问题台账（建议放 `docs/reviews/` 同目录的台账文件或项目管理系统，字段同上）。
2. **跟踪**：周会过"P0/P1 未闭环 + P2 逾期"两项；月报过全量与趋势。
3. **自动升级**：逾期未整改自动升一级（P2→P1→P0），升级后由技术负责人介入；连续两次升级的问题进入季度架构评审议题。
4. **复验**：修复必须附"复现原问题的命令 + 现在的输出"，QA 复跑通过才允许关闭；仅"代码看起来改了"不予关闭。
5. **风险接受**：确实无法按期修复的 P1，须由技术负责人签署风险接受（写明影响面、缓解措施、最终期限），并在月报公示；P0 不接受风险接受。
6. **基线联动**：修复使某门禁计数下降后，同一次提交内执行 `--update-baseline` 收紧基线，防止数字回弹（基线上调会被钩子拦截）。
7. **复发标记**：同类问题 90 天内重复出现，标记为"复发"，必须补自动化规则或清单条目，不能只再修一次。

## 10. 度量指标

### 10.1 核心指标

| 指标 | 定义 / 公式 | 目标 | 数据来源 | 频率 |
|---|---|---|---|---|
| 门禁拦截率 | 被钩子/CI 拒绝的提交数 ÷ 总提交数 | 5%–15%（过高说明本地不自检，过低说明门禁失效） | 钩子日志 + CI 记录 | 每周 |
| 缺陷逃逸率 | 上线后发现的 P0/P1 ÷（审查发现 + 上线后发现） | < 10% | 问题台账 | 每月 |
| 审查发现密度 | 每千行变更发现的问题数（按维度拆分） | 基线化后观察趋势，不设绝对值目标 | 结论单 + diff 行数 | 每月 |
| 首次通过率 | 一次审查即通过（无 P0/P1）的变更占比 | > 70% | 结论单 | 每月 |
| 审查周期 | 提交到结论发布的时长（P50/P90） | P90 ≤ 1 个工作日 | 任务单时间戳 | 每月 |
| 整改及时率 | SLA 内关闭数 ÷ 应关闭数 | ≥ 95% | 问题台账 | 每月 |
| 基线收紧幅度 | 本季度基线合计 ÷ 上季度基线合计 | 每季度下降 ≥ 20% | `gate_baseline.json` 历史 | 每季度 |
| 覆盖率 | `coverage.xml` line-rate（`fastapi_app` + `utils`） | 季度 +5pp，12 个月到 35% | CI 覆盖率产物 | 每月 |
| 复发率 | 90 天内重复出现的同类问题 ÷ 总问题 | < 15% | 问题台账标签 | 每季度 |
| 关键路径测试覆盖 | 关键业务路径中有自动化回归的比例 | 100% | 覆盖清单 | 每季度 |
| 平均恢复时间（MTTR） | 事故发现到恢复的时长 | P0 ≤ 2h，P1 ≤ 8h | 事故复盘 | 每月 |

### 10.2 反指标（防止指标被"刷"）

| 反指标 | 风险 | 监控方式 |
|---|---|---|
| 审查批注总数 | 为凑"发现密度"刷低价值评论 | 抽样评估批注的 P2 以上占比 |
| 单 PR 往返轮次 | 形式化卡点、故意拖延 | 轮次 > 3 的变更做抽查，区分"真复杂"与"审查低效" |
| 门禁 `--no-verify` 次数 | 绕过门禁 | 统计并公示，非常规绕过须在周会说明 |
| 覆盖率单点冲刺 | 写无断言测试刷行覆盖 | 抽查新增测试的断言强度；覆盖率不单独作为验收依据 |
| 基线上调次数 | 用放松门禁换绿灯 | 架构上已由钩子拦截；任何上调需书面理由并记入月报 |

**指标使用纪律**：指标用于发现问题，不用于考核个人。将指标与个人绩效绑定会直接导致数据失真（瞒报、拆分提交、弱化断言），这是本方案明确禁止的做法。

## 11. 持续改进

### 11.1 月度复盘（三问）

1. 本月哪个维度的问题最多？是"人没看住"还是"机器没覆盖"？
2. 有没有本可机器拦截却靠人发现的重复问题？（→ 转成规则）
3. SLA 未达成的根因是"没时间"还是"没人会"？（→ 排期或培训）

### 11.2 季度规则评审

对每条门禁与清单条目做四分类：
- **保留**：仍有效，继续执行。
- **加严**：误报率低但阈值偏松（如复杂度 25 → 20），上调严格度。
- **下沉**：人审高频项 → 自动化（如"接口无鉴权依赖"可用 AST 检查）。
- **删除**：长期零命中且无风险覆盖价值的条目（避免清单膨胀导致走过场）。

评审结论必须落到提交：要么改 `pyproject.toml` / `ruff.toml` / 检查脚本 / 基线，要么改本方案文本。**只开会不改文件等于没评审。**

### 11.3 基线收紧流程（标准动作）

```bash
# 1. 修复存量，使计数下降
python scripts/quality_gate.py --report          # 确认当前计数
# 2. 重建基线（只允许下降；上调会被提交钩子拒绝）
python scripts/quality_gate.py --update-baseline
# 3. 与修复同批提交，附"计数从 X 降至 Y"的说明
git add scripts/gate_baseline.json <修复文件> && git commit
```

### 11.4 知识沉淀路径

```
单次问题（问题单）
   → 同类问题 ≥3 次（打标签聚合）
   → 写入检查清单条目（本方案第 7 节）
   → 若能机器判定，写成 scripts/check_*.py 并接入 quality_gate.py（带 --self-test）
   → 基线登记存量，新增即拦截
```

这条链路是本方案的核心：**问题不重复讨论第二次**。每一个重复出现的问题，都是清单或门禁的缺口，而不是"这次没注意"。

### 11.5 审查者培养

- 新审查者先跟随 2 次审查（只观察、写独立结论，与主审比对差异）。
- 季度校准：同一变更双人盲审，比对结论差异，偏差大的维度做专项讲解。
- 审查者必须能独立复现问题（跑命令、看日志），不接受"凭经验判断"作为唯一依据。

### 11.6 里程碑

| 阶段 | 时间 | 交付 |
|---|---|---|
| M1 落地 | 第 1 个月 | 本方案生效；C0 清单进入日常；问题单台账建立；GAP-4/7 关闭；覆盖率 20%→25% |
| M2 补自动化 | 第 2–3 个月 | GAP-1/6 关闭（分层门禁 + 文档校验）；基线下降 20%；覆盖率到 30%；首份季度架构审查报告 |
| M3 稳态 | 第 4–6 个月 | GAP-3 关闭（守卫测试抗格式化 + 全仓 format）；覆盖率到 35%；专项审查全部轮转一轮；月度指标连续 3 个月达标 |
| M4 优化 | 第 7–12 个月 | 关键路径测试覆盖 100%；基线合计降至当前 40% 以下；P0 逃逸率连续两季度为 0 |

| 术语 | 含义 |
|---|---|
| 基线棘轮（ratchet） | 存量违规登记为基线不阻断、新增即失败、基线只降不升的机制 |
