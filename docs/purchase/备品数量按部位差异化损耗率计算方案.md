## 0. 问题定位

### 0.1 现象

`/beile-order` 的「生产数量 = 订单数量 + 备品数量」，其中备品取自采购单快照，而备品只由**订单级单一损耗率**算出：

```
备品 = ceil(订单数量 × 订单级损耗率‰)
```

不同部位（一行布料 = 一个部位）损耗不同——如对条/对格的头布 30‰、素色身布 10‰——单一率必然不是高估就是低估，于是「总订单的备品数量计算不准确」。

### 0.2 根因（代码事实）

| # | 事实 | 来源 | 影响 |
| --- | --- | --- | --- |

### 0.3 结论

问题的根在**备品来源**（订单级单率），**不在 `/beile-order` 展示层**——该页公式正确，读的是快照。修复面收敛为：

> 新增一个「从部位率派生备品」的重算函数，挂到 3 个写入点。**零数据库迁移、零前端改动（P0）、零读路径性能影响。**

## 1. 计算口径与公式

### 1.1 术语与载体

| 术语 | 含义 | 系统载体 |
| --- | --- | --- |
| 部位 | 产品的用料部位 | 采购明细行（**一行布料 = 一个部位**） |
| 部位损耗率 rᵢ | 该部位的生产损耗（千分之几） | `purchase_order_item.loss_rate` |
| 订单级率 | 部位率缺失时的回退基线 | `purchase_order.spare_rate` |
| 备品 | 为覆盖生产损耗而多生产的整件数 | `purchase_order.spare_quantity` / `purchase_order_sku.spare_qty` |
| 生产数量 | 订单数量 + 备品数量 | 前端派生展示，不落库 |

**数据模型现状**：BOM 物料表（`product_fabric` / `product_material` / `product_accessory`）**没有部位字段**，物料行只有 `role_id`（BOM 角色作用域）。故「部位」不以主数据形式存在，而是**以后勤明细行的粒度承载**——这与「一行布料 = 一个部位」的口径一致，也是本方案不需要新增数据维度的根本原因。

### 1.2 推荐公式（方案 A：瓶颈部位决定）

```
① 部位生效率   r_eff(SKU) = max{ 该 SKU 各部位行的 loss_rate }
                            （行率为 NULL → 回退该单 order.spare_rate）

② SKU 备品     spare(SKU)  = ceil( N_SKU × r_eff(SKU) / 1000 )

③ 采购单备品   spare(PO)   = Σ_SKU spare(SKU)
```

**取整**：`math.ceil`，与 `calc_spare_quantity`（`purchase_utils.py:74`）逐字一致。
**多 SKU**：逐 SKU 独立 ceil 后求和，与 `/beile-order` 既有的「按产品名 MAX 再求和」口径同源（`beile.py:253`），避免「先求和再 ceil」的口径分裂。

**业务解释（可直接向工厂/客户解释）**：备品是整件；生产 N+S 件时各部位同时投料，能否凑齐整件由**最难做的部位**决定。其他部位损耗更低，备品件里的用量天然富余（其布料已由各自行的 `loss_rate` 加放覆盖）。

**与现状的关系**：今天一个谨慎的用户被迫把唯一那个率设成最高的部位值（否则头布不够）。方案 A 产出与之**数值相同**的备品，但布料侧不再为低损耗部位多买。

### 1.3 候选方案对比

以「订单 1000 件，头布 30‰、身布 10‰」为例：

| | 公式 | 本例备品 | 全行同率 R 时 | 4 部位各 15‰ |
| --- | --- | --- | --- | --- |
| **A 瓶颈决定（推荐）** | `ceil(N × max(rᵢ)/1000)` | **30 件** | `= ceil(N×R/1000)` → **与现行为一致** | 15 件 |
| B 折件求和 | `Σᵢ ceil(N × rᵢ/1000)` | 40 件 | k×R → **备品跳部位数倍** | 60 件 |
| C 用量加权 | `ceil(N × Σ(uᵢrᵢ)/Σuᵢ / 1000)` | 14 件 | `= 现行为` | 15 件 |

- **B（求和）**：概率模型（各部位独立损坏、任一坏即废一件，废品率 ≈ Σrᵢ）成立，但①**迁移破坏**——统一率用户在切到逐行后，即使不改任何值，备品也会瞬间变成部位数倍，用户第一反应是「算错了」；②**结构性偏高**，备品随部位数线性膨胀（6-8 部位 × 15‰ = 9-12%），远超毛绒行业 2-5% 惯例，多备的每件都要吃布料、占产能。
- **C（加权）**：与现状兼容，但**讲不出业务故事**（无法解释「为什么用量大的部位对备品影响更大」），且需把 BOM 单件用量引入计算链路，复杂度换不到表达力。
- **A（推荐）**：兼容（全行同率 ⇒ 与现行为逐字一致）、行业对齐（单部位 5-30‰ ⇒ 备品 0.5-3%）、故事清晰、计算只依赖已落库字段。

### 1.4 兼容性证明（上线无跳变）

| 上线前状态 | 上线后 |
| --- | --- |
| 单 SKU，所有行率 = R | `max = R` ⇒ `ceil(N×R/1000)`，**逐字一致** |
| 单 SKU，行全 NULL 且订单级 = R | NULL 行回退 R ⇒ 同上 |
| 单 SKU，行全 NULL 且订单级 NULL | 备品 0，与今天一致 |
| 多 SKU，各行率互不相同 | 备品**变小或不变**（从「受最高率支配」变为「各 SKU 按自身最高率」），方向正确且可解释 |

## 2. 实施步骤

### 2.1 数据结构调整：**零迁移**

| 需要的能力 | 现有载体 | 结论 |
| --- | --- | --- |
| 部位级损耗率 | `purchase_order_item.loss_rate`（迁移 053） | 已具备 |
| 逐 SKU 备品 | `purchase_order_sku.spare_qty` / `spare_rate`（迁移 047） | 已具备 |
| 订单级回退率 | `purchase_order.spare_rate` | 已具备 |

唯一**语义更新**（非结构变更）：`purchase_order_sku.spare_rate` 由「统一率」变为「该 SKU 生效率（= 其部位率 max）」。

**该变更零风险**：经全仓核查，`purchase_order_sku.spare_rate` 目前**无任何读路径消费**——`beile.py:246` 把它读进内存视图后未被使用（`_rollup_sku_rows` / `_inject_per_sku_fields` 只取 `order_qty` / `spare_qty`），`/beile-order` 展示的率来自**订单级** `purchase_order.spare_rate`（`beile.py:332`）。故重定义其语义不会影响任何现有行为。

可选补一条仅改列 COMMENT 的迁移；**建议不做**，避免触碰单 head 迁移链。

### 2.2 后端

**新增函数 1：`resolve_sku_effective_rate(db, po, skus, items)`** —— SKU → 部位行映射

```python
# 复用生成路径的展开口径（含填充类 name_suffix、默认单位），
# 保证「生成时的行」与「重算时的行」同名同键，避免两套命名规则匹配不上
bom_keys = expand_bom_keys(product_id)        # {(material_name, specification, unit)}，全作用域
matched  = [it for it in items if (it.material_name, it.specification or '', it.unit or '') in bom_keys]
rates    = [it.loss_rate if it.loss_rate is not None else order_rate for it in matched]
return max([r for r in rates if r is not None], default=0.0)
```

- 匹配键直接复用 `purchase_order_generate.py:133` `_material_row` 的赋值口径（F7），**不引入模糊匹配**；
- SKU → 产品：优先 `purchase_order_sku.product_barcode`（精确），回退 `product_name`；
- 任一环节解析失败 → **降级**为「该采购单全部明细的 max」，记 `logger.warning`，**绝不抛错**（沿用本模块既有降级风格，参见 `beile.py:232`）。

**新增函数 2：`recompute_po_spare_from_item_rates(db, po_ids)`** —— 批量重算

```
批量取 POs / items / skus（各一条 IN 查询，无 N+1）
  → 逐 SKU 按公式 ①②
  → 写 sku.spare_qty、sku.spare_rate
  → order.spare_quantity = Σ_SKU spare(SKU)
  → 失效 /beile-order 派生缓存
```

**三个挂载点**：

| # | 位置 | 现状 | 改为 |
| --- | --- | --- | --- |
| 1 | `purchase_order_crud.py:466`（行率写入后） | 只写 `it.loss_rate`，**不重算备品** | 追加 `recompute` ← **修缺陷的主挂载点** |
| 2 | `purchase_order_crud.py:473`（`_write_spare_rate_to_orders`） | `_apply_spare_rate` 订单级 ceil + `resync_po_sku_spare` 同率覆盖 | 先写 `order.spare_rate`（**仅作 NULL 行回退基线**），再 `recompute` |
| 3 | `purchase_order_crud.py:344`（complete）、`:398`（batch complete） | 同 2 | 同 2 |

挂载点 1 保证「改部位率 → 备品立即变准」；2 / 3 保证统一率与完成下单路径不会被旧的同率覆盖逻辑改写回去。

**契约**：`save_factory_summary_edits` 的请求体不变（`edits[].loss_rate` 已存在），响应不变；`factory-summary` 读接口**不变**。

### 2.3 前端

**P0：不改任何前端代码。** 逐行率输入、防抖、按行串行化（`fabricDrainPromises`，`useSummaryModal.ts:717`）均已就绪；备品由后端重算，`/beile-order` 自动反映。

## 5. 性能评估

| 维度 | 结论 |
| --- | --- |
| **读路径（最关键）** | **零变化**。`/beile-order` 列表/详情读的是已存快照 + 既有缓存，本方案**不新增任何读查询** ⇒ 列表页响应时间不变 |
| 写路径触发时机 | 仅「用户改率」（300ms 防抖 + 按行串行化，已在途合并）与「完成下单」 |
| 单次重算开销 | 最多 4 条定点批量查询（items / skus / products / BOM，均按 `IN`）+ 内存 O(行数)。单张采购单 10–50 行 ⇒ 毫秒级；相对现有保存路径增量 < 20% |
| 多单批量（改统一率） | 查询按批合并为 4 条 `IN`，**非 4N**，无 N+1（沿用本模块既有批量预取写法） |
| 索引 | 无需新增：`idx_purchase_order_sku_po`、`idx_purchase_order_item_order`、`idx_purchase_order_sku_source` 已覆盖 |
| 缓存失效 | 重算后需失效 `/beile-order` 派生缓存（与现有采购单写路径同一处，不新增失效面） |
| 部署 | 无迁移 ⇒ 不增加启动时长；回滚只需回退代码 |

## 6. 分期、风险与回滚

| 阶段 | 范围 | 风险 |
| --- | --- | --- |
| **P0 止血** | 后端 `recompute` + 公式 A + 全部降级链 + 单测。**零迁移、零 UI** | 低；代码级回滚，无数据回滚需求 |
| **P1 可观测** | 弹窗「预计备品合计」只读展示（先出 HTML 对比稿）；`/beile-order` 率提示改读 SKU 生效率 | 低 |
| **P2 可选** | ① SKU → 明细行映射快照表（抗 BOM 变更）；② 「备品计入布料」联动（F10 旧账） | 中 |

**主要风险：BOM 反查是「当前 BOM × 历史单据」。** 采购单生成后若 BOM 改名/删行，重算可能少匹配若干行 ⇒ 已由「降级为订单级 max + 用例 8/9 覆盖」兜住；若业务要求 BOM 变更后仍逐 SKU 稳定，升级到 P2①（生成时快照映射，需新表 + 生成路径改动）。

**明确不在本次范围**：备品件自身的布料未计入采购量（各行加放基数为订单量 N 而非生产量 N+S）。这是《备品率与材料损耗率拆分设计方案.md》§3.2 P1 联动从未实施的旧账，与本方案正交，需单独评估——**本方案不会让它变得更糟**（备品数量只减不增或不变）。
