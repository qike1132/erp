# 代码评审标准（Code Review Standard）

> 定位：`AGENTS.md` §4 第 4 条「新眼睛评审」只规定了**要审**；本文规定**审什么、怎么判、什么算过**。
> 流程与工具见 [code-review-process.md](code-review-process.md)；五条铁律的展开见 [verification-and-review.md](verification-and-review.md)。
>
> **一条前提**：格式、长度、复杂度、裸 except、N+1、BOM、迁移形状、env 漂移、ruff、依赖漏洞、
> nosec 预算、bandit、密钥、孤儿模块、文件大小、前端类型/构建/对齐、pytest/覆盖率——这些**机器已经拦了**。
> 评审不重复机器，只负责机器判不了的四类：**语义正确性、契约一致性、风险与影响面、测试是否真实**。

## 0. 适用范围

| 改动 | 评审强度 |
|---|---|
| 业务代码（`fastapi_app/`、`frontend-vite/src/`、`migrations/`、`server_manager/`） | **全量评审**（本文全部条款） |
| 配置/运维（`.env*`、`config/`、`deploy/`、`.githooks/`、`.github/workflows/`） | 全量评审 + 回滚演练证据 |
| 测试代码 | 全量评审（重点：测试是否真会红） |
| 纯文档（`docs/`、`*.md`，无可执行配置） | 免审，但密钥扫描仍跑 |
| 依赖升级（`requirements/`、`package.json`/`package-lock.json`） | 降级审：lock diff + `pip-audit`/`npm audit` + 上游变更日志 |
| 回滚到已知良好 commit | 免审；提交信息必须写被回滚的 commit 与原因 |
| 纯格式化/重命名（无逻辑改动） | 降级审；**必须单独提交**，不得与逻辑改动混在一起 |

## 1. 结论只有四种

| 结论 | 条件 | 动作 |
|---|---|---|
| **通过** | 零 Blocker / High / Medium；Low/Nit 可留 | 合并 |
| **有条件通过** | 仅 Low/Nit；或 Medium 已获 owner 同意延期并建了 issue | 合并；遗留项必须有 issue 与期限 |
| **打回** | ≥1 High，或 ≥1 未获同意延期的 Medium | 修复后复审 |
| **阻断** | ≥1 Blocker | 禁止合并，与其他项无关 |

**「零发现」不是合格评审。** 评审者必须能说出「我重点看了哪三处、为什么它们安全」；
说不出 = 视为未评审（沿用 `verification-and-review.md` §4）。同理，**「LGTM」「看起来没问题」不算结论**。

## 2. 缺陷分级（判定标准）

| 级别 | 定义 | 判定问句 | 处置 |
|---|---|---|---|
| `[B]` Blocker | 可致生产不可用、数据错误、凭据泄露，或**无法在 5 分钟内回滚** | 合并后最坏情况是什么？回滚路径是什么？ | 禁止合并 |
| `[H]` High | 在真实用户路径上产生错误结果、破坏前后端契约、突破安全边界，但影响可控 | 哪个操作会触发？触发后是数据错还是页面错？ | 当版必修 |
| `[M]` Medium | 不立即出错，但显著提高故障概率或维护成本（事务边界错、异常被吞、无观测、性能退化 >30%、缺回归测试） | 半年后别人改这里会不会踩？ | 当版修；确需延期须 owner 同意并建 issue（结论转「有条件通过」） |
| `[L]` Low | 可读性、重复、命名、注释缺失，不影响行为 | 改不改都不影响正确性？ | 可后续 |
| `[N]` Nit | 个人偏好，**必须显式标注「可不改」** | —— | 不阻断 |

本仓真实实例（用于校准，不是假设）：

- `[B]` 2026-10-14 生产后端加载了非 main 分支源码 → 前端新、后端旧，订单号整列空白。
- `[B]` v5.40 删除 `_start_redis` → 「启动服务」100% 崩溃；停机序用字面逆序 → broker 自锁。
- `[B]` `prod_runner` 的「假成功」：探测失败仍置 `running`，Nginx 从未启动而文件声称正常。
- `[H]` 备份删除接口未校验 `../` → 可删任意文件。
- `[H]` 恒真的镜像断言测试（期望值由被测代码自己算出）——测试永远绿，等于没有防线。
- `[M]` `except Exception` 吞掉探测异常，故障表现为「健康检查全失败」而非真实原因。
- `[M]` 生产环境后端让出 gzip、Nginx 又没起 → 全站未压缩（86% 流量浪费）。

**分级纪律：**

1. 级别由**影响**决定，不由改动行数决定——一行改动也可以是 Blocker。
2. 每条评论**只能有一个级别**，写在开头：`[H] 这里的权限过滤漏了越权条件`。
3. 不确定时按高一级处理，但必须写明「我不确定的前提是什么」。
4. 禁止无判定标准的评论：「建议优化」「可以更好」「不符合最佳实践」——必须写**什么条件下会错/慢/泄露**。
5. 风格偏好不得标为 High；`[N]` 不得超过本轮评论的 1/3，否则视为用 nit 淹没真问题。

## 3. 必审维度

### 3.1 通用四问（每个 diff 都问）

| # | 维度 | 具体问句 |
|---|---|---|
| 1 | **正确性** | 空/0/负数/超长/并发/重复提交会怎样？时区？金额精度（`Decimal` 还是 `float`，四舍五入在哪一层）？查询是否漏了 `user_id`/角色/软删除条件？（本仓无多租户，越权过滤=用户与角色维度） |
| 2 | **契约** | 前后端字段是否同源（`@/types`）？错误码/HTTP 状态变了吗？分页/排序默认值变了吗？旧客户端还能用吗？ |
| 3 | **失败路径** | 异常被吞了吗？失败会回滚吗？重试幂等吗？超时有界吗？日志能否定位（业务主键/trace_id）且不含凭据？ |
| 4 | **影响面** | 还有谁调用（逐个 grep 调用点，别用前缀一把梭）？存量数据要不要回填？开关/默认值变化对生产意味着什么？ |

### 3.2 按改动类型路由（命中即查，逐条可判定）

**后端 API 端点**（`fastapi_app/api/`）

- [ ] 新端点是否挂了权限依赖（`Depends(require_*permission)`）？默认是拒绝还是放行？
- [ ] 是否绕开 service 直接写 SQL / 直接 `db.commit()`？
- [ ] 响应模型是否漏字段、是否把内部字段（密码哈希、内部备注）带出去？
- [ ] 列表接口是否有分页上限？导出接口是否有行数上限？
- [ ] 参数校验：路径/查询参数的类型、范围、`Literal` 枚举是否收窄？
- [ ] 业务异常是否映射成 4xx，而不是一律 500？

**service / 数据库**（`fastapi_app/services/`）

- [ ] 事务边界：service 只 `flush`，提交交给 `get_async_db` / `db_transaction`；独立事务是否有 `# manual-tx: <理由>`？
- [ ] 并发：是否需要行锁/`FOR UPDATE`/advisory lock/乐观锁版本号？两个请求同时到达会怎样？
- [ ] 幂等：重复提交、重试、消息重投会不会产生第二条记录/重复扣减？
- [ ] 批量：循环里查库（N+1）是否改成 `selectinload` 或 `IN` 分批？`IN` 列表有没有上限？
- [ ] 精度：金额/数量是否全程 `Decimal`？`float()` 是否混入金额计算？
- [ ] 软删除/状态过滤是否一致（`deleted_at IS NULL`、`status != 'cancelled'`）？

**迁移**（`migrations/versions/`）

- [ ] 单 head？`down_revision` 指向正确？
- [ ] 是否有破坏性 DDL（`DROP`、`ALTER TYPE`、`NOT NULL` 无默认、改列类型）？回滚方案是什么？
- [ ] 大表加索引/改列是否会长时间锁表？回填是否分批、可中断、可重跑？
- [ ] **禁止对生产库 `alembic revision --autogenerate`**；是否在临时空库验证过 `upgrade head` + `downgrade`？
- [ ] 迁移里是否夹带业务逻辑（禁止）？

**前端**（`frontend-vite/src/`）

- [ ] loading / empty / error 三态是否都有？接口失败时页面会不会白屏或显示 0？
- [ ] 竞态：快速切换筛选/分页时，旧响应会不会覆盖新结果（是否用了请求序号/AbortController）？
- [ ] 按钮级权限是否与后端一致？隐藏了按钮但接口仍可调，是否可接受（必须后端也拦）？
- [ ] 金额/日期/数量格式化是否走统一工具？有没有 `toFixed` 造成精度丢失？
- [ ] 是否有 `any`、`@ts-ignore`、`console.log` 残留？
- [ ] 组件是否 ≤400 行（门禁拦）、逻辑是否该抽 composable？
- [ ] 空值/超长文本/小屏是否破坏布局（涉及 UI 改动必须有截图）？

**认证与权限**（任何涉及 `auth`、`permission`、`user`、`role` 的改动）

- [ ] 越权（IDOR）：按 id 查询/修改时是否同时限定 `user_id`/角色范围？
- [ ] 新端点是否默认拒绝？角色变更是否即时生效（缓存要不要失效）？
- [ ] token 过期/刷新/注销路径是否覆盖？密码/密钥/验证码是否可能进日志？
- [ ] 文件上传/下载：路径遍历、类型校验、大小上限、存储目录是否在允许列表内？

**配置与运维**（`.env*`、`config/`、`deploy/`、`server_manager/`、`prod_runner`）

- [ ] 新增环境变量是否同步进 `.env.example`（`env_drift` 门禁会拦）？
- [ ] 默认值在**生产**是否安全（例如加密开关默认 `false` 的语义、调试开关默认关）？
- [ ] 改动是否影响启动顺序/依赖服务（停机序必须逆拓扑，失败必须中止后续启动）？
- [ ] 是否有回滚路径（改坏了怎么恢复、旧配置在哪）？端口/路径是否硬编码？
- [ ] 健康探针是否校验**响应内容**而不只是状态码（本仓已因此长期隐瞒故障）？

**测试**（`tests/`、`fastapi_app/tests/`、`*.test.ts`）

- [ ] 这条测试**拦哪种错**？（错分支/漏副作用/边界/契约破坏）说不出 = 不该有。
- [ ] 期望值是**手工推导**的字面量，还是由被测代码/helper 自己算出（镜像断言）？
- [ ] 有没有「mock 存在性断言」冒充行为测试？
- [ ] 失败路径、边界值、权限拒绝是否各有一条？
- [ ] 是否依赖执行顺序/共享夹具/真实时间？是否清理自己造的数据？
- [ ] **变异检查**：把被测行为故意改坏一处，这条测试会红吗？（作者须当场跑给评审者看）

**依赖**

- [ ] `requirements/<tier>.lock` 与 `.txt` 是否同步（`check_requirements_lock.py`）？
- [ ] 新增依赖是否必要、是否与现有库重复、license 是否可接受？
- [ ] `pip-audit` / `npm audit` 是否干净？豁免是否写了 `id + reason + expires`？

### 3.3 明确**不**由人审承担（机器已覆盖，别再逐行挑）

`quality_gate.py` 的 `GATES`（**清单以该文件为准，不要背数字**）：`n_plus_one`、`bare_except`、
`function_length`、`vue_component_length`、`service_commit`、`bom`、`alembic_heads`、`env_drift`、
`ruff`、`complexity`、`loop_shadow`、`pip_audit`（+ CI 的 `file_size_gate`、`scan_secrets`、
`check_orphan_modules`、`check_requirements_lock`、mypy 聚焦门禁）。

**bandit 在 CI 是 `--exit-zero`，只产出 `security-report.json`，不做判定**——评审看到 bandit 报告里
的新发现，仍要自己判断是否 High；不要因为 CI 绿了就认为安全。

CI 门禁 job（test/lint/frontend，另有 build 打包校验）：pytest + coverage≥40、ruff/mypy、前端 `type-check`/`lint`/`vitest`/`build`/`check:api`/`check:routes`/`check:dto`/`check:types`。

**评审看到这些问题，直接引用门禁输出，不再重复评论。** 门禁红了先修门禁，不要带红评审。

## 4. 证据标准（PR/CL 必须带）

| 声称 | 必须附 | 不接受 |
|---|---|---|
| 功能可用 | 操作路径 + 实际响应/截图 | 「我试了」 |
| bug 已修 | **复现测试先红、修复后绿**的两次输出 | 只贴绿 |
| 无回归 | 聚焦测试命令 + 结果 | 「全量应该没问题」 |
| 性能不变/更好 | 前后同口径数字（命令 + 数值） | 「感觉更快」 |
| 安全 | 威胁路径 + 对应测试/扫描输出 | 「加了校验」 |
| 迁移可回滚 | 临时库 `upgrade head` + `downgrade` 输出 | 「downgrade 写了」 |
| 前端改动生效 | 构建产物指纹 + 页面截图（或实测 URL） | 「重新构建了」 |

证据三条硬要求：

1. **当场跑**：本次改动后的输出，不是上次的、不是 CI 的（除非 CI-only 改动）。
2. **可复现**：写清命令与工作目录，别人能跑出同样结果。
3. **失败也给**：没跑通的部分如实写「未验证 + 原因 + 风险」，隐瞒比失败更严重。

## 5. 评论规范

格式（四段，缺一不可）：

```
[H] 权限过滤漏了越权条件
触发：任意用户把 URL 里的 id 换成别人的，就能读到他人订单
建议：在查询里补上 `Order.user_id == current_user.id`（或对应角色范围），并补一条越权测试
依据：fastapi_app/services/order_service.py:123
```

- 作者回应只有三种：**接受并改**（推 commit）/ **不接受并给证据**（测试、文档、实测）/ **转 issue**（写期限与负责人）。
- 禁止人身评价、禁止「按我的经验应该……」而不给依据、禁止把讨论留在 IM 里不留 PR 记录。
- 评审结论写在 PR 顶部固定区块（模板见 `.github/pull_request_template.md`），含各级别条数与最终结论。

## 6. 角色、批量与时限

| 角色 | 职责 |
|---|---|
| 作者 | 自检、附证据、逐条回应；**不得自审通过**；不得在评审期间 force-push 改写已审提交（需重新评审） |
| 评审者 | 未参与实现的**新鲜上下文**；只读 diff + 需求原文；一次审完整个 CL（2026-10-13 约定） |
| owner | 裁决分歧、批准例外、决定 hotfix 是否事后补审、决定是否回滚 |

- **批量上限**：有效 diff（排除 lock/生成物）≤ **400 行/CL**；超过先拆。机械改动（重命名/格式化/依赖锁）单独提交。
- **时限**：提交评审后 **1 个工作日内**首轮反馈；Blocker 立即；复审只看**增量 + 原问题是否闭环**，不重新全文审。
- **一次评审**：评审时点 = 推送前一次，审「当前分支相对 main 的 merge-base 起的全部提交」，不逐提交审。

## 7. 例外与豁免

| 场景 | 规则 |
|---|---|
| 生产不可用的紧急 hotfix | 可先合后审；**24h 内补审并记录**；必须留回滚点与事故记录 |
| 回滚提交 | 免审；提交信息写被回滚 commit、原因、影响范围 |
| 纯文档 | 免审；密钥扫描照跑 |
| 门禁豁免（`nosec`、`noqa`、`secret-scan:allow`、`allowlist.txt`） | 必须写理由；新增 `allowlist.txt` 条目须在提交信息说明；`nosec` 受预算门禁约束 |
| 基线调整（`scripts/gate_baseline.json`） | **只允许下调**；上调须 owner 书面同意并在 PR 说明为什么是存量而非新增 |

**例外不得用于赶进度。** 同一模块 30 天内出现 2 次 hotfix → 触发专项复盘，而不是继续走例外。

## 8. 度量（月度看趋势，不做个人绩效）

| 指标 | 定义 | 用法 |
|---|---|---|
| 缺陷逃逸率 | 合并后 14 天内因该 CL 产生 hotfix/回滚的比例 | 首要指标；先测 3 个月基线，再定目标 |
| 评审发现密度 | (Blocker + High) 数 / 千行有效 diff | 判断评审强度是否足够；**不设越高越好** |
| 假测试拦截数 | 变异检查未变红的测试条数 | 衡量测试真实性；应为 0 |
| 门禁棘轮 | `gate_baseline.json` 各计数 | 只降不升（已有机制） |
| 评审等待时长 | 提交 → 首轮反馈的中位数 | 流程健康度 |

采集：PR 标签 `review:blocker` / `review:high` / `review:false-test`，配合 `git log` 与基线历史。
**不要用「评审意见条数」当绩效**——会激励挑 nit、压制真问题。

## 9. 十分钟清单（可直接贴进 PR）

- [ ] 我能用一句人话说清**根因/改动理由**，不是只描述改了什么
- [ ] 这次改动配了哪条测试？当场跑过，且**看过它红**
- [ ] 把被测行为故意改坏一处，测试**确实变红**
- [ ] 失败路径（空/异常/权限拒绝/重复提交）至少想过一遍
- [ ] 事务边界正确：service 不擅自 `commit`
- [ ] 权限：新端点默认拒绝，按 id 访问带 user/角色条件
- [ ] 契约：前端字段来自 `@/types`，错误码/分页默认值未破坏
- [ ] 影响面：调用点已逐个确认，存量数据/配置默认值已考虑
- [ ] 回滚路径说得出口（改坏了怎么退）
- [ ] 没有夹带：只提交本任务文件，`git status` 干净
