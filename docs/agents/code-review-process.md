# 代码评审流程（Code Review Process）

> 配套标准：[code-review-standard.md](code-review-standard.md)（分级、检查表、证据要求）。
> 启用手册（今天怎么开始跑、三层启用顺序、回滚）：[code-review-rollout.md](code-review-rollout.md)。
> 本文只管**怎么走**：谁在什么时候做什么、退出条件是什么、出问题怎么回。
> 与 `AGENTS.md` §4 的关系：不新增评审时点，仍沿用「**推送前一次审完整个 CL**」。

## 1. 流程总览

```
S0 任务定义 ──> S1 作者自检 ──> S2 提交 ──> S3 生成评审包 ──> S4 独立评审
                    ▲                                              │
                    │                                              ▼
                    └──── S5 分级修复 <── 打回 ── 分级（B/H/M/L/N）
                                   │
                                   ▼
                          S6 复审（只看增量）──> S7 推送 + CI 全绿 ──> S8 合并后验证 ──> S9 复盘
```

三条硬约束：

1. **一次评审**：审「当前分支相对 main 的 merge-base 起的全部提交」，不逐提交审。
2. **零 High/Medium 才推送**（沿用 2026-10-13 约定）；Blocker 一律禁止合并。
3. **评审者必须是未参与实现的新鲜上下文**；作者自审不算评审。

## 2. 各阶段定义

| 阶段 | 责任人 | 输入 | 动作 | 退出条件（证据） |
|---|---|---|---|---|
| **S0 任务定义** | 作者 | 需求/故障现象 | 写清：要解决什么、验收标准、影响面（用户/数据/接口/配置/运维）、回滚方式 | PR 描述前三段写完；说不清回滚方式 = 不许动手 |
| **S1 作者自检** | 作者 | 改动 | ① 跑 `python scripts/quality_gate.py`；② 按改动范围跑最小验证（见 `AGENTS.md` §4 表）；③ 逻辑改动写复现测试并**看它红**；④ 做**变异检查**；⑤ 自查十分钟清单 | 门禁 exit 0；红→绿输出留存；变异后测试确实变红 |
| **S2 提交** | 作者 | 通过的改动 | 一个提交只做一件事；只 `git add` 本任务文件；提交信息写**为什么**；不夹带并发会话的活 | `git status --porcelain` 无意外文件；提交信息能回答「为什么」 |
| **S3 评审包** | 作者 | 分支 | `python scripts/review_packet.py --out logs/review-packet.md`（省略 `--base` 自动解析远端 main；本仓远端名为 `erp`） | 评审包含变更清单、风险标记、必查项、必跑命令 |
| **S4 独立评审** | 评审者（新鲜上下文，最强模型） | 评审包 + diff + 需求原文 | 按标准 §3 逐维度审；每条评论带级别；给出四种结论之一 | 评审结论写入 PR 顶部；零发现须说明「重点看了哪三处」 |
| **S5 分级修复** | 作者 | 评审意见 | Blocker/High 立即修；Medium 当版修（延期须 owner 同意并建 issue）；Low/Nit 可后续；逐条回应 | 每条意见有「已改 commit / 证据反驳 / issue 链接」三者之一 |
| **S6 复审** | 评审者 | 增量 diff + 原问题清单 | 只核原问题是否闭环 + 新增改动是否引入新风险 | 零 Blocker/High；Medium 已闭环或已获同意延期 |
| **S7 推送与 CI** | 作者 | 通过复审的分支 | 等 owner 说「推送」→ 推送 → 盯 CI 全绿 | CI 全绿；红了先看**第一个 failure step** |
| **S8 合并后验证** | 作者/运维 | 已部署版本 | 关键路径实测（登录/主流程/接口 200 且内容正确）、看错误日志与健康快照 | 实测通过；异常有结论 |
| **S9 复盘** | owner/作者 | 逃逸缺陷 | 新根因写进 `docs/agents/pitfalls.md`；标准/门禁缺项补进本文或 `quality_gate.py` | 文档更新；同类问题有机器或人防拦截 |

## 3. 命令手册

```bash
# 0) 确认分支与工作区（并发会话多，先看清）
git rev-parse --abbrev-ref HEAD
git status --porcelain

# 1) 机器门禁（只拦新增，基线只降不升）
python scripts/quality_gate.py

# 2) 聚焦测试（输出存文件，别换 filter 重跑同一套件）
pytest tests/test_xxx.py -q > /tmp/pytest-xxx.log 2>&1; tail -20 /tmp/pytest-xxx.log

# 3) 前端（按需）
cd frontend-vite && npm run type-check && npm run lint && npm test

# 4) 评审包
python scripts/review_packet.py --out logs/review-packet.md

# 5) 独立评审（推送前一次）
#    /open-code-review:delegate-review —— 审 merge-base 起的全部提交，最强模型
```

- `logs/` 下的评审包**不入库**（运行期数据）。
- 全量 pytest 必须提权、独占单实例（`logs/_run_pytest_elevated.ps1`），否则假红。
- 验证结论可复用：代码+依赖未变时，进 review/commit/PR 不必重跑。

## 4. 评审者操作顺序（避免被 diff 带跑）

1. **先读需求与验收**，再读 diff——先有「应该怎样」，才看得出「哪里不对」。
2. **先看风险标记**（评审包给出：迁移/权限/事务/配置/契约/无测试），优先审高影响面。
3. **按文件类型套检查表**（标准 §3.2），不逐行读格式。
4. **重点看失败路径与边界**，正常路径通常作者已自测。
5. **验证测试真实性**：随机抽 1 条，要求作者做变异检查；恒真测试直接 `[H]`。
6. **最后看可读性**，且标 `[L]/[N]`，不占结论。

## 5. 分歧处理

| 情形 | 处理 |
|---|---|
| 作者认为评审者误判 | 用**可执行证据**裁决：补一条测试、跑一次基准、查官方文档；不靠辩论 |
| 双方对「是否 Blocker」有分歧 | 按高一级处理，owner 终裁 |
| 评审者要求超出本 CL 范围 | 转 issue，不在本 CL 扩面（除非是本 CL 引入的问题） |
| 评审者长期不响应 | 超 1 个工作日升级 owner；不得自行「视为通过」 |

## 6. 异常路径

**CI 红了**

1. 看**第一个 failure step**，不看最后一个。
2. 禁止「重跑碰运气」。怀疑 flake 必须给证据：同一 commit 两次结果不同 + 两次日志。
3. 已知假红（并发 pytest、`%TEMP%` 权限、编码）按 `docs/agents/pitfalls.md` §7/§15 判别，不按代码回归处理。

**评审中发现 Blocker**

- 立即停止合并；若已合并 → 优先回滚（不是先修），回滚后再排修复。
- 若已上生产 → 按事故流程：止血 → 取证 → 根因 → 回归测试 → 复盘。

**紧急 hotfix**

- 允许先合后审，但必须：① 留回滚点；② 24h 内补审；③ PR 标 `hotfix` 并写事故编号。
- 同一模块 30 天内 2 次 hotfix → 专项复盘，禁止继续走例外。

**评审包生成失败 / base 不存在**

- 显式指定 base：`--base main` 或 `--base <commit>`；不要用「猜的 merge-base」当评审范围。

## 7. 记录留存

- **评审记录只存 PR**（描述 + 评论 + 结论区块），不进 IM、不进临时文档。
- PR 顶部固定区块由评审者填写：

```
## 评审结论
- Blocker: 0  High: 1  Medium: 2  Low: 3  Nit: 1
- 结论：打回（存在 High）
- 重点核查：事务边界、权限过滤、迁移回滚
- 复审范围：commit abc1234..def5678
```

- 合并后 PR 不删除，作为该改动的决策记录。

## 8. 流程自身的迭代

- **季度复盘**：看 §8 度量趋势，而不是看单次评审意见数。
- 某类问题连续 3 次被评审发现 → 说明机器该拦：补进 `quality_gate.py` 或 CI，而不是继续靠人盯。
- 某条检查表项连续 6 个月零命中 → 考虑删除，保持清单可执行。
- 标准变更走 PR，由 owner 批准；变更理由写进提交信息。
