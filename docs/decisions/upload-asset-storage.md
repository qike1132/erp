# 上传资产存储治理决策

## 状态

已评估，建议分阶段实施；未直接移动历史文件。

## 背景

当前 `static/uploads/customer-sampling/`、`fastapi_app/static/uploads/` 中已有打样图片被 Git 跟踪，并生成缩略图。继续入库会带来三类问题：

1. Git 仓库持续膨胀，克隆和备份成本增加。
2. 业务图片与源码权限绑定，源码仓库读者即可获得客户资料。
3. 缩略图、原始图和衍生文件生命周期与业务记录脱钩。

## 方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| MinIO/S3 对象存储 | 权限、生命周期、容量与源码解耦，可直接生成内部代理 URL | 需部署存储、迁移历史对象、改上传下载链路 | 推荐目标方案 |
| Git LFS | 改造成本低，保留提交历史 | 仓库托管方通常按流量收费，客户图片权限仍与源码仓库绑定 | 仅作为过渡方案 |
| 继续存 Git | 无改造成本 | 仓库膨胀和敏感资料扩散持续恶化 | 不建议 |

## 推荐迁移路径

1. 在内网部署 MinIO，创建 `erp-uploads` bucket，并配置仅限服务账号访问。
2. 应用切换为 `STORAGE_TYPE=s3`，先让新上传对象写入 MinIO；读取端保持当前 URL 兼容层。
3. 建立迁移清单：按 `static/uploads/**/*.{webp,jpg,png}` 与 `fastapi_app/static/uploads/**/*` 枚举文件，写入“旧路径 → 对象 key → 数据库引用状态”。
4. 复制文件到 MinIO 并校验 SHA-256；校验通过后再修改数据库引用。
5. 新上传稳定运行至少一个备份周期后，从 Git 索引移除历史资产，并保留一个可恢复的归档快照。
6. 在 `.gitignore` 中禁止业务上传目录重新入库。

## 验收标准

- 新上传图片不出现在 Git status 中。
- 数据库中的图片 URL 指向存储服务或内部代理 URL。
- 迁移报告中每个旧文件都有“迁移成功/不再使用/需人工确认”的终态。
- 全量测试通过，备份恢复演练包含 MinIO 数据或明确记录备份边界。
