# 从 OpenAPI 生成前端 DTO 类型

日期：2026-10-04
状态：设计已批准，待实施

## 问题

前端有 **436 个手写 DTO 声明**（`interface` 362 + `type` 别名 98；分布于
`src/types/index.ts`、`src/api/*.ts` 及各 view 的 composables），与后端
`fastapi_app/schemas/` 的 Pydantic 模型各写一份。仓库已有
`scripts/check_openapi_frontend_alignment.py`（333 行，已在 CI 运行），但它只校验
**端点路径是否存在**，完全不校验 schema/DTO 形状。

真实摩擦不是"类型会慢慢漂移"，而是**已经在用断言绕过类型系统**：
`src/api/request.ts` 的泛型 `T` 没有默认值，省略泛型返回 `unknown` 而非 `any`，
于是全仓出现 **130 处 `as unknown as`**（51 个文件）。手写类型与后端返回形状
编译器无从校验，每个调用点只能强制断言。

## 目标

从 FastAPI 已自动生成的 OpenAPI schema 生成 `frontend-vite/src/types/api.d.ts`，
并把可消灭的 `as unknown as` 断言换成真实类型检查。

## 非目标

- **不**替换 `list[dict]` 这类无类型 schema 为真实 Pydantic 模型。那是独立的一件事，
  会改变生产接口的响应契约（`response_model` 会剥掉 schema 未声明的字段），不在本次范围。
- **不**追求"全部 DTO 由生成覆盖"。做不到，见"覆盖率的真实形状"。

## 覆盖率的真实形状

实施前实测（2026-10-04，`app.openapi()` 离线导出）：

| 测量项 | 数值 |
|---|---|
| OpenAPI schema / 路径 / 操作 | 431 / 340 / 378 |
| 响应有具体类型 | 301/378（80%） |
| 响应主体无类型（`list[dict]`、裸对象、裸数组） | 77/378（20%） |
| 前端 DTO 声明总数 | 460（362 interface + 98 type 别名） |
| 其中能在 schema 找到同名 | 84 |
| **逐字段比对后无损、生成即可安全替换** | **79** |
| 同名但**会丢字段**（前端视图模型，非后端 DTO） | 8 |

即：生成物在**接口维度覆盖 80%**，在**DTO 维度覆盖 17%**（79/460）。
剩下 83% 的手写 DTO 依然要靠人维护。这不消除双份劳动，
但把"已声明契约"的部分变成单一真值。

**那 8 个"会丢字段"的不是缺陷，是分类正确。** 它们是前端视图模型而非后端 DTO：
`NavItem`/`NavSection`（`title`/`path` 是 store 适配层产物，见
`src/stores/auth.ts:137-143` 的 `name`→`title` 映射）、`MonthlySummary`
（含前端聚合的 `DepartmentSummary[]`）、`FabricItem`（前端自加 `item_ids`/`loss_rate`）。
**这些必须留作手写，不得被生成物覆盖。** 生成器不碰它们，门禁也不要求它们同步。

## 已知数据陷阱

**`list[dict]` 是逃生门，schema 看不见里面的字段。**
`OrderListResponse.data` 声明为 `list[dict]`，dict 内部不过 Pydantic 校验，
handler 注入的字段原样穿透。实测构造 14 字段 item 走 `OrderListResponse`，
`product_image` / `purchase_order_qty` / `spare_quantity` / `is_ordered` /
`has_processes` **全部存活**。

后果：若把 `data` 收紧成 `list[OrderItemSchema]`，`response_model` 会**剥掉**这 5 个
真实到达前端的字段——前端立刻坏掉。这是**不**动 `list[dict]` 的技术原因，
不只是范围原因。生成器对这些响应产出 `Array<Record<string, unknown>>`
（`data` 实测是 required，故不带 `?`），不假装覆盖。

**schema 名有两种形态。** 22 个被展平成 `fastapi_app__schemas__staging__StagingListResponse`。
生成器需归一化尾段，否则这批 schema 匹配不上。实测无非法 TS 标识符、
无保留字冲突。

**`anyOf` 482 处中 479 处是 `X|null` 的 nullable 模式**（306 string、108 integer…），
另有 3 处真正的多类型联合。生成器只需把 `anyOf:[X,null]` 塌成 `X | null`，
其余走通用联合逻辑。`enum` 仅 3 处。

## 设计

### ① 导出器 `scripts/export_openapi.py`

复用已验证可行的离线路径：`from fastapi_app.main import app; app.openapi()`。
不连数据库、不依赖生产服务（已实测 15 秒内完成）。输出 `openapi.json` 快照入库。
这是唯一的后端入口。

### ② 生成器 `scripts/generate-api-types.mjs`

Node，与现有 `check-*.mjs` 同栈。读 `openapi.json`，遍历 `components.schemas`，
输出 `src/types/api.d.ts`。

映射规则：

| JSON Schema | TypeScript |
|---|---|
| `$ref` | 具名引用（先归一化展平名） |
| `anyOf: [X, null]` | `X \| null` |
| 其他 `anyOf`/`oneOf` | 联合类型 |
| `enum` | 字面量联合 |
| `allOf` | 交叉类型 |
| `type: array`，`items` 有 properties | `Foo[]` |
| `type: array`，`items` 为裸 object/dict | `Array<Record<string, unknown>>` |
| `type: array`，无 `items` | `Array<unknown>` |
| `type: object`，`additionalProperties` 为 schema | `Record<string, T>` |
| `integer` / `number` / `string` / `boolean` | 对应 TS 类型 |
| 字段名非合法标识符 | 加引号原样保留 |

文件头写 `// @generated by scripts/generate-api-types.mjs — DO NOT EDIT`。
生成物入库；同步校验由第 ③ 节的门禁负责（重新生成到内存、逐字节比对、漂移即红并打印 diff）。

### ③ 门禁：扩展 `check_openapi_frontend_alignment.py`

不新建 CI 配置，扩展现有脚本，它已在 `.github/workflows/ci-cd.yml` 运行。
保留它现有的端点路径校验，追加"生成物同步"校验：重新生成到内存，
与入库的 `api.d.ts` 逐字节比对，不一致则红并打印 diff。

`check:api` 保持现有职责（移动端绕过 API 层检测）不动——那是另一个正交检查。

### ④ 收敛断言

`request.ts` 的泛型 `T` 无默认值，62 处裸调返回 `unknown`，导致调用点必须断言。
对其中**能对应上生成类型**的部分（79 个无损 DTO 所服务的调用点），
改为真实类型调用，断言随之消失。

**不能消灭的部分必须说清**：20% 的接口响应是 `list[dict]`，生成器对它们产出
`Array<Record<string, unknown>>`——取属性得到的仍是 `unknown`，仍需断言/收窄。
**这类断言消不掉**，生成器对它们无能为力。因此"消灭 130 处"不是本方案的目标；
目标是**能消的消掉，并让剩余的断言数量从 130 下降到一个可解释的数字**。

**逐个改，不批量 sed**——每处要判断该用哪个生成类型，以及 store/组件层是否已有
适配映射必须保留。改完跑 `vue-tsc`，让编译器判定而非人工判断。

## 测试

- **生成器单测**：构造含 `$ref` / `anyOf` nullable / `enum` / `list[dict]` /
  非标识符字段名的 schema，断言输出 TS 正确
- **漂移回归**：改 openapi.json 一个字段，断言门禁变红
- **诚实性守卫**：断言 `api.d.ts` 里 `OrderItemSchema` **不含** `product_image`
  —— 证明生成层不会假装覆盖注入字段
- **视图模型守卫**：断言那 8 个前端视图模型**不出现在** `api.d.ts` 的替换清单里
- **断言收敛回归**：记录改动后 `as unknown as` 的实际剩余数，作为基线断言，
  防止后续回潮

## 风险

- **生成物入库后，错误的类型会像水印一样渗进全站代码。** 因此诚实性守卫是必测项，
  而非可选。
- **收敛断言的过程可能暴露存量 bug。** 前端在 API 边界上有意设计的适配层
  （如 `NavItem` 的 `name`/`url` → `title`/`path`）必须保留，不能被生成类型覆盖掉。
  发现问题时停下报告，不自行决定"前端该跟谁"。
- 实施期间若后端有并发会话在改 schema，生成物会频繁失配。动手前先 `git status` 确认。
