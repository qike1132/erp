# 滨发ERP 技术栈评估与性能优化报告

> 评估日期：2026-08-21 ｜ 版本：v2.0.0 ｜ 目标：确认选型是否最优 + 给出可落地的性能提升方案

---

## 一、总体结论

**你的技术栈选型整体处于"最佳实践"级别，2026 年这个场景下没有需要替换的主流框架。** 不需要推倒重来，但存在 **3 个 P0 级修复点** 和 **一批 P1/P2 优化**，落地后可再获得一个数量级的性能提升（尤其在报表和首屏加载上）。

评分：后端 9.5/10 ｜ 前端 9/10 ｜ 部署 6/10（唯一明显短板）

---

## 二、逐层选型评估

### 1. Web 框架层 ✅ 最优
| 项 | 现状 | 评价 |
|---|---|---|
| 框架 | FastAPI 0.137 全异步 | 2026 年 Python web 综合最优选，生态/Docs/性能俱佳 |
| JSON 序列化 | **自定义 `MsgspecResponse`**（msgspec.json.encode 替代 orjson） | 当前最快的序列化路径，正确 |
| 中间件 | 仅 2 个（SlowAPI 限流 + 审计日志） | 极简，无多余开销 |
| 安全 | JWT 三算法 + Cache-Digest 防护 + 生产强校验 + 错误脱敏 | 完备 |

**潜在替代品评估**：Litestar 性能相近但迁移成本高、生态小 → **不换**。

### 2. 数据库层 ✅ 最优（有参数调优空间）
已具备：asyncpg（最快 PG 驱动）+ SQLAlchemy 2.0 async + 动态连接池（防超 max_connections）+ pre_ping + LIFO + **读写分离（2s 快速降级主库）** + 慢查询监听 + keyset 深翻页 + pg_class 近似计数 + PgBouncer 支持（开关已埋好）。

**优化空间**：
- PG 服务端参数未调优（见 P1-4）
- 报表聚合查询未物化（见 P1-5）
- 索引冗余/缺失未审计（见 P1-7）

### 3. 缓存层 ✅ 最优
L1 进程缓存 + L2 Redis + 0.3s 超时快失败 + **断路器**（3 连败短路 30s）+ 缓存域按位失效 + 跨 worker 失效广播（可选开关）。教科书级设计。

### 4. 异步任务层 ⚠️ 需要小修
| 项 | 现状 | 处理 |
|---|---|---|
| 队列 | ARQ 0.26（原生 async，纯异步栈下的正确选择） | 升级到 `arq>=0.28`（requirements 注释已认可，消除 redis<5 元数据冲突） |
| 遗留 | `fastapi_app/core/celery_app.py` 仍存在 | 删除，避免与 ARQ 混淆 |
| 对比 | Celery（同步阻塞模型）/ Dramatiq（不原生支持 async） | 均不换，ARQ 最优 |

### 5. 前端层 ✅ 最优（有减重空间）
已具备：Vue 3.5 + Vite 7 + TS + Pinia + TanStack Query + PrimeVue 4 + Tailwind 4 + ECharts 6 + manualChunks 精确分包 + 组件按需引入 + **PWA SW 三层缓存策略**（读接口 SWR / 写接口 NetworkOnly / 兜底 NetworkFirst 1.5s）+ CSP + 生产去 console。

**减重空间**：
- `vendor-fontawesome` 整包 `free-solid-svg-icons`（约 1MB+）→ 应按需引入图标
- ECharts 已拆 core，确认是否全部 `use()` 注册（建议按需）
- 用已装的 `rollup-plugin-visualizer` 跑一次产物体积分析

### 6. 部署层 ⚠️ 最大性能短板
| 问题 | 影响 | 解法 |
|---|---|---|
| 无 Nginx 时回退 **`vite preview`** | 非生产级服务器（无缓存头、压测性能差） | 强制 Nginx 前置（现有 `deploy_nginx.ps1`） |
| 静态文件由 FastAPI StaticFiles 直出 | Python 处理静态资源浪费 CPU | Nginx 直接 serve + gzip/brotli + immutable 强缓存 |
| 单机 EXE 并发上限 | 内网几十人够用，但压测/扩展受限于单机 | 保持（行业正确选择），Nginx 前置补足 |

## 三、性能提升路线图

### P0 — 立即做（1-2 天，零风险）
1. **arq 升级** `0.26.0 → >=0.28`，消除 redis 版本冲突声明
2. **删除 `celery_app.py`** + config.py 中 Celery 配置项（已迁移 ARQ）
3. **Nginx 前置**：静态资源（.js/.css/.png/woff2）由 Nginx serve + gzip + 强缓存头（hash 文件名 immutable），`/api` 反代 uvicorn；`prod_runner` 无 Nginx 时不再回退 vite preview

### P1 — 高价值（1 周）
4. **PG 服务端调优**（一键脚本）：
   - `shared_buffers = 25% 物理内存`
   - `effective_cache_size = 75% 物理内存`
   - `work_mem = 4-16MB`（按报表大小）
   - `maintenance_work_mem = 1GB`
5. **报表热路径物化**：dashboard / report 中 TOP 聚合查询 → 建物化视图 + 定时刷新（或每日预聚合表），聚合查询从秒级降到毫秒级
6. **前端减重**：FontAwesome 全量→按需；跑 `rollup-plugin-visualizer` 分析；单 chunk 目标 <600KB
7. **索引审计**：查重复索引、缺失复合索引（如 `order_no + order_date`、`product_id + stock` 组合）

### P2 — 扩展性（有空再做）
8. **PgBouncer** transaction 模式（代码已支持 `PGBOUNCER_ENABLED=true`，补部署配置即可）
9. **开启 `CACHE_L1_BROADCAST_ENABLED=true`**，收敛多 worker 脏数据窗口
10. **慢查询治理闭环**：利用已有慢查询监听，定期导出 + review
11. Redis Sentinel 高可用按需启用

## 四、明确不需要替换的东西

- ❌ FastAPI → Litestar / Starlette：收益甚微，成本巨大
- ❌ ARQ → Celery：纯异步栈 ARQ 更优
- ❌ PostgreSQL → MySQL：PG 在报表、复杂查询、JSON 能力全面领先
- ❌ Redis → Memcached：Redis 有 Pub/Sub + 持久化 + 数据结构
- ❌ PrimeVue → Element Plus：v4 已成熟，迁移无收益
- ❌ 微服务化：单公司内网 ERP，单体最可靠、运维最简单
