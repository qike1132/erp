# /beile-order 订单数量与备品同步 —— 产品需求文档（PRD）

## 1. 项目信息

| 项 | 内容 |
| --- | --- |
| Language | 简体中文 |

### 1.1 原始需求复述

> 修复 `http://192.168.0.95:3000/beile-order` 的订单数量逻辑问题：修改其前端与后端，使订单及备品数量实时同步自 `http://192.168.0.95:3000/purchase` 的实际数据（例如变形金刚订单总量 10000 调整为 订单 10000、备品 500），确保 `/beile-order` 展示信息与实际下单数据完全一致，并新增对应前端显示。针对 `http://192.168.0.95:3000/customer-order` 下未在 `/purchase` 完成下单的湖北订单，在 `/beile-order` 增加明确提示；仅当对应订单在 `/purchase` 下单完成后，`/beile-order` 方可确认订单。

### 1.2 已确认前提（本 PRD 的既定口径，不再推翻）

1. **备品必须落库**：在 `purchase_order` 表新增备品数量字段。
2. **备品真相源** = `/purchase`「汇总下单」弹窗里的「损耗率（千分之几）」：`备品 = ceil(订单数量 × 损耗率‰)`，必须随下单一起持久化，不能只留在前端会话态。
3. **数量显示口径**：已下单 → 显示采购单实际下单数量；未下单 → 显示客户订单原数量并标注「未下单」。
4. **确认门控范围**：订单行与备货行都受控（未在 `/purchase` 完成下单则不可确认）。

## 2. 产品定义

### 2.1 产品目标（一句话）

让 `/beile-order` 的**订单数量、备品数量、可确认性**三者完全对齐 `/purchase` 的真实下单数据，消除「页面数量 ≠ 实际下单」与「未下单却可确认」两类错误。

正交的 3 个目标：
- **数据一致**：`/beile-order` 展示的数量 = `/purchase`（`purchase_order`）中该订单的实际下单数量（含备品）。
- **时序一致**：`/purchase` 一侧下单/改损耗率后，`/beile-order` 能近实时（写入即失效缓存）反映。
- **流程受控**：未在 `/purchase` 完成下单的湖北记录，`/beile-order` 给出明确提示且禁止确认。

### 2.2 现状问题（量化，来自只读实测）

| 问题 | 现状证据 |
| --- | --- |
| 数量裸取客户订单原值 | 后端 `services/order/beile.py::_build_beile_order_record` 用 `item.quantity`；`_build_beile_stockin_record` 用 `stockin.quantity`。**完全没读 `/purchase` / `purchase_order`**。 |
| 备品在数据库中不存在 | 全库 `information_schema` 无任何 spare/loss/备品/损耗字段或表；备品只活在前端会话态 `useSummaryModal.ts:25 calcSpareQuantity()` 与 `SummaryModal.vue` 的 `lossRate = ref(0)`，关闭弹窗即丢。 |
| 关联只能靠 JSON 数组 | `purchase_order.source_order_id`（单值列）在 43 条记录中 **0 条非空**，全为 NULL；只能用 `source_order_ids`（JSON 数组字符串，如 `"[65091]"`）关联客户订单。实测 43 条：28 completed / 15 pending。 |
| 缓存导致非实时 | `beile.py::get_beile_orders_with_stockins` 与 `get_beile_unconfirmed_count` 均 `@cache_result(ttl=60, local_ttl=15)`。 |
| 备货行无关联字段 | `shared_models/stock_in.py` 的 `StockIn` 仅有 `customer` / `product_id` / `quantity` / `stockin_date`，**无任何关联客户订单的字段**，「是否已下单」的判定规则缺失。 |
| 损耗率易丢 | 损耗率输入框（`SummaryModal.vue:49-58`）在**非编辑态**即可输入，而「保存修改」按钮只在编辑态出现（:67-72）⇒「改了损耗率但没进编辑态/没点保存」是必现的失败路径。 |
| 确认无前置校验 | `services/order/beile.py::confirm_beile_order / confirm_beile_stockin` 仅校验工厂与幂等，**不校验是否已下单**。 |

### 2.3 用户故事

- **As a** 湖北订单操作员，**I want** `/beile-order` 的数量列展示的是 `/purchase` 里该订单的真实下单数量（而非客户订单原数量），**so that** 我核对生产/发货时不因数字不一致而出错。
- **As a** 湖北订单操作员，**I want** 在新列直接看到每个订单的**备品数量**，**so that** 我不用再去 `/purchase` 弹窗里口算损耗。
- **As a** 湖北订单操作员，**I want** 未在 `/purchase` 完成下单的记录被明确标红提示且「确认订单」按钮不可点，**so that** 我不会误确认一个还没真正下单的订单。
- **As a** 采购操作员，**I want** 我在「汇总下单」里填的损耗率能被保存并在下单完成时生效，**so that** 备品数量能被稳定地带到 `/beile-order`，即使我忘了点「保存修改」。
- **As a** 湖北订单操作员，**I want** 采购侧下单完成后，`/beile-order` 无需手动刷新即可看到最新数量并允许确认，**so that** 两个页面之间不再需要人工来回核对。

### 3.2 备品与订单数量的口径定义（本次最关键，写死）

**真相源**：`purchase_order` 表。订单数量 = `product_quantity`；备品数量 = 新字段 `spare_quantity`。

**关联关系**：客户订单 `O` 的关联采购单集合 `P(O) = { p | O.id ∈ parse(p.source_order_ids) }`（`source_order_ids` 为 JSON 数组字符串；`source_order_id` 单值列全为 NULL，**不得使用**）。

**「已下单」定义**：`∃ p ∈ P(O)` 且 `p.status = 'completed'`（即 `completed_at` 非空）。`pending` 视为**未完成下单**。

**订单数量 Q_display**：
- 已下单：`Q_display = MAX{ p.product_quantity | p ∈ P(O), p.status='completed' }`（**取最大值，不求和** —— 同一客户订单被拆到多个供应商时，多张采购单携带同一订单数量，求和会重复计数）。
- 未下单：`Q_display = O 的客户订单原数量`，并标注「未下单」。

**备品数量 S**：
- 公式：`S = ceil(Q × r / 1000)`，其中 `r` = 损耗率（千分之几），`Q` = 该采购单的订单数量。
- 已下单：`S_display = MAX{ p.spare_quantity | p ∈ P(O), p.status='completed' }`（同理取 max，避免多供应商重复计数）。
- 未下单：不展示备品数值，显示「—」或「未下单」。

**取整规则**：使用 `Q` 的原始数值（`NUMERIC(12,2)`，允许小数）直接计算，结果**向上取整到整数**（与既有 `calcSpareQuantity` 的 `Math.ceil` 完全一致，前后端口径必须同源）。

**边界处理（必须全部实现）**：

| 边界 | 规则 |
| --- | --- |
| 损耗率 `r = 0` 或缺失（NULL） | `S = 0` |
| 损耗率 `r < 0`（非法） | 归一为 `0` → `S = 0` |
| 损耗率 `r > 1000` | 截断为 `1000`（与前端 `max=1000` 一致） |
| 订单数量 `Q ≤ 0` 或非有限值 | `S = 0`，且订单数量列显示 `0` 并保留未下单/异常提示 |
| 同一客户订单对应多张采购单 | 数量与备品均**取 MAX，不求和**（见待确认问题 3） |
| 同一客户+产品被拆到多个供应商采购单 | **不重复计数**：`/beile-order` 按「客户订单」维度展示，取 MAX 后天然去重 |
| 采购单状态混合（部分 completed / 部分 pending） | 只要**存在 completed** 即视为已下单；展示 completed 集合的 MAX |

**数值算例（≥6，含用户给的 10000 / 500）**

| # | 场景 | 输入 | 计算 | 结果（展示） |
| --- | --- | --- | --- | --- |
| 1 | 用户原例（变形金刚） | Q=10000，r=50‰ | ceil(10000×50/1000)=ceil(500) | 订单 **10000**、备品 **500** |
| 2 | 损耗率=0 | Q=10000，r=0 | ceil(0) | 订单 10000、备品 **0** |
| 3 | 非整除向上取整 | Q=9999，r=50‰ | 9999×0.05=499.95 → ceil | 备品 **500** |
| 4 | 极小损耗 | Q=100，r=1‰ | 100×0.001=0.1 → ceil | 备品 **1** |
| 5 | 小数损耗率 | Q=100，r=0.5‰ | 100×0.0005=0.05 → ceil | 备品 **1** |
| 6 | 订单数量为 0 | Q=0，r=50‰ | ceil(0) | 订单 0、备品 **0** |
| 7 | 订单数量为负（异常） | Q=-5，r=50‰ | 非法 → 0 | 备品 **0**，数量列显示 0 + 异常/未下单提示 |
| 8 | 损耗率超上限 | Q=10000，r=1200‰ | 截断 r=1000‰ → ceil(10000) | 备品 **10000** |
| 9 | 同一客户订单两张采购单（均 completed） | p1(qty=10000,spare=500)，p2(qty=10000,spare=500) | MAX(10000,10000)=10000；MAX(500,500)=500 | 订单 **10000**、备品 **500**（**不叠加为 20000/1000**） |
| 10 | 混合状态 | p1 completed(qty=10000,spare=500)，p2 pending(qty=10000) | 已下单；仅取 completed 集合 | 订单 **10000**、备品 **500** |
| 11 | 未下单 | 无任何关联采购单 | —— | 显示客户订单原数量 + 徽章「未下单」，备品列显示「—」 |

### 3.3 「未完成下单」判定规则

**订单行（`record_type='order'`）**
- 判定：`O` 是否存在 `status='completed'` 的关联采购单（关联 = `O.id ∈ parse(purchase_order.source_order_ids)`）。
- 不存在 → 该行标记「未下单」，确认按钮禁用。

**备货行（`record_type='stockin'`）** —— `StockIn` 无关联客户订单字段，采用**推荐匹配规则**（见待确认问题 2）：
- 判定：存在采购单 `p`，满足 `p.status='completed'` 且 `p.customer_name = stockin.customer` 且 `p.product_name = stockin.product.name`（产品名以 `Product.name` 为准）。
- 无匹配 → 标记「未下单」，确认按钮禁用。
- 该规则为**近似匹配**，需产品确认；备选方案见待确认问题 2。

### 3.5 确认门控的产品行为

- **前端**：未下单时「确认订单」按钮 `disabled`，hover tooltip 固定文案 `请先在采购中心完成下单`。
- **后端（推荐双端都拦）**：`confirm_beile_order` / `confirm_beile_stockin` 在落库前校验「已下单」；未通过则拒绝。
  - HTTP 状态：`409 Conflict`（冲突而非 404，语义更准）。
  - 错误 `detail` 固定文案：`该订单未在采购中心完成下单，请先在采购中心完成下单后再确认`。
- **前端错误提示**：捕获后 `toast.error(detail)`，文案同后端 `detail`，保证端到端一致。

### 3.6 时效（实时）定义

- 目标：`/purchase` 一侧「下单完成 / 批量确认订单 / 汇总保存」提交成功后，`/beile-order` 下一次请求即返回最新数据（**写入即失效缓存，时效 ≈ 0，承诺 ≤ 1s**）。
- 实现约束：在采购侧写事务**提交后**失效 `/beile-order` 相关缓存键（订单列表 + 未确认计数），保留现有 60s TTL 作为兜底。

## 4. 验收标准（可被 E2E 断言、可判定）

1. **AC-1 数量同步**：某湖北客户订单在 `/purchase` 完成下单且 `product_quantity=10000` 后，`/beile-order` 该行「数量」列显示 `10000`（而非客户订单原数量），并带「已下单」徽章。
2. **AC-2 备品同步**：上条对应采购单 `spare_quantity=500` 时，`/beile-order`「备品数量」列显示 `500`。
3. **AC-3 未下单提示**：对未在 `/purchase` 完成下单的湖北订单，`/beile-order` 该行带「未下单」徽章、按钮禁用。（顶部横幅计数断言已随横幅下线移除。）
4. **AC-4 门控-前端**：未下单行的「确认订单」按钮 `disabled=true`，tooltip 文案 = `请先在采购中心完成下单`。
5. **AC-5 门控-后端**：直接调用 `POST /api/v1/orders/{id}/confirm`（未下单订单）返回 `409`，`detail` = `该订单未在采购中心完成下单，请先在采购中心完成下单后再确认`；数据库中 `confirmed_at` 仍为 NULL。
6. **AC-6 门控放开**：该订单在 `/purchase` 完成下单后，同一确认接口返回 `200`，`confirmed_at` 被写入。
7. **AC-7 口诀算例**：`Q=9999, r=50‰` → 备品显示 `500`；`r=0` → 备品显示 `0`；`Q=0` → 备品显示 `0`。
8. **AC-8 去重**：同一客户订单对应两张 completed 采购单（各 qty=10000/spare=500）时，`/beile-order` 显示订单 `10000`、备品 `500`（不出现 20000 / 1000）。
9. **AC-9 备货行门控**：无匹配 completed 采购单的备货行，其「确认备货」按钮禁用；`POST /api/v1/orders/stockin/{id}/confirm` 返回 `409`。

## 5. 待确认问题（≤5，各附推荐选项）

**Q1（必须确认）｜损耗率改了但用户没点「保存修改」就下单完成，怎么处置？**
- 现状：损耗率输入框在非编辑态即可改；「保存修改」只在编辑态出现。
- 推荐：**把损耗率随「保存修改」与「下单完成 / 批量确认订单」两处动作一并提交并落库**。即下单完成时以**输入框当前实时值**为准计算 `spare_quantity` 写入采购单；若请求未携带损耗率，则沿用该采购单已存值（无则 0）。这样即使未进编辑态、未点保存，也不会丢备品。
- 备选：为损耗率单独加「即时保存」（改动更大，不推荐）。

**Q2（必须确认）｜备货行「是否已下单」的关联判定规则？**
- 现状：`StockIn` 无关联客户订单字段，无法直接关联。
- 推荐：按 `(客户名, 产品名)` 匹配存在 `status='completed'` 的采购单即视为已下单（准确度足够，改动最小）。
- 备选：为 `StockIn` 增加关联字段（改动大）；或备货行仅提示不门控（与用户「备货行也受控」冲突，不推荐）。

**Q3（必须确认）｜同一客户订单对应多张采购单时，数量/备品怎么算？**
- 推荐：**取 MAX，不求和**（防止多供应商采购单重复计数）。
- 备选：求和（仅在能确认「每张采购单的 product_quantity 是拆分后的子数量」时才成立，当前证据不支持）。

**Q4｜`pending` 状态算不算「已下单」？**
- 推荐：**不算**，仅 `status='completed'` 才算「已下单」；`pending` 显示为「未完成下单」。
- 依据：用户口径 3「已下单 → 显示采购单的实际下单数量」中的「已下单」对应 `/purchase` 的「下单完成」动作（`completed`）。

**Q5｜实时同步的时效与缓存策略？**
- 推荐：采购侧写入即失效 `/beile-order` 缓存（订单列表 + 未确认计数），目标时效 ≤ 1s；保留 60s TTL 兜底。
- 备选：把 `/beile-order` 列表缓存的 TTL 直接降到 ≤5s（更简单但仍有窗口，不推荐作为唯一手段）。
