## 0. 先纠正一个任务前提（很重要）

你要求「重构 v5.33」。但在动手前必须先厘清三件事，否则方案会打偏：

### 0.1 v5.33 是一个**已知有 P0 缺陷的旧版**，不是当前代码

| 事实 | 证据 |
|---|---|
| v5.33 是 2026-08-15 构建的 | `dist/ERP服务器管理器_v5.33.exe` 文件时间戳 |
| 当前源码已是 **v5.40** | `server_manager.py` L59：`_VERSION = 'v5.40'` |
| v5.33 有 **4 个 P0 缺陷** | `docs/bugs/BUG-SERVER-MANAGER-v5.33-MODE-SWITCH-20260908.md` |
| 这些缺陷**已在新版修复** | 重建交付报告记录 16 项缺陷修复，QA 220/220 断言通过 |

v5.33 的四个 P0：

1. **开发模式 100% 无法启动** —— `_ensure_production_stopped` 超时分支返回 2 元组，调用方解包 3 元组 → 崩溃
2. **生产模式停不掉** —— `nssm stop` 后不等 STOPPED 确认就报「已执行」，`except: pass` 吞掉「拒绝访问」
3. **宽特征扫描误杀** —— 按 `python`/`node` 强杀，误杀 NSSM 监管进程 → 5 秒自动复活，形成「杀不死」死循环
4. **无防重入** —— 日志显示一秒内 6 轮并发清理

**结论：不要以 v5.33 为基线做重构。** 正确做法是以**当前 `server_manager.py`（v5.40，2134 行）为基线**，v5.33.exe 只作为「为什么必须改」的历史证据。下文的方案全部基于 v5.40。

### 0.2 这不是一个开源项目，「GitHub 检索」需要重新定义

`ERP服务器管理器` 是你们自研的闭源商业工具（GitHub remote: `qike1132/erp.git`，私有仓库）。GitHub 上**不存在**同名开源项目。

所以我把检索重新定义为：**检索功能等价的 5 类开源项目**，从中提取架构与工程实践。这是唯一有意义的做法。

### 0.3 v8 重构方案**已经存在**，本报告是它的校验与增补

`docs/ui-redesign/v8-ERP服务器管理器重构方案.md`（2026-08-31）已给出完整的 4 层架构方案。同时 `packaging/server_manager_v8.spec` 已就绪，但 **`server_manager_v8/` 包目录根本不存在** —— 方案写了，代码没写。

## 2. 检索结论与选型裁决

### 2.1 整体格局：三层分化

| 层 | 项目 | 对你的意义 |
|---|---|---|
| **框架层** | Tauri 111k / Wails 36k / pywebview 6k | UI 层换栈的依据。**v8 已选 pywebview —— 这个选择是正确的**（见 §2.2） |
| **进程编排层** | PM2 43k / process-compose 2.8k / WinSW 14k | **与本项目功能高度重合**，是 Domain 层设计的直接模板 |
| **系统管理层** | System Informer 16k / WinSW 14k / Servy 2k | Windows 进程/服务操作的**正确做法**，MIT 可安全参考 |

### 2.2 对已有 v8 技术选型的校验结论

**✅ pywebview 是正确的选择，不需要改。** 理由：

1. **不动技术栈** —— 后端是 Python（FastAPI/SQLAlchemy/ARQ），业务逻辑全在 Python。pywebview 让 UI 换成 Web 技术但**业务层零改动**，重构风险可控。
2. **体积可控** —— `packaging/server_manager_v8.spec` 已配好 excludes，排除 fastapi/uvicorn/pandas 后 EXE 预计 40-60MB（当前 19MB，可接受）。
3. **Tauri/Wails 的代价过高** —— 换成 Rust/Go 意味着**业务逻辑全部重写**，而你最有价值的资产恰恰是经过实机验证的进程管理逻辑（v8 方案自己也强调「必须逐行迁移而非重写」）。**为 UI 质感重写业务内核，投入产出比极差。**

**唯一保留意见**：pywebview 依赖系统 WebView2。Windows 10/11 通常已内置，但**老服务器（Server 2016/2019）可能缺失**。v8 方案未提及此依赖的检测与降级 —— 这是必须补的（见 §4 风险 R5）。

### 2.3 三项最有价值的借鉴（按优先级）

| 优先级 | 来源 | 借鉴内容 | 解决你哪个具体问题 |
|---|---|---|---|
| **P0** | **process-compose** | 领域模型：声明式进程定义 + depends_on + 健康探针 + 日志分流 + REST 控制面 | Domain 层设计**直接对标**，避免自创一套不完整的模型 |
| **P0** | **uptime-kuma** | 探针抽象 + 心跳调度 + 三态状态机（UP/DOWN/PENDING）+ 连续失败判定 | 解决健康检查写死、慢启动误判（D15） |
| **P1** | **System Informer / WinSW** | SCM API 结构化查询替代 `sc` 文本解析；NSSM 失败策略细化 | 解决 v5.39 审查 🔴#1 的子串误判漏洞 |

### 2.4 许可证风险清单（关键）

因为是**商业闭源产品**，GPL 系有传染性，必须区别对待：

| 许可类型 | 项目 | 结论 |
|---|---|---|
| ✅ **安全** | Tauri(MIT/Apache)、uptime-kuma(MIT)、traefik(MIT)、wails(MIT)、System Informer(MIT)、WinSW(MIT)、Servy(MIT)、Portainer(Zlib)、kind(Apache-2.0)、process-compose(Apache-2.0)、pywebview(BSD-3) | 可借鉴代码与架构 |
| ⚠️ **污染风险** | **PM2 (AGPL-3.0)** —— 最危险，抄代码即触发传染 | **仅读思路，禁抄代码** |
| ⚠️ **污染风险** | **Cockpit (GPL-3.0+/LGPL-2.1+)** | 仅借鉴分层与边界设计 |
| ⚠️ **需核实** | Supervisor（PyPI 标注 NOASSERTION，实为 GPL 系派生） | 使用前必须自行核实 |

**统一纪律**：即使 MIT/Apache 项目，也**只吸收架构与领域模型，避免逐行移植**。这样既规避版权/衍生作品争议，也迫使自己做适配设计而非盲目照搬。

## 3. 重构方案建议

### 3.1 总原则

> **重构对象是架构与 UI 层，不是业务能力。**
> 现有进程管理、服务托管、端口清理、Redis 探测逻辑是**经实机验证的资产**，必须**逐行迁移而非重写**。

这条原则与已有 v8 方案一致，我完全认同。以下是**增补与细化的落地细节**。

### 3.2 目标架构

```
┌─────────────────────────────────────────────────────────┐
│  Presentation 层（可替换）                                │
│  pywebview + HTML/CSS/JS（Edge WebView2）                │
│  · 视图：按「资源树 + 详情 Tab」组织（借鉴 Portainer）      │
│  · bridge.py：唯一特权入口，只收结构化意图，禁拼命令        │
│    （借鉴 Cockpit 的桥接边界）                            │
├─────────────────────────────────────────────────────────┤
│  Application 层（场景编排，无 I/O 细节）                   │
│  UseCase：StartDevMode / SwitchToProd / EmergencyStop    │
│  Pipeline + Step 显式建模（借鉴 process-compose/蓝鲸）      │
│  · 每步带状态/耗时/可重试/可中断 → UI 呈现为 Stepper       │
├─────────────────────────────────────────────────────────┤
│  Domain 层（纯逻辑，零 I/O，可 100% 单测）★ 关键            │
│  · 领域模型：Process / Service / HealthProbe / Dependency │
│  · 状态机：四态语义（RUNNING/STOPPED/未知/未安装）          │
│  · 端口契约、模式互斥规则、就绪判定规则                     │
│  · 借鉴 process-compose 的模型 + uptime-kuma 的探针状态机  │
├─────────────────────────────────────────────────────────┤
│  Adapter 层（真实世界接口，唯一碰系统的地方）               │
│  process_win / service_scm（★ 改 SCM API）/ health_http   │
│  storage_json / audit_jsonl / metrics_psutil / notify_win │
│  · 借鉴 System Informer：SCM 结构化查询替代文本解析        │
└─────────────────────────────────────────────────────────┘
依赖方向严格单向：Presentation → Application → Domain ← Adapter
```

### 3.3 技术选型

| 关注点 | 选型 | 理由 |
|---|---|---|
| 桌面外壳 | **pywebview**（保持 v8 决定） | 业务零改动，体积可控 |
| 前端 | 保持现有 Vite 栈 | 已有成熟前端工程，不重复造轮子 |
| UI 通信 | **结构化事件（命名事件 + TypedDict/pydantic schema）** | 借鉴 Wails Events，替代无 schema 的 queue 消息 |
| 就绪等待 | **统一 `wait_until(predicate, timeout, interval)` 原语** | 借鉴 kind 的 readiness 门闩 |
| 健康检查 | **探针抽象 + 三态状态机（含 PENDING）** | 借鉴 uptime-kuma |
| SCM 查询 | **`pywin32`/`ctypes` 调 SCM API，弃 `sc` 文本解析** | 借鉴 System Informer，根除子串误判 |
| 配置 | **静态/动态分离 + pydantic schema 校验** | 借鉴 Traefik |
| 打包 | 保持 PyInstaller，spec 已就绪 | `server_manager_v8.spec` 可直接用 |

### 3.5 重构步骤

**阶段划分（建议按此顺序，关键路径在 P1）**

**P1 为何是关键路径**：Domain 层是唯一「零 I/O、可单测」的层。**先把它做扎实并配上测试，后续所有迁移才有安全网**。当前项目最大的短板就是「有效测试覆盖为零」（v5.39 审查 🟡#11），必须在 P1 扭转。

### 3.6 迁移纪律（务必遵守）

1. **逻辑逐行迁移，禁止「顺便优化」** —— 迁移期只做「搬运 + 分层」，任何行为改动单独提交、单独验证。
2. **每次迁移一个 adapter，立即补测试** —— 不要批量迁移后再补测。
3. **保留事故编号注释** —— 现有代码的「事故编号 → 防御点」追溯体系（v5.39 审查称其为亮点）必须随代码迁移，这是最珍贵的知识资产。
4. **双轨运行期** —— v5.40 与 v8 并存，配置文件按 schema 版本隔离（v8 方案已定此策略）。
5. **禁止引入 GPL 系代码** —— 见 §2.4。

## 5. 执行建议（结论）

1. **立刻修正基线**：不要重构 v5.33。以 **v5.40（2134 行）为基线**，v5.33.exe 归档为历史证据。
2. **先处理 R10**：Redis 密码不对称 + 重启风暴是**正在发生的生产故障**，优先于任何重构工作。密码已泄漏在 GitHub 历史中，建议轮换。
3. **重构按 P0→P5 推进，P1（Domain + 测试）是关键路径**，先把可测试内核做扎实再动 UI。
4. **新能力（告警/RBAC/审计）独立立项**，不要混进重构（R4）。
5. **禁止引入 GPL 系代码**（PM2 AGPL、Cockpit GPL），只借鉴架构与领域模型。
6. **优先借鉴三项**：process-compose（领域模型）、uptime-kuma（健康探针状态机）、System Informer/WinSW（Windows 服务与进程的正确做法）。
7. **保持 pywebview 选型不变** —— 检索证实这是正确决定，换成 Tauri/Wails 意味着业务逻辑重写，得不偿失。
