## ★ P3 的六条核心架构决策

### 决策一：Port 签名里的类型，定义权一律在 domain 层

**问题**：Protocol 的**返回类型**若定义在 adapters 层，会形成
`domain/ports.py → adapters` 的违规依赖。而**门禁对「返回类型」这种隐性依赖无能为力**
—— 它只能拦 import 语句，拦不住「签名里引用了谁」。

**落法**：凡是出现在 Port 签名里的类型（`OpResult` / `KillResult` / `HealthSample` /
`MetricsSample` / `AuditEntry` / `ChainVerifyResult` …），定义权全部收归
`domain/results.py`。

**这条不靠门禁守，靠纪律**：因为它是**逻辑依赖**而非语法依赖。已写入
`domain/ports.py` 的模块文档，作为后续新增 Port 的检查项。

### 决策二：显式结果对象，失败必须带 reason

`OpResult` / `KillResult` / `HealthSample` / `MetricsSample` / `AuditEntry`
全部带 `ok/reason/detail`，且 `__post_init__` **强校验**：

```python
def __post_init__(self) -> None:
    if not self.ok and not self.reason:
        raise ValueError('失败结果必须说明 reason（否则用户只看到「失败」两个字）')
```

这是解决 v8 方案 D5「静默失败」的落点 —— 让「静默失败」在构造时就崩，
而不是等用户来问「为什么点了没反应」。

### 决策三：权限不足返回 `OpResult.failure` 而非抛异常

**理由**：权限不足是**预期内的正常分支**（Viewer 点了一个 L2 按钮），
不是异常。抛异常会让调用方被迫用 `try/except` 处理一个业务流程。

**但必须留痕**：被拒时同时发事件 + 写 `AuditOutcome.DENIED` 审计 ——
这是 v8 方案 §2.5「堡垒机 4A」的硬要求：**谁在什么权限下被拦了**，必须有据可查。

```python
# 审计条目对 DENIED 有额外校验
if self.outcome is AuditOutcome.DENIED and not self.reason:
    raise ValueError('被拒的审计条目必须记录 reason')
```

### 决策四：校验在服务端做，不信前端说的「我已确认」

前端可以伪造。所有高危校验（危险等级、确认令牌、目标名匹配、端口合法性）
一律在用例层重做一遍。`ConfirmationToken.satisfies()` 是**唯一**判定入口。

**配套**：前端不该自己拼确认提示文案。`required_confirmation(action)` 统一提供给前端：

```python
Action.UNINSTALL_SERVICE → {'kind': 'typed', 'word': '卸载服务',
                            'hint': '请输入「卸载服务」以确认',
                            'requires_reason': 'true'}
```

两边各写一份文案，改一处就会不一致 —— 更糟的是不一致之后**没人会发现**，
因为两边各自都「看着对的」。

### 决策五：批量 L3 操作与「输入名称确认」的矛盾解法

**矛盾**：`ConfirmationToken.satisfies()` 要求 `typed_name == target`。
但卸载是**批量**操作（一次卸 erp-prod + erp-arq），用户不可能输入两个名字。

**解法**：`@require(..., target_arg='confirm_target')` 用**固定确认词**：

```python
CONFIRM_WORD_UNINSTALL = '卸载服务'

@require(Action.UNINSTALL_SERVICE, target_arg='confirm_target')
def execute(self, *, ..., confirm_target=CONFIRM_WORD_UNINSTALL, names=(), ...):
```

用户的确认动作从「输入两个服务名」变成「输入确认词一次」——
防误点目的达到（仍需 TYPED + reason），但不要求用户做不可能的事。

### 决策六：容器是唯一允许 import adapters 的「上层」文件

`container.py` 位于包根，**不属于任何一层**，因此可以同时 import adapters
与 application 而不违规。它是 composition root。

**配套断言**（写进 `test_container.py`，比门禁更直接）：

```python
def test_application_layer_never_imports_adapters(self):
    """除 container.py 外，application/ 下不允许出现任何 adapters import。"""
```

**实际代价**：一旦这条被破坏，用例就不能在无 Windows 的 CI 里跑
（Fake 替换不了 `NssmService`）。所以它不是洁癖，是可测性的前提。

## ★ P3 的四个实现陷阱（都是真实踩到的）

### 陷阱一：命令成功 ≠ 状态已变

`kill_tree` 返回 `ok=True` 时，进程可能**仍在终止中**；`nssm remove` 返回成功时，
服务可能仍在「标记删除」状态。

**落法**：杀完必须**复查**。`KillPort` 与 `StartProd` 都加了 `_recheck()`：

```python
RECHECK_ATTEMPTS = 3
RECHECK_INTERVAL_S = 0.5
```

**同源陷阱**：`KillResult.targeted == 0`（没找到可杀进程）**不是成功** ——
端口仍然被占。原始代码只判 `result.ok`，把这个场景误判为成功：

```python
# 修复后区分三种结果
if not result.ok:
    failures.append(f'PID {pid}: {result.error or "未知错误"}')
elif result.targeted == 0:
    failures.append(f'PID {pid}: 未找到可终止的进程')   # ★ 不是成功
else:
    killed.append(pid)
```

这个 bug 是**测试揪出来的**（`test_zero_targeted_is_failure`），不是靠审查发现的。

### 陷阱二：「未知」状态一律按危险侧保守处理

`ServiceStatus.UNKNOWN` 比 `STOPPED` 多一层不确定性。所有相关判定：

| 场景 | UNKNOWN 的处理 |
|---|---|
| 是否放行启动 | 算**运行中** → 不放行 |
| 是否重启 | 算**运行中** → 不重启 |
| 是否安装 | 算**已存在** → 不安装 |
| 是否算已停止 | **不算** ✓ 只有 `ABSENT` 才算 |

```python
def _is_running(deps, name) -> bool:
    # ★ 严格枚举比较，不用 'RUNNING' in state
    #   （STOP_PENDING 的文本里也可能带 RUNNING）
    return deps.service.state(name) is ServiceStatus.RUNNING
```

### 陷阱三：两种端口口径绝不可混用

| 口径 | 参数 | 状态 | 用途 |
|---|---|---|---|
| 窄 | `listening_only=True` | LISTENING | **决定杀谁** |
| 宽 | `listening_only=False` | 含 ESTABLISHED | 只用于**留痕展示** |

**用留痕口径去杀人 = 杀掉所有客户端**（6379 上有 143 个 ESTABLISHED 连接）。

**落法**：`KillPort.execute()` 只调一次窄口径；宽口径由独立的 `inspect()` 提供
—— 「独立成方法而不是给 `execute` 加参数，就是为了让口径在调用点一眼可见」。

### 陷阱四：留痕必须在杀之前

进程死后 PID 会被**复用**。「当时是谁占着端口」一旦错过就**永久丢失** ——
之后查到的可能是完全不相关的进程。

```python
def execute(self, port, ...):
    occupiers = self.inspect(port)     # ① 先留痕（宽口径）
    self._record_before_kill(ctx, confirm)
    ...                                # ② 再杀（窄口径）
```

## ★ P3 新增：打包 spec 同步门禁

### 为什么需要

PyInstaller 的 `hiddenimports` 是**手写**清单。手写就有漂移，且漂移只在
**打包后**暴露 —— 本地源码运行完全正常。

最危险的一类：`usecases/__init__.py` 用 `__getattr__` + `_EXPORTS` 字符串表
**惰性再导出** 11 个子模块。PyInstaller 的静态分析看不到「表里的字符串 →
真的去 import 那个模块」这条边，于是子模块被**整体漏掉**。
运行时表现是 `AttributeError`。

### 门禁检查的六项

| # | 检查 | 为什么 |
|---|---|---|
| 1 | 源码有、spec 没有 | 漏列 → 运行时会炸 |
| 2 | **惰性再导出模块必须登记** | 静态分析看不到，打包后必炸（最重要） |
| 3 | spec 有、源码没有 | 拼写错误 / 删了模块忘清 |
| 4 | 必装第三方（webview） | 缺失会导致运行时崩溃 |
| 5 | 「计划中」模块已实现 | 提醒清豁免表（warning） |
| 6 | **惰性解析结果非空** | 防「假绿灯」——见下 |

### ★ 门禁开发中真实踩到的假绿灯

第 6 项不是设计出来的，是**踩出来的**。

**现象**：门禁报「✅ 通过」，但打印的「惰性再导出模块: 0」——
usecases 包明明有 11 个子模块。

**根因**：`_EXPORTS` 的写法是**带类型注解**的赋值：

```python
_EXPORTS: dict[str, tuple[str, ...]] = {...}
```

在 AST 里这是 `ast.AnnAssign`，**不是** `ast.Assign`。我的解析器只判了 `Assign`，
于是永远返回 0 个模块 —— 一个「通过但什么都没查」的门禁。

**比报红更危险**：报红会有人修；假绿灯会让所有人以为这里已经被守住了。

**修复**：同时处理 `AnnAssign` 与 `Assign`，并**加第 6 项检查**：
若 `usecases/__init__.py` 存在但解析出 0 个模块 → 直接判失败。

### 门禁也有自检

```bash
python scripts/check_spec_sync.py --selftest
```

用**合成输入**验证 8 项防御真的生效（不是靠改坏仓库里的 spec）：

```
✓ 正常输入应通过
✓ 漏列源码模块应被抓到
✓ spec 拼写错误应被抓到
✓ 惰性导出漏列应被抓到
✓ 缺少 webview 应被抓到
✓ 惰性解析为 0 应报假绿灯
✓ 已实现的计划模块应给 warning
✓ 已实现的计划模块不应报错
✓ 空输入应触发假绿灯保护
```

为此把核心逻辑抽成纯函数 `evaluate(src, spec, lazy) -> Report`，
与打印/文件读取解耦 —— 纯函数才能被合成输入直接验证。

## ★ 复用检查经验：断言副作用，不只断言返回值

用例层最容易犯的错是**「返回成功但什么都没做」**。测试体系为此有两条纪律：

1. **断言副作用**：不只 `assert result.ok`，还要断言 `FakeService.control_calls`
   里真的有那次调用、`FakeAudit` 里真的落了审计、端口真的被释放了。

2. **Fake 必须诚实**：`FakeProcess.kill_tree` 只在
   `result.ok and result.targeted > 0` 时释放端口 —— 早期版本无条件释放，
   于是**掩盖了「杀不死」场景**，让两个真实缺陷（见陷阱一）在测试里通过了。

```python
def kill_tree(self, pid, *, timeout_s=5.0):
    if self.kill_result is not None:
        # ★ 只有「真的杀掉了目标」才释放端口
        if self.kill_result.ok and self.kill_result.targeted > 0:
            self._release(pid)
        return self.kill_result
```

→ 教训：**一个过于宽容的 Fake，会把真实缺陷伪装成已修复。**
