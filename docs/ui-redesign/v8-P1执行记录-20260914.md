### 5. Domain 模块：`domain/port_contract.py` ✅ 新增

**迁移来源**：

| 原实现 | 位置 | 迁移为 |
|---|---|---|
| `_Ports` 单例 | L104-109 | `PortConfig` frozen dataclass（热更新改为整体替换） |
| `_find_port_pids(port)` | L1072 | `extract_port_pids` + `PortFilter.LISTENING_ONLY` |
| `_get_port_occupier(port)` | L395 | `parse_netstat_occupiers` + `PortFilter.LISTENING_OR_ESTABLISHED` |
| `_get_port_occupier` 的 tasklist 解析 | L406-409 | `parse_tasklist_name` |

**核心洞察：同一个 netstat 输出，两种口径刻意不同**

| 用途 | 口径 | 理由 |
|---|---|---|
| **击杀** | 仅 `LISTENING` | TIME_WAIT 会自行过期且不阻塞重绑（v5.40 审查 #23）。实测本机 TIME_WAIT **609 行**（占绝大多数），PID 恒为 0 |
| **留痕** | `LISTENING` 或 `ESTABLISHED` | 连接方也是占用者，运维需知道「谁在占用」（v5.40 审查 #6） |

**用真实数据（2026-09-14 采集，1157 行）驱动设计**：

- **TIME_WAIT 占 609 行**、ESTABLISHED 143、LISTENING 85 → 印证审查 #23 的必要性
- **UDP 行只有 4 列且无状态列**（TCP 是 5 列）→ 解析器必须做列数防御
- **IPv4/IPv6 双栈重复**：3000 端口 24 条明细 → 12 个唯一 PID

**★ 修正了旧实现的两处真实缺陷**

`_get_port_occupier` 用子串 `f':{port}' in line` 匹配，实测有两处误报：

| netstat 行（目标端口 3000） | 旧子串 | 新列位 | 说明 |
|---|---|---|---|
| `0.0.0.0:3000 ... LISTENING` | True | True | 正常 |
| `0.0.0.0:30000 ... LISTENING` | **True** | False | 误报①：`:3000` 是 `:30000` 的子串 |
| `127.0.0.1:54321  127.0.0.1:3000  EST` | **True** | False | 误报②：匹配到了**外部地址**列 |

后果：留痕日志会写出错误的占用者名单，而留痕是「按端口击杀」前唯一的可追溯记录
（审查 #6 的整改），写错等于事故无法追溯。

本实现统一采用**列位精确匹配**，误报①②均消除。已固化为测试：
`test_substring_false_positive_30000_not_matched` / `test_remote_address_not_counted_as_local`。

**双栈设计决策**：`parse_netstat_occupiers` 保留明细（`local_addr` 不同即不同记录，
留痕场景下「监听 IPv4 还是 IPv6」有价值）；`extract_port_pids` 按 PID 去重
（击杀同一 PID 两次无意义）。

**测试：`test_port_contract.py`（67 用例）** —— 样本取自真实采集，
覆盖 TIME_WAIT 排除、UDP 行防御、双栈、子串误报回归、畸形输入。

**核心安全性质（v5.40 自证断言 A5）**：

**三个必须记住的语义**：

1. **`StopResult` 的三字段契约**（§6.1）：v5.33 超时分支只返回 2 元组而调用方解包 3 个
   → `not enough values to unpack` → 开发模式 100% 启不了。
   改用 frozen dataclass 后字段数由类型定义固定，并保留 `__iter__` 让旧调用点的
   `ok, reason, stopped_any = result` 写法继续可用。
2. **失败必须带 reason**（`__post_init__` 强校验）：v5.33「生产停不掉」的一部分原因
   就是失败是空洞的，没有可诊断信息。
3. **D6：guard 只对 NSSM 托管服务有效**。`AppExit` 是 NSSM 特有概念，
   对原生 Windows 服务（erp-redis 等）毫无作用 —— 因此 `needs_restart_guard`
   的判定**只看是否有 nssm**，与目标模式无关。

**★ P0-3 的修复点**：`is_residual_prod_runner` 使用**精准特征** `'prod_runner'`，
而非 v5.33 的宽特征扫描（`python` / `node`）。后者会误杀 NSSM 监管中的进程
→ NSSM 检测 Exit → 5 秒重启 → 又被误杀 → **死循环**。精准特征 + PID 白名单双保险。
已固化为 `test_plain_python_is_not_a_residual` / `test_node_is_not_a_residual`。

## ★ 迁移过程中的两次真实纠偏（重要教训）

### 纠偏一：`wait_until` 的探测次数

写 `test_readiness.py` 时有两个测试失败。**根因是我的测试期望值算错了，
不是实现有问题** —— 但这件事暴露了一个更大的风险：

原实现 `_wait_service_running` 的结构是

```python
deadline = monotonic() + timeout
while monotonic() < deadline:   # ← 先判超时
    探测...                      # ← 后探测
    sleep(1)
```

是「**先判超时、后探测**」。我最初写成了「先探测、后判超时」（更符合直觉），
导致探测次数多 1 次。

**如果没做这个核对，就会把一次行为改变悄悄带进重构。**
在 30~60s 超时、1s 间隔的场景下这个差异几乎不可观测，
正是这种「几乎不可观测的差异」最容易在重构中积累成不可解释的故障。

**做法**：实测旧结构在注入时钟下的确切探测次数，
修正实现对齐，并把对拍数据固化为参数化测试
（`test_attempt_count_matches_legacy_semantics`）。

### 纠偏二：`test_state_machine.py` 的 6 个失败——这次是**实现**缺东西

首轮 316 passed / 6 failed，全部集中在 `StopResult` 的三字段解包：

```
TypeError: cannot unpack non-iterable StopResult object
```

**测试写得没错，是实现漏了一件事。** 我用 frozen dataclass 替换了旧的
`NamedTuple`，字段契约守住了（不可能少字段），但**丢了可迭代性** ——
而旧调用点写的是 `ok, reason, stopped_any = result`。

这等于把 §6.1 的崩溃从「少返回一个」换成了「根本不可迭代」，**换汤不换药**。

**做法**：给 `StopResult` 补 `__iter__` / `__len__` / `_fields`，
显式恢复三字段解包能力。这是**迁移保真**要求的一部分：
替换数据载体时必须盘点旧载体的**全部**能力（解包、索引、反射字段、比较），
只对齐「看起来明显」的那些是不够的。
