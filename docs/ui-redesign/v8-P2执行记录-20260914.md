## ★ 五条进程安全约定（逐条落到代码）

这五条是所有进程终止代码的底线，任何一条失守都可能造成误杀生产进程。已在 `process_win.py` 的模块 docstring 中显式记载：

| # | 约定 | 代码落点 |
|---|---|---|
| ① | **绝无 shell 参与** | `taskkill_argv()` 返回 list，调用方用 `shell=False`；全模块无 `shell=True` |
| ② | **绝不向上杀祖先链** | `kill_many()` 的 `killed` 集合只累加 `children(recursive=True)` + 自身，**绝不含 `parents()`** |
| ③ | **psutil 路径必须与 `taskkill /T` 同语义** | `kill_pid()` docstring 注明「自身 + 全部后代」；有单测断言祖先 PID 不在击杀集合内 |
| ④ | **绝不做宽特征兜底** | `scan_residual()` 在缺 psutil 时返回 `skipped_reason='缺少 psutil，跳过残留进程清理（不做宽特征兜底）'`，**不降级为按进程名杀** |
| ⑤ | **宁可漏杀不可误杀** | `is_residual_candidate()` 6 步判定链，任一步不确定即返回 False |

### 两种端口口径必须区分

这是本阶段最容易混淆、也最容易写错的地方：

| 函数 | 口径 | 用途 | 常量 |
|---|---|---|---|
| `port_pids()` | **仅 LISTENING** | 决定「杀谁」 | `LISTENING_ONLY` |
| `port_occupiers()` | **LISTENING + ESTABLISHED** | 给用户看的「谁占着端口」留痕 | `LISTENING_OR_ESTABLISHED` |

用留痕口径去杀人 → 会杀掉所有**连进来**的客户端连接；用击杀口径去留痕 → 用户看不到已建立连接的占用者。

## ★ 建立正反双向分层门禁

P1 只做了**正向**门禁（domain 层禁止 import I/O 模块）。P2 补上**反向**门禁：禁止 adapters 层复刻领域判定。

理由：分层架构真正的失守方式往往不是「domain 变脏」，而是「adapters 把判定抄一遍」—— 抄完之后 domain 层的修改不再影响运行路径，纯度门禁看着还全绿，但实际行为已经分叉。

`scripts/check_domain_purity.py::check_adapters()` 拦三类违规：

```python
DOMAIN_LITERALS = {'未安装': ..., '未知': ...}       # ① 领域状态字面量
FORBIDDEN_SERVICE_CODES = ('1060',)                  # ② sc 返回码裸字面量
ADAPTER_ALLOWED_INTERNAL = ('server_manager_v8.domain',
                            'server_manager_v8.adapters')   # ③ 非法跨层 import
```

- **① 领域状态字面量**：adapters 里出现 `'未安装'` / `'未知'` 字符串 → 说明它在自己判状态，而不是调 `parse_sc_query_output()`
- **② sc 返回码裸字面量**：adapters 里出现 `1060` → 说明它在自己解释 sc 的返回码
- **③ 非法跨层 import**：adapters 不得 import `application` / `presentation`（依赖倒置方向约束）

**门禁已实测可拦人**：注入探针文件 → 3 处命中、退出码 1；清理后 → 0 处。

新增 `--no-adapters` 参数供局部调试；`main()` 改为正反双向检查并聚合判定。`.pre-commit-config.yaml` hook 名称同步改为「分层门禁（domain 零 I/O + adapters 零判定复刻）」。

## ★ 迁移过程中的三次真实纠偏（重要教训）

### 纠偏一：`netstat_lines()` 返回类型搞错（适配器 vs 领域层的职责边界）

**现象**：
```
AttributeError: 'list' object has no attribute 'splitlines'
```

**根因**：我把 `netstat_lines()` 写成返回 `splitlines()` 后的列表，但领域层契约是
`parse_netstat_occupiers(output: str, ...)` —— 要**字符串**。

**为什么这是个深刻的问题**：适配器拆行，等于把领域层解析职责切走一半。
一旦适配器开始 `splitlines()`，下一步自然就是 `for line in lines: if 'LISTENING' in line`
—— 判定逻辑就这样一点点渗进适配层，而纯度门禁拦不住（它只能拦字面量和 import）。

**修复**：`netstat_lines()` 返回**原始字符串**，docstring 注明「适配器拆行等于把领域层解析职责切走一半」。

→ 教训：**适配器只负责「取回原始字节」，不做任何形态变换。**

### 纠偏二：`test_established_included_for_audit` 的期望值是我算错的

**现象**：
```
AssertionError: assert '5936' in {'20760', '8288'}
```

我原本断言 `127.0.0.1:54321 → 127.0.0.1:3000` 这一行里守护 3000 端口的 PID 5936 应被计入。

**实测后发现**：这一行中 **`3000` 是远端地址**，本地端口是 `54321` —— 所以 5936 **本就不该**计入。

**这正是旧实现子串匹配 `f':{port}' in line` 的误报②**：`':3000'` 匹配到了「外部地址」列。旧实现的 bug 被我错当成正确行为写进了测试。

**修复**：断言改正为 `assert '5936' not in pids`，并新增 `test_remote_address_not_counted` 固化回归防护。

→ 教训：**写测试期望值时必须回到领域层实跑确认，不能按直觉算。**（这与 skill 里已有的「对拍失败先怀疑测试」是同一条，但这次的陷阱更深：不是算错次数，而是**把旧 bug 当成了正确行为**。）

### 纠偏三（★ 实现真实漏项，对拍揪出）：非 Windows 下 `creationflags` 漏出 `134217728`

**现象**：
```
[_cap OEM 解码参数] win=False oem=True t=5:
  旧={'creationflags': 0, ...}
  新={'creationflags': 134217728, ...}
```

**根因**：我把 `_NO_WINDOW = getattr(subprocess, 'CREATE_NO_WINDOW', 0)` 写成**不判平台**；旧实现是 `CREATE_NO_WINDOW if _IS_WINDOWS else 0`。在 LINUX 上 `subprocess.CREATE_NO_WINDOW` 恰好也存在（值 `134217728`），所以漏判平台会在非 Windows 环境注入非法 `creationflags`。

**修复**：改为 `no_window_flag()` 函数按平台返回，`cap()` 调用它。

**附带发现**：`test_proc.py` 的 `test_always_has_no_window_capture_timeout` 断言了**错误行为**（断言恒有 `creationflags`），一并重写为 `test_no_window_flag_on_windows` + `test_creationflags_zero_on_non_windows`。

→ 教训：**对拍不仅要跑本平台，还要跑「平台分支」** —— 用参数化的 `win=True/False` 覆盖两个分支，否则本机永远跑不出另一分支的差异。这个 bug 若带到生产，会在 Linux 部署时炸出 `ValueError: creationflags is only supported on Windows`。

## ★ 第四个陷阱：测试断言了「错误的机制」（比断言错误的值更危险）

**现象**：
```
AssertionError: 必须有 ProxyHandler 才能清除代理 / assert []
```

我原本断言「直连 opener 里应当有一个 proxies 为空的 `ProxyHandler`」。

**实测后发现真实机制**：`build_opener` 会把「无贡献」的 handler **去重掉**，因此直连 opener 的 handlers 里**根本没有 `ProxyHandler`**；而默认 `build_opener()` 会自动补一个带 `getproxies()` 结果的 `ProxyHandler`（本机实测 `{'https': 'http://127.0.0.1:54590', ...}`）。

**修复的表现是「handler 缺失」，不是「有 proxies 为空的 handler」。**

**修复**：重写整个 `TestBuildDirectOpener` 类：
- 核心断言改为 `proxy_handlers == []`
- 加反例 `test_env_proxy_would_be_used_without_the_fix`
- 加对比 `test_direct_opener_differs_from_naive_when_proxy_set` 证明这个修复有意义

→ **这是本轮最值得记的教训**：断言错误的值 → 测试失败 → 你立刻知道要改；**断言错误的机制** → 如果实现恰好也「顺着」写（比如硬塞一个空 ProxyHandler 进 handlers），测试会**通过**，然后把错误认知固化成假安全感传给后人。

**防法**：对「机制性断言」先写最小验证脚本实测，看到真实内部状态再写断言。
