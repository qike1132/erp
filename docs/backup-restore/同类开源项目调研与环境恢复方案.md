# 「新服务器一键恢复运行环境」同类开源项目调研与落地裁决

> 调研日期：2026-08-29 ｜ 场景：ERP 服务器管理器新增「备份与恢复」模块，目标=新服务器一键还原整套运行环境（迁移/容灾）
> 检索范围：PostgreSQL 备份恢复 / Windows 整机备份 / 加密去重文件备份 / 声明式环境重建四大方向
> 结论先行：**无单一开源轮子可整体套用**；行业通解是"分层组合"——本方案维持自研 v3.0 内核，逐层借鉴成熟范式。

---

## 1. 同类项目对比

### 1.1 数据库层：PostgreSQL 备份恢复

| 项目 | Stars/语言 | 功能设计 | 技术架构 | 优劣 | 本项目借鉴 |
| --- | --- | --- | --- | --- | --- |
| **pgBackRest** | 3.7k / C | 全量+增量(块级)+差量、并行、加密、校验、delta restore、PITR、S3 | 物理备份（数据目录+WAL），conf 驱动 | ✅ PG 生态事实标准、功能最全、加密内建 ｜ ⚠️ 面向大库(≥500GB)、需 WAL 归档、仅 8KB 块 | 大库增强选项（P4），小库不引入 |
| **Barman** | 2.8k / Python | 多服务器集中备份、流式 WAL、rsync 增量、PITR | 中央备份主机 + SSH/流复制 | ✅ EDB 商业支持、Python 可扩展 ｜ ⚠️ 无并行/无校验、配置重 | 多实例管理思路（本项目单实例，弱相关） |
| **WAL-G** | 4k / Go | 页级增量、PITR、S3/云原生；**支持 PG+MySQL+Redis+MongoDB** | 单二进制 + 云存储 | ✅ 单文件零依赖、Go 性能好、多数据库 ｜ ⚠️ 无差异/增量备份接口（页级 delta 为主） | 若需"多库统一备份"，它是样板（本项目 Redis 走 RDB 更简单） |
| **pg_dump/pg_restore**（内置） | — | 逻辑导出：SQL/custom 格式、并行、跨大版本迁移最安全 | 官方工具 | ✅ 迁移首选、只读权限即可、无需停机 ｜ ⚠️ 无增量/PITR | **本项目 DB 层主引擎（库小：63 表 / ~27k 行 / 6.7MB）** |

**裁决**：DB 层用 **pg_dump -Fc + JSON 双轨**（迁移安全、无停机、零新依赖）。pgBackRest/WAL-G 列为 P4 可选增强（数据量上 GB 级且要 PITR 时再评估）。

### 1.2 文件/配置层：加密去重备份

| 项目 | Stars/语言 | 功能设计 | 技术架构 | 优劣 | 本项目借鉴 |
| --- | --- | --- | --- | --- | --- |
| **restic** | 33k / Go | 内容寻址分块去重、AES-256 加密、多后端(S3/B2/GCS/Azure/SFTP)、增量快照 | 单二进制，本地/远程仓库 | ✅ 最广社区、单文件跨平台、后端最全 ｜ ⚠️ 无内置 GUI、内存占用偏高 | 异地副本通道（备份 .envbak 后推 S3/WebDAV） |
| **Kopia** | 13k / Go | 去重+压缩(zstd)+AES-256-GCM/ChaCha20、**内置 Web UI/桌面端**、按目录策略、服务端模式 | 单二进制 + KopiaUI | ✅ Windows 支持全、内置 UI/调度、WebDAV/S3 原生 ｜ ⚠️ 较新(2019)、资源占用较高 | 若未来要"文件层独立引擎"的首选替代 |
| **BorgBackup** | 13k / Python+C | 压缩最强、append-only 防勒索、FUSE 挂载 | 仓库需本地/SSH 服务端 | ✅ 存储效率最高 ｜ ⚠️ Windows 仅 WSL、后端少 | 不适用（Windows 场景） |
| **Duplicati** | 6k / C# | 纯 Web UI、20+ 云后端、块级增量、AES 加密 | .NET + Web 服务 | ✅ GUI 友好、适合消费云盘 ｜ ⚠️ 性能一般、历史 bug 多 | 不引入 |

**裁决**：文件层维持 **自研 ZIP + AES-256-GCM**（复用既有 `core/backup_encryption.py`，零新依赖、与 meta/进度键体系天然融合）。restic/Kopia 的角色 = **可选"异地副本通道"**（P4）。

### 1.3 Windows 整机/裸机层

| 项目 | Stars/语言 | 功能设计 | 技术架构 | 优劣 | 本项目借鉴 |
| --- | --- | --- | --- | --- | --- |
| **UrBackup** | ~2.1 万实例 / C++ | 文件+映像双备份、增量极快（Change Journal）、去重、VSS 一致快照、裸机恢复(USB)、Web 管理 | Client/Server：UDP 发现 + TCP 传输 + Web(55414) | ✅ Windows 支持好、文件+镜像完备、AGPL ｜ ⚠️ 独立重型系统（客户端/服务端），与"管理器内置模块"形态冲突 | **只借范式不引本体**：VSS 一致性、增量追踪思路 |
| **Veeam Agent(免费)** | 商业 | Windows 裸机/文件备份、恢复介质 | 商业代理 | ✅ 可靠 ｜ ⚠️ 商业授权/重 | 外部可选：整机镜像层由 Veeam/UrBackup 承担，管理器管应用层 |

**裁决**：OS 级整机镜像**不并入管理器**（超出"ERP 运行环境"边界、体积/复杂度失控）；作为文档化的外部可选层。管理器内借用其 **VSS 一致性**（备份时对打开文件做 shadow copy）与"增量变化追踪"思想。

### 1.4 环境重建/迁移方法论

| 项目 | 定位 | 关键范式 | 本项目借鉴 |
| --- | --- | --- | --- |
| **Ansible** | 声明式环境重建（IaC = DR 计划） | 迁移五阶段：**清点源机 → 供给新机 → 同步数据 → 切换 → 验证 → 回滚**；`site.yml` 一条命令重建整机 | **恢复引擎即"迷你 Ansible"**：runtime/services 清单 = playbook，执行器 = 预检→还原→注册→自检→回滚（本方案已有此结构） |
| **Docker Compose + Volume** | 容器化环境整体迁移 | 编排文件 = 环境定义；数据卷备份/恢复；healthcheck 自检 | 若未来容器化，范式可平移；当前 NSSM 原生栈不引入 |

## 2. 关键结论（调研启示）

1. **没有"装了就一键迁移 Windows 上 Python/Node/NSSM 栈"的现成轮子**——自研模块是正解，这与首轮调研结论一致（同类面板/工具都聚焦单层：要么 DB、要么文件、要么整机）。
2. **行业通解 = 分层组合**：数据库用官方 dump 工具（迁移安全）｜文件/配置用加密归档｜OS 层用镜像工具（可选外部层）｜环境定义用声明式清单。
3. **本方案 v3.0 结构与行业范式高度吻合**，无需推倒重来，只需按调研补充 3 处增强点：
   - **DB 层确认**：pg_dump -Fc 为主（跨大版本迁移最安全，符合"新服务器"场景）；
   - **一致性借鉴**：VSS shadow copy（备份时对 app/conf 做一致快照，替代"停写窗口"的硬停机）；
   - **异地副本通道**：restic/rclone 推送到网络盘或 S3（解决"备份单点存储"风险）。

## 3. 落地裁决（待确认）

| 决策点 | 裁决 | 理由 |
| --- | --- | --- |
| 引擎基线 | **自研 v3.0 内核**（ZIP + AES-256-GCM + 复用现有编排/增量/进度键/加密） | 零新依赖、与既有备份子系统无缝融合；restic/Kopia 等引入反而增加维护面 |
| DB 一致性 | pg_dump -Fc `--single-transaction` 为主 + JSON 双轨 | 迁移安全、无停机；数据量小（<10GB）无需 pgBackRest |
| 文件一致性 | 备份时启用 **VSS shadow copy**（借用 UrBackup 范式）替代硬停机窗口 | 打开文件也可一致备份；恢复端无需 VSS |
| 异地副本 | 可选通道：`.envbak` 复制到网络盘 / rclone 推 S3（restic 仓库可选） | 满足 3-2-1 容灾；默认关闭、配置开启 |
| 大库/PITR | P4 可选项：数据量上 GB 且需 PITR 时评估 pgBackRest/WAL-G | 当前规模不需要 |
| 整机镜像 | 不并入；文档化外部可选层（Veeam/UrBackup） | 边界清晰，避免失控 |
