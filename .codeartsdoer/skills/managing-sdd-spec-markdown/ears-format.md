# EARS格式规范

## 概述
EARS (Easy Approach to Requirements Syntax) 是一种简化的需求语法方法，用于编写清晰、可测试的需求。

## EARS模式

### 1. 普遍性需求 (Ubiquitous)
**格式**: 系统**应**[功能描述]
**适用场景**: 适用于所有情况的需求
**示例**: 系统**应**记录所有用户操作日志

### 2. 状态驱动需求 (State-driven)
**格式**: 当[状态/条件]时，系统**应**[功能描述]
**适用场景**: 当系统处于特定状态时的需求
**示例**: 当用户已登录时，系统**应**显示用户个人信息

### 3. 事件驱动需求 (Event-driven)
**格式**: 当[事件]时，系统**应**[功能描述]
**适用场景**: 当特定事件发生时的需求
**示例**: 当用户点击"提交"按钮时，系统**应**验证表单数据

### 4. 可选功能需求 (Optional feature)
**格式**: 当[条件]时，系统**应**[功能描述]
**适用场景**: 仅在特定条件下适用的需求
**示例**: 当启用高级功能时，系统**应**提供数据分析报表

### 5. 异常需求 (Exception)
**格式**: 当[异常情况]时，系统**应**[异常处理]
**适用场景**: 处理错误或异常情况的需求
**示例**: 当数据库连接失败时，系统**应**显示错误提示并记录日志

## 验收标准格式

### Given-When-Then格式
```
给定(Given): [前置条件]
当(When): [触发动作]
那么(Then): [预期结果]
验证: [验证方式]
```

### 验证方式
- `programmatic`: 可通过自动化测试验证
- `human-judgment`: 需要人工判断验证
- `integration`: 需要集成测试验证

## 需求编号规则
- 功能需求: FR-1, FR-2, FR-3...
- 非功能需求: NFR-1, NFR-2, NFR-3...
- 验收标准: AC-1, AC-2, AC-3...

## 最佳实践
1. 每个需求应该是原子性的，只描述一个功能点
2. 避免使用模糊词汇，如"适当"、"合理"等
3. 需求应该是可测试和可验证的
4. 使用主动语态，明确责任主体
5. 保持需求描述简洁明了
