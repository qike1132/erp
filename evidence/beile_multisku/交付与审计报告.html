2问题与根因链

用户现象：同一订单、同一下单时间包含约 20 个 SKU 时，页面无法显示每个 SKU 各自的订单数量。 逐层下钻后确认这是五层叠加的问题，任一单点修复都不足以解决。

  1. 数据模型层（主因）汇总下单一律「1 个客户 = 1 张采购单」，多 SKU 产品名被 '、'.join 拼接、数量被求和写入 purchase_order.product_quantity。 逐 SKU 下单量自落库起即不可还原。
  2. 读路径口径错误订单级数量取 MAX(product_quantity)。该写法本意是「同 SKU 拆多供应商去重」， 但当一张采购单覆盖多张客户订单时（实测有单覆盖 15 张），每张订单都显示同一合计，系统性高估。
  3. 前端列语义漂移数量列在「无筛选时显示 63791」与「筛选后显示 32766」两个值之间跳变 —— 同一行两个真相。
  4. 虚拟列表测量自相矛盾measureItems() 量的是被 inline 固定高约束后的盒子， 而 getItemStyle() 又把 estimatedHeight(54) 写回固定高 ⇒ 行高恒 54px， 配合 .bo-td{overflow:hidden} 直接裁掉超出内容。20 SKU 行自然高约 464px，会被裁成 2 行。
  5. 筛选作用域前端从不向后端传产品筛选参数，只在当前页 18 条上做客户端过滤 ⇒ 「搜到 0 行」被误报为「订单不存在」。
关键判断

RC-4 若不先修，直接实现逐 SKU 展开会让症状更糟（20 SKU 行被裁成 2 行）。 因此它被列为方案硬前置 P-0。

3治本方案：逐 SKU 数量快照

核心是新增 purchase_order_sku 表，把逐 SKU 的订单数量、备品量、损耗率在写路径落库， 使「每个 SKU 各自的下单量」成为可还原的事实，而不是靠前端猜测。

字段含义备注
po_id所属采购单FK → purchase_order.id ON DELETE CASCADE
product_nameSKU 产品名读路径按归一化名称匹配
order_qty该 SKU 的订单数量合并后数量，不摊派
spare_qty备品量ceil(order_qty × 损耗率‰)，费率变更时重算
spare_rate损耗率快照千分之几，可追溯
source_order_id
source_record_type		来源记录定位必须含类型：本仓 order.id 与 stockin.id 会撞号，缺列会串号
口径恒等式

Σ order_qty == purchase_order.product_quantity（同一采集口径）。 唯一约束 (po_id, source_record_type, source_order_id, product_name) 作为第二道防线； 不纳入 product_barcode（可空，PG 下 NULL != NULL 会使约束失效）。

踩坑记录（值得记住）

migrations/alembic.ini 的 script_location = . 是相对当前工作目录解析的， 从仓库根直接执行会报 ImportError: Can't find Python file env.py。

解法是用驱动脚本把 script_location 设为绝对路径、保持 cwd 不变—— 若改成 cd migrations，.env 与 settings 的相对解析会跟着偏移，风险更高。

混合态安全阀（设计上已覆盖）

回填只覆盖 17/30 张单，属于「部分回填」混合态。读路径的 rollup_ok 要求 「该来源的全部关联采购单都有逐 SKU 快照」，否则回退旧口径 —— 不会因部分回填产出错误数值。

5QA 发现并修复的备货行缺陷

多 SKU 主链路通过后，独立回归在备货（stockin）行揪出两处缺陷，其中一处页面可见、数值放大近 97 倍。

5.1 现象与独立复现

备货单客户 / 产品自身数量模糊命中采购单精确逐 SKU修复前注入值
35045TOP TOY / 变形金刚10000[20397] → 9694610 行969461 / 980126
35042MINISO国内 / Nommi10000[20351,20352,20385,20384,20383] → 124241 行 = 10000行级 12424 ≠ 10000
35043MINISO国际 / 妹妹二代100004 张全 100004 行10000（正确）

根因三层，缺一不可：备货行只能用「(客户名, 产品名) 模糊匹配」找采购单 → 命中集合的 MAX(product_quantity) 被当成该备货自己的数量 → 前端「单 SKU 且已下单则回退订单级」把该值直接显示为 SKU 数量。

注意：属既有缺陷，非本轮引入

修复前页面同样显示 969461，但本轮的降级规则使其继续暴露，且违反「降级不得编造数字」的硬要求，因此必修。

5.2 治本修复

修复契机是：回填后的 source_record_type 让备货行首次具备「精确（带类型）匹配」能力。

层改动

7遗留事项与设计取舍

7.1 一处需要业务方知情的语义取舍

备货行「无精确依据时不显示数量」的代价

新契约下，当模糊匹配恰好正确时（例如只有一个候选采购单），备货行也会退化为 「自身数量 + 生产数量『—』」，即损失了那份本来正确的信息。

判断依据：无法区分「对的模糊」与「错的模糊」（id 撞号且历史数据无类型信息）， 宁可不给无法证明的数字；真实生产 30 张 completed 采购单全部有非空 source_order_ids，故该退化只影响无逐 SKU 快照的历史备货；正路径（以该备货为来源生成的采购单会写入 source_record_type='stockin' 快照）已就位。

7.2 遗留清单

编号事项影响状态
R-113 张历史采购单源订单已被清理，永久走降级口径这些单在页面不渲染，无用户可见差异已定性
R-2备货行模糊匹配正确时亦不显示数量仅历史数据；正路径已覆盖需业务确认
