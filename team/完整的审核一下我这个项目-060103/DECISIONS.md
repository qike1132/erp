## 决策 1 · 本轮为只读审核（用户 Q1 拍板）

- **选了什么**：本轮不产生任何业务代码改动；交付形态固定为「总报告 + 分维度/分角色报告 + 可执行整改 backlog」。所有角色的 `inScope` 只写 run-dir 下的工件路径。
- **备选**：① 只读审核 + 直接修复（边审边改）；② 只读审核但允许提交 git（便于回滚修复）。
- **为什么不选**：① 违反 Q1，且**这台机器既是生产主机也是运维主机**（`AGENTS.md` §0），无独立测试/预发环境，边审边改会把未验证的改动直接推给在用业务；② Q1 同时禁止任何 git 写操作，且审核过程本身不产生需要回滚的变更。
- **落地**：`SPEC.md` §6「边界与禁止项」；`TASKS.json` 每条任务的 `contract.forbids`。

## 决策 2 · 跳过竞品 / 行业调研腿，改为 OWASP + 等保基线对标

- **选了什么**：不设独立的竞品调研任务；把安全维度的对标工作并入 `T10`（sec），产出 OWASP Top 10 (2021) 十项逐项结论 + 等保 2.0 基线对标。
- **备选**：① 保留独立竞品调研腿（对标同类 ERP 产品）；② 完全不做任何外部对标。
- **为什么不选**：① SKILL §7.12 的双研究允许在**无竞品需求**时合并为一项；本项目是**内网部署的内部生产系统**，不参与市场竞标，竞品调研**不产生可执行整改项**，只会消耗深度预算（Q5 要求把预算用在修复后验证上）；② 完全不对外部基线会导致安全审计缺一把公认的尺子，无法回答「够不够安全」。
- **落地**：`SPEC.md` §2.1 的 D05 行；`TASKS.json` T10 的 `acceptance`（OWASP 十行表）与 `SPEC.md` A23。

## 决策 6 · 分维度报告的工件命名用 `AUDIT-<DIM>.md`

- **选了什么**：模板既有名（`SPEC.md` / `PLAN.md` / `RESEARCH.md` / `REVIEW.md` / `TEST.md` / `SUMMARY.md` / `AUTHORITY.md` / `DECISIONS.md` / `TASKS.json` / `任务看板.md`）**优先复用**；模板未覆盖的分维度报告统一命名 `AUDIT-<DIM>.md`（`AUDIT-ARCH.md` / `AUDIT-BACKEND.md` / `AUDIT-FRONTEND.md` / `AUDIT-DB.md` / `AUDIT-SEC.md` / `AUDIT-OPS.md` / `AUDIT-DOCS.md` / `AUDIT-UIUX.md` / `AUDIT-PERF.md` / `AUDIT-CONSISTENCY.md`）。
- **备选**：① 把 10 份分维度报告塞进模板既有的 `REVIEW.md` / `PLAN.md` 等少数几个文件；② 用中文文件名（`架构审计.md`）；③ 每个维度建子目录 `audit/ARCH.md`。
- **为什么不选**：① 模板既有名有**单一负责人**（`REVIEW.md` → reviewer、`TEST.md` → qa），把 backend/dba/sec 的产出塞进去会造成**跨角色覆写**，且 `REVIEW.md` 被 T05/T15 复用会互相踩；② 中文文件名在 PowerShell 5.1 + Python 的路径处理上多一层编码风险（本机已知 BOM/编码坑），且不利于脚本化机判；③ 子目录会让「文件存在 + 字节数」这类机判验收多一层路径拼接，收益为零。
- **额外理由（可核）**：`AUDIT-*.md` **不在**专家团插件的工件归属表（`lib/artifact-ownership.js` 的 `ARTIFACT_OWNERS`）里 —— 该表未列入的文件名**不限制写入**，因此各角色可以各自 `write` 自己的分维度报告而**不触发 R1 工件归属门禁**；反之若复用 `REVIEW.md`，除 reviewer 外的角色会被 pre-execute 门禁直接拦下。
- **落地**：`SPEC.md` §2.2 责任矩阵；`TASKS.json` 各任务的 `inScope`。
