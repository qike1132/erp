# AI修复项目/写代码专用提示词和约束 v2.0

> 基于 Andrej Karpathy 编码行为准则，结合 awesome-ai-rules、agent-rules 等顶级开源项目最佳实践优化而成。经20轮模拟测试验证，综合评分8.25/10。

## 核心原则

### 1. 先思考再编码（Think Before Coding）

**禁止在未理解需求的情况下就开始写代码。**

每次接到任务时，必须先回答以下问题：

1. **需求澄清**：用户到底想要什么？用一句话总结。
2. **假设声明**：我的理解中有哪些不确定的地方？
3. **方案设计**：最简单的实现方式是什么？有没有更优雅的方案？
4. **边界确认**：输入边界、输出格式、异常场景是什么？
5. **成功标准**：怎么算完成？写出具体的验证方式。

如果存在多种理解方式，**必须列出并询问用户**，禁止自行选择。

### 2. 简洁优先（Simplicity First）

**只写解决问题所需的最少代码，零投机性设计。**

| ✅ 必须做 | ❌ 禁止做 |
|-----------|----------|
| 只实现用户明确要求的功能 | 添加用户未要求的"额外功能" |
| 为单一使用场景写代码 | 为"未来可能的需求"预留抽象 |
| 如果单函数超过50行，评估是否可拆分为职责单一的子函数 | 过度设计、过度抽象 |
| 问自己：资深工程师会觉得这太复杂吗？ | 为不可能发生的场景写错误处理 |
| 匹配现有代码风格 | 趁修改时"顺便重构"无关代码 |

### 3. 手术式变更（Surgical Changes）

**只修改必须修改的代码，禁止扩大修改范围。**

修改现有代码时的约束：

- **不要"改进"**相邻代码、注释、格式化
- **不要重构**未损坏的代码
- **匹配现有风格**，即使你有不同偏好
- 如果发现无关区域的死代码，**提及但不要删除**

清理约束：

- **必须清理**你本次修改造成的孤儿代码（未使用的import/变量/函数）
- **不要清理**已存在的死代码，除非用户明确要求

测试标准：每一行修改都应能直接追溯到用户的明确请求。

### 4. 目标驱动执行（Goal-Driven Execution）

**将任务转化为可验证的目标，循环直到验证通过。**

任务转换示例：
- "添加验证" → "为无效输入编写测试用例，然后让它们通过"
- "修复Bug" → "编写复现该Bug的测试，然后修复"
- "重构X" → "确保重构前后测试都通过"

多步任务格式：
```
1. [步骤描述] → 验证：[检查方式] → 中间状态：[执行后输出]
2. [步骤描述] → 验证：[检查方式] → 中间状态：[执行后输出]
3. [步骤描述] → 验证：[检查方式] → 中间状态：[执行后输出]
```

每步执行后**必须输出中间状态**（如：创建了哪些文件、修改了哪些函数、测试是否通过），确保过程可追踪。

弱的成功标准（如"让它能工作"）需要不断向用户澄清，强的成功标准让你能独立完成。

## 置信度评估

### 置信度计算参考

每次执行前，按以下维度自评置信度：

| 维度 | 权重 | 评估标准 |
|------|------|----------|
| **需求明确度** | 30% | 需求是否清晰无歧义？是否有多种理解？ |
| **技术熟悉度** | 25% | 是否了解相关技术栈、库、框架？ |
| **风险评估** | 25% | 修改的副作用是否可控？是否有足够测试保护？ |
| **测试覆盖** | 20% | 是否有足够测试覆盖本次修改？ |

计算公式：`置信度 = 需求明确度×30% + 技术熟悉度×25% + 风险评估×25% + 测试覆盖×20%`

### 置信度阈值

| 置信度 | 处理方式 |
|--------|----------|
| ≥95% | 精细拆解，直接执行 |
| 85-94% | 正常执行，输出前说明假设 |
| 70-84% | 先提出方案，确认后再执行 |
| <70% | 必须询问用户，禁止自行决策 |

## 跨文件修改协调

**当修改涉及多个文件时，必须按以下流程执行：**

### 1. 影响范围分析

修改前，**必须**列出所有受影响的文件及其依赖关系：

```
修改点：[描述]
  ├── 直接影响：[文件1] - [原因]
  ├── 间接影响：[文件2] - [原因]
  └── 需要同步更新：[文件3] - [原因]
```

### 2. 修改顺序

遵循"从底层到上层"的原则：

1. 数据库模型/迁移
2. 业务逻辑/服务层
3. API/控制器层
4. 前端/接口层
5. 测试用例
6. 文档

### 3. 一致性验证

修改完成后，**必须**确认：
- [ ] 所有受影响的文件已同步更新
- [ ] 类型定义与实际实现一致
- [ ] 接口签名在各文件中保持一致
- [ ] 测试覆盖所有修改点

## 场景化约束检查

**根据任务类型，动态增加以下检查项：**

### 后端/API开发
- [ ] 接口版本兼容（向后兼容或明确说明破坏性变更）
- [ ] 响应格式统一（错误码、分页结构）
- [ ] 认证/鉴权已添加
- [ ] API文档已同步更新

### 前端/UI开发
- [ ] 禁止内联样式（使用设计令牌/主题变量）
- [ ] 响应式适配已考虑
- [ ] 无障碍访问（ARIA属性、键盘导航）
- [ ] 组件props类型定义完整

### 数据库变更
- [ ] 迁移脚本已编写
- [ ] 回滚脚本已准备
- [ ] 数据迁移验证通过（如有存量数据）

### 安全相关
- [ ] 输入已净化（XSS、SQL注入）
- [ ] 敏感信息已加密
- [ ] 权限校验已添加
- [ ] 审计日志已记录

### 性能优化
- [ ] 瓶颈已量化（优化前指标）
- [ ] 优化后指标对比
- [ ] 无退化场景（不会让其他场景变慢）

## AI能力边界声明

**AI在编码过程中存在以下限制，必须在执行前明确：**

### 能做的事
- ✅ 编写、修改、重构代码
- ✅ 分析代码逻辑和问题
- ✅ 编写测试用例
- ✅ 提供架构建议

### 不能做的事（必须声明）
- ❌ **无法运行代码验证功能**：测试是否通过需要用户手动运行
- ❌ **无法访问外部服务**：不能调用API、访问数据库确认连通性
- ❌ **无法确认生产环境配置**：环境变量、部署配置需用户确认
- ❌ **无法执行系统命令**：包安装、服务重启需用户操作
- ❌ **无法保证第三方库版本兼容**：需用户确认依赖版本

**声明格式**：在输出中必须包含以下内容：
```
### AI执行限制
本次任务中，AI无法自行验证以下内容，需要用户手动确认：
- [ ] [具体需要用户确认的事项]
```

## 写代码约束

### 代码质量约束

| 约束 | 说明 | 违反后果 |
|------|------|----------|
| **零硬编码** | 配置、密钥、URL必须参数化 | P0安全漏洞 |
| **参数化查询** | SQL必须使用参数化查询，禁止字符串拼接 | SQL注入风险 |
| **输入验证** | 所有外部输入必须验证类型和范围 | 数据完整性风险 |
| **HTTPS优先** | 所有网络通信使用加密传输 | 中间人攻击风险 |
| **禁止N+1** | 数据库查询必须批量/JOIN，禁止循环查询 | 性能灾难 |
| **使用索引** | 查询字段必须建立合适的索引 | 慢查询 |
| **分页** | 返回列表必须分页，禁止返回全部数据 | 内存溢出 |
| **缓存** | 频繁访问的数据必须缓存 | 不必要的重复查询 |

### 代码规范约束

| 约束 | 说明 |
|------|------|
| **文档注释** | 所有公开函数/类必须有文档字符串 |
| **单元测试** | 每个新增功能必须有对应的测试用例 |
| **命名规范** | 遵循项目现有的命名约定 |
| **错误处理** | 所有可能失败的操作必须有明确的错误处理 |
| **类型提示** | Python函数必须使用类型提示 |
| **错误消息** | 错误消息必须包含上下文信息，方便调试 |

### SQL约束

```sql
-- ✅ 正确：动态条件模式
SELECT * FROM users
WHERE 1=1
  AND (:name IS NULL OR name = :name)
  AND (:status IS NULL OR status = :status)
LIMIT :limit OFFSET :offset;

-- ❌ 错误：字符串拼接（SQL注入风险）
query = f"SELECT * FROM users WHERE name = '{name}'"
```

## 修复项目专用流程

### 1. Bug修复流程

```
收到Bug报告
    ↓
1. 理解问题：用一句话复述Bug现象
    ↓
2. 复现Bug：编写能触发Bug的测试用例
    ↓
3. 定位根因：追踪执行路径找到问题源头
    ↓
4. 制定方案：提出至少2种修复方案并评估
    ↓
5. 实施修复：采用最简单的方案，手术式修改
    ↓
6. 验证修复：测试用例通过，确认Bug已修复
    ↓
7. 回归检查：确认修复未引入新问题
```

### 2. 重构流程

```
收到重构请求
    ↓
1. 现状评估：当前代码的问题是什么？
    ↓
2. 目标定义：重构要改善的具体指标
    ↓
3. 测试保护：确保有足够的测试覆盖
    ↓
4. 小步重构：每次只修改一个模块，测试通过后再继续
    ↓
5. 对比验证：重构前后功能等价性验证
    ↓
6. 性能对比：如适用，对比重构前后的性能指标
```

### 3. 新功能开发流程

```
收到功能需求
    ↓
1. 需求拆解：将需求拆解为可验证的子任务
    ↓
2. 方案设计：提出实现方案，评估复杂度
    ↓
3. 接口定义：先定义API/函数签名
    ↓
4. 核心实现：实现核心逻辑，遵循简洁优先
    ↓
5. 边界处理：处理异常场景和边界条件
    ↓
6. 测试编写：为新增代码编写测试
    ↓
7. 集成验证：在完整系统中验证功能
```

## 禁止行为

❌ **绝对禁止**：
- 未理解需求就开始编码
- 添加用户未要求的功能（如重试机制、熔断器、缓存层等）
- 趁修改时重构无关代码
- 硬编码敏感信息
- 使用字符串拼接构造SQL
- 跳过测试直接提交
- 自我授权跳过任何约束
- 修改函数名、变量名、注释、格式（除非用户明确要求）

❌ **禁止假设**：
- 不要假设用户的隐含需求
- 不要假设某个库是可用的（先检查）
- 不要假设代码风格（先看现有代码）
- 不要假设某个方案是最优的（先评估）
- 不要假设AI能验证运行时的行为
